# 📜 知识库内容编写与表达规范

> **最高纲领与核心定位**：
> 本规范是整个技术知识库（Java 后端、分布式、AI 应用开发等）的最高内容生产、重构与审查标准。
> 恪守 **KISS（简洁至上）**、**第一性原理（深度分析）** 与 **事实为本** 三大核心准则，旨在打造工业级、高质量、兼顾工程实战与认知效率的顶级技术知识库。

## 🧭 一、核心理念与写作原则

### 1. 简洁至上（KISS 原则）

- 简洁以讲清楚和覆盖关键内容为前提：问题背景、核心原理、必要例子与适用边界不能为了缩短篇幅而省略；
- 崇尚清晰、简洁与可维护性，杜绝过度工程化与没有必要的防御性设计；
- 能用一句话讲透的结论，绝不堆砌大段车轱辘话；
- 避免为了“看起来很高深”而引入冗余的废话和非必要复杂度。

### 2. 第一性原理（深度剖析）

- 不停留在“怎么配”或“API 怎么调”，必须刨根问底“为什么这样设计”；
- 根据主题深入必要的底层机制；例如需要解释并发时，再讨论 JVM、内存屏障或操作系统调度，不为追求深度而堆砌无关细节。

### 3. 事实为本（工程真实性）

- 示例可以简化，但要说明前提和省略的内容；不要把演示代码或模拟结果写成生产验证；
- 所有技术论断必须经得起官方源码、RFC 规范和工业级生产排障的推敲；
- 凡有业界演进（如 JDK 15+ 废弃偏向锁、JDK 21 虚拟线程挑战 WebFlux），必须如实反映最新工程趋势，杜绝背诵过时的老旧八股文。

## ❓ 二、提问与面试问答规范（默认折叠、支持自测）

提问与面试连环问的根本价值在于**“检验掌握程度、激发读者的主动联想与深度自测”**。如果将题目与答案直接平铺展开，读者一眼扫过就会产生“我已经懂了”的认知错觉，彻底丧失主动复盘的价值。

### 1. 核心标准：强制使用原生默认折叠 Question 引用块

全库中所有面试题、连环追问、深入思考题、30 秒面试绝杀等场景，**一律强制采用 Obsidian 原生默认折叠块语法**：

```markdown
> [!question]- 题目编号与完整题干（支持一览问题，不剧透答案）
> 核心解答结论（30 秒答题版）...
> 
> 深入底层机制展开（2 分钟深入版）...
> 
> **生产实战与排障避坑**：
> 1. 要点一...
> 2. 要点二...
```

### 2. 编写铁律（Checklist）

| 规则维度 | 正确规范（DO） | 严厉禁止（DON'T） |
| :--- | :--- | :--- |
| **折叠标识** | 必须带有减号：`> [!question]-`（默认收起） | ❌ 严禁使用无减号的 `> [!question]`（平铺展开） |
| **题干位置** | 完整题干直接跟在 `> [!question]- ` 之后 | ❌ 严禁在标题栏写“点击查看答案”、“高频问题”等废话 |
| **展示形式** | 独立卡片化折叠展示 | ❌ 严禁使用无折叠的大表格、无折叠列表展示长篇问答 |
| **口语前缀** | 答案直接进入核心阐述，层次分明 | ❌ 严禁添加“现场绝杀：”、“【答】”、“【答案解析】”等多余口语前缀 |
| **首尾修饰** | 干净利落，直接展示文本 | ❌ 严禁在回答外层包裹生硬的中文双引号 `“...”` |
| **多行缩进** | 折叠块内部每一行（含空行、列表、代码块）必须带 `> ` | ❌ 严禁在折叠块中漏写 `>` 导致 Markdown 块结构断裂 |

## 💡 三、举例与比喻规范

先说明问题，再用例子解释关键过程：例子可以紧跟相关正文，也可以放进引用块或独立小节，以读者容易理解为准。技术推导中的输入、输出和边界应明确，不用与实际机制不符的类比替代解释。
- 同一主题尽量沿用一个贯穿示例，避免每节都换一套数据；例子只保留理解当前知识所需的细节。
- 类比适合建立直觉，但要指出类比的边界；能直接说清楚时，不必强行类比。
- 模拟数据、示意流程与真实测试结果要明确区分，不把演示写成生产验证。

## 📝 四、排版、引用、图表与代码规范

### 1. 标题和空行

文件名简短、见名知意，保留编号和必要的英文术语；章节标题可以使用与内容相符的 emoji，方便浏览，但不为装饰重复堆砌。
标题、代码块、引用块、表格和 Mermaid 图的前后各留一个空行；普通正文描述相邻时不额外插空行。正文引出无序或有序列表时，列表紧接正文，中间不留空行；列表前是标题、代码块、引用块、表格或 Mermaid 图时，仍按这些块的规则留空行。
同一知识点可写成一段正文，或一段说明加列表，按内容选择。列表项保持简短，一句话能说清楚就直接写；只有标签有助于区分和查找时，才用“加粗标签：解释”。精简时保留必要的解释和边界。

### 2. Obsidian 引用与提问

- 使用 `> [!abstract]`、`> [!tip]`、`> [!warning]` 等引用块突出定义、提示和边界，避免把整篇正文都放进引用块。
- 自测题、面试题使用默认折叠的 `> [!question]- 完整题目`，答案紧随其后，每一行都保留 `>`。
- 引用整个文档使用 `[[文件名|显示文字]]`；指向具体章节使用 `[[文件名#章节标题|显示文字]]`；确有必要指向某个具体段落时，在独立段落末设置稳定的 `^块ID`，并使用 `[[文件名#^块ID|显示文字]]`。需要直接嵌入内容时使用 `![[文件名#^块ID]]`；列表、引用块和表格等结构化块的 ID 按 Obsidian 规则单独成行。
- 优先链接现有内容，避免复制同一段解释。改名、合并或移动文件后，同步更新全库引用，并检查章节标题与块 ID 是否仍然存在。

### 3. Mermaid 图表

只在流程、层次或对比确实需要图时使用 Mermaid；节点写清楚角色、输入和输出，不靠装饰拉长图表。图必须经过 Mermaid 解析检查，包含括号、引号或特殊符号的节点标签应正确转义；若当前环境无法运行解析器，交付时明确说明验证限制。

### 4. 代码示例

- 代码围绕当前知识点，保持短小；较长的完整工程可放到项目实战中，正文只展示理解机制所需的关键部分。
- AI 应用开发以 Java 和 Spring AI 为主；确有工具生态限制时可使用其他语言，并说明原因。
- 每个代码块标明语言。片段要明确说明已省略的对象、配置和依赖；需要完整运行的示例则提供必要条件和验证方式。
- 代码、版本与 API 以相应版本的官方资料核对。没有实际运行的示例不能写成“已验证”或“生产可用”。

## 🧠 五、通关总结与复习（99 文档）

每个知识区的复习文档使用 `99-本章总结与复习.md`。围绕本区主线组织全景图或速查表、关键问题和关联笔记；问题数量由内容决定，不为了凑数重复正文。面试题和自测题使用默认折叠的 question 引用块。

## ✅ 六、模板与审查 Checklist

每次新建笔记或重构现有文档时，必须对照以下清单进行自检：
- [ ] **是否包含了完整的 YAML Frontmatter 元数据**（title, tags, created, updated, status, mastery）；
- [ ] **正文是否先解释问题，再用必要的具体例子说明关键过程**，且事实、模拟和推测有明确区分；
- [ ] **是否讲清为什么、怎么做以及关键边界**；内容精简后是否遗漏理解所需的步骤或例子；
- [ ] **标题、引用块、表格和代码块前后是否留空行，普通正文是否避免多余空行**；
- [ ] **章节与块引用是否指向真实存在的标题或块 ID**，重命名后是否检查了外部链接；
- [ ] **代码是否短小并注明前提**；示例版本、依赖和验证状态是否准确；
- [ ] **status 和 mastery 是否保留学习者实际记录**，没有根据写作完成情况擅自调整；
- [ ] **所有面试题、连环追问、复盘自测是否 100% 采用 `> [!question]-` 默认折叠格式**；
- [ ] **折叠块标题栏是否是完整的题干**，内部解答是否直击本质且去除了多余口语前缀；
- [ ] **所有 Mermaid 图表是否符合规范并通过语法检查（0 Error）**；
- [ ] **文档末尾是否包含清晰的下一步导航或复盘记忆钩子**。
