# 分布式与微服务：本章总结与复习

> [!abstract] 一句话总结
> 分布式系统无法消除网络、节点和时钟故障，只能先声明一致性与可用性取舍，再用共识、事务、锁、ID 和运行时治理把正确性边界、故障影响面与排查证据设计清楚。

## 核心知识概览

| 模块 | 核心问题 | 关键结论 | 对应笔记 |
| --- | --- | --- | --- |
| 分布式取舍 | 网络分区时优先一致还是优先响应 | P 必须面对；CAP 要落实到具体操作，BASE 依靠幂等、重试、补偿和对账收敛 | [[01-CAP与BASE理论]] |

| 跨服务一致性 | 多个资源如何共同完成业务状态变化 | 2PC 强一致但阻塞，TCC 显式预留，Saga 适合可补偿长流程，Outbox/CDC 适合事件驱动最终一致 | [[03-分布式事务-2PC-TCC-Saga]] |

## 快速复习

1. CAP 只在网络分区发生时迫使 C/A 取舍，其中 C 是线性一致而非 ACID 一致性；真实设计应按接口或操作选择，不能只给整个系统贴 CP/AP 标签。
2. Raft 的安全性来自多数派交集、任期和日志新旧约束；leader 本地追加不等于提交，当前任期日志经多数派持久化后才能安全推进 `commitIndex`。
3. 跨服务一致性先问能否接受中间状态：短而强一致可考虑 2PC，可预留资源用 TCC，可补偿长流程用 Saga，DB 与 MQ 常用 Outbox/CDC。
4. TCC 必须处理幂等、空回滚和防悬挂；Saga 的补偿是业务动作，不是机械反向 SQL，而且补偿本身也需要重试、告警和人工入口。
5. 分布式锁只降低并发冲突概率。Redis 锁应使用 `SET NX PX` 原子加锁并用 Lua 比较 value 后删除，关键写入仍靠唯一约束、条件更新或 fencing token 拒绝旧持有者。
6. 分布式 ID 选型要同时考虑唯一性、趋势递增、吞吐、时钟回拨、workerId 分配和前端精度；号段模式可用双 buffer 降低数据库发号压力。
7. 稳定性策略从总 deadline 和容量模型出发：限流保护入口和资源边界，Bulkhead 隔离依赖，熔断同时观察错误率与慢调用率，重试只用于幂等操作且不能层层叠加。
8. 服务治理先做候选实例过滤，再做负载均衡；轮询不一定适合长连接、异构实例、本地缓存或多可用区场景，灰度发布还需流量染色、分组观测和快速回滚。
9. 链路追踪不是业务日志的替代品。先由指标发现服务与接口异常，再用 Trace 找慢 span，最后凭 traceId 关联日志；采样和标签必须控制成本、敏感数据与高基数。
10. “最终一致”必须有收敛闭环：状态记录、幂等键、超时扫描、重试/DLQ、对账告警和人工处理缺一不可。

## 自测问题

1. 对库存预扣、订单详情读和积分到账三个操作，你会分别偏向何种一致性策略？用户可见行为和补偿机制是什么？
2. 为什么 Raft 的新 leader 不会覆盖已提交日志？多数派、term 和候选日志新旧判断分别起什么作用？
3. 面对订单、库存、支付、履约的长流程，为什么通常不选择一个 2PC 大事务？如何用状态机、Outbox 和 Saga 形成恢复闭环？
4. Redis 锁持有者发生长时间 GC，锁过期后恢复执行，怎样阻止它覆盖新持有者的结果？
5. 用户请求总预算 1500ms、下游开始变慢时，如何分配 timeout、retry、熔断和半开探测，避免重试风暴？
6. 一次 MQ 消费后的异步线程没有 traceId，你会沿哪些传播点检查，并如何关联指标、Trace 与日志定位问题？
