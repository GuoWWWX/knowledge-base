# 分布式与微服务：本章总结与复习

> [!abstract] 一句话心智模型
> 分布式与微服务是**用工程基础设施驯服不可靠网络的艺术**：
> - **基石理论（CAP/BASE）**：承认物理网络分区（P）必然存在，在 CP 强一致与 AP 高可用间做战略抉择，用 BASE 最终一致性撑起万亿大促；
> - **共识核心（Raft）**：随机超时化解瓜分选票，多数派 Quorum 严防脑裂，选举限制确保历史提交绝不丢失；
> - **数据安全（事务/锁/ID）**：Seata AT 模式靠前后镜像与 Undo Log 实现无感回滚；Redisson 靠看门狗后台定时续期杜绝提前过期与死锁；雪花算法用 64 位时序位运算秒产百万趋势自增主键；
> - **稳定护城河（限流/熔断/染色/链路）**：Sentinel 熔断跳闸斩断级联雪崩；全链路流量染色打通无感灰度；SkyWalking 无侵入 JavaAgent 穿针引线让性能瓶颈无所遁形。

## ⚡ 大厂面试必杀 10 连问（直击底层第一性原理）

> [!NOTE] 30 秒极速精准回答模板
> 
> **Q1：为什么说分布式系统中“CA 架构”在物理上根本不存在？**
> - **答**：分布式系统的各个节点部署在不同物理服务器与机房中，由网线、光纤和交换机相连。在真实物理世界中，网络丢包、延迟、光纤被挖断（即网络分区 P）是不可抗拒的客观事实。一旦网络分区发生，系统要保证强一致（C）就必须拒绝未经同步的读写（牺牲可用性 A）；要保证随时可用（A）就必须返回本地可能过时的旧数据（牺牲一致性 C）。因此网络分区下，系统**只能在 CP 和 AP 之间做二选一**，CA 在物理上不成立。
> 
> **Q2：Raft 算法是如何防止选举时出现瓜分选票（Split Vote）死循环的？**
> - **答**：通过**随机化选举超时时间（Randomized Election Timeout）**机制。Raft 将每个节点的选举超时时间随机设定在 150ms 到 300ms 之间。当 Leader 宕机后，通常只有一个节点率先超时并发起拉票，赶在其他节点之前抢先集齐多数派选票当选，彻底避免了所有节点在同一时刻发起竞选导致选票被瓜分的僵局。
> 
> **Q3：Seata 的 AT 模式底层是如何在不改动业务代码的情况下实现回滚的？**
> - **答**：通过**数据源代理（DataSourceProxy）**机制。在一阶段执行更新前，代理自动查询目标记录的“前镜像（Before Image）”，执行业务 SQL 后查询“后镜像（After Image）”，将前后镜像生成 `Undo Log` 并在同一本地事务内提交释放行锁；若全局失败需要回滚，Seata 校验当前数据是否等于后镜像（防脏写），随后使用前镜像反向生成恢复 SQL 执行数据还原。
> 
> **Q4：TCC 事务中的“空回滚”与“防悬挂”是什么概念？如何解决？**
> - **答**：
>   - **空回滚**：Try 请求因网络延迟还没到，TC 判定超时直接发出了 Cancel，分支节点若未做判断直接归还资源会导致数据凭空多增。
>   - **防悬挂**：Cancel 空回滚执行完后，迟到的 Try 请求又慢吞吞到达并执行了资源预留，后续再无 Cancel 释放，导致该资源永久悬挂冻结。
>   - **解法**：建立 TCC 状态表并以事务 ID 为主键。Cancel 执行前先查记录，未 Try 过则插入已取消标记（空回滚记录）；Try 执行前先查若已被标记取消，直接拒绝执行预留，杜绝悬挂。
> 
> **Q5：手写 Redis 分布式锁时，为什么释放锁必须使用 Lua 脚本？**
> - **答**：为了防范**锁提前过期导致误删他人持有的锁**。由于业务耗时可能超出锁的 TTL，线程 A 的锁过期后线程 B 成功加锁，此时线程 A 醒来若直接执行 `DEL`，就会误删线程 B 的锁。因此加锁时必须存入唯一随机 Token，释放时先 `GET` 校验当前锁的值是否等于自己的 Token，相等才删除。这一“比对+删除”逻辑必须借助 **Lua 脚本**在 Redis 内部原子执行，防止在比对和删除之间发生竞态切换。
> 
> **Q6：Redisson 的看门狗（Watchdog）机制是怎样防止锁提前失效的？**
> - **答**：当调用 `lock.lock()` 未显式指定超时时间时，Redisson 激活看门狗，默认将锁过期时间设为 30 秒。随后后台启动基于 Netty 时间轮的定时任务，每隔 10 秒（`lockWatchdogTimeout / 3`）自动向 Redis 发送一段 Lua 脚本，检查如果当前线程依然持有锁，就将其过期时间重新刷新重置为 30 秒。线程死机时定时器停止工作，30 秒后锁由 Redis 自动释放，既防止了提前超期，又避免了死锁。
> 
> **Q7：为什么 MySQL 聚簇索引主键严禁使用 UUID，而推荐雪花算法（Snowflake）？**
> - **答**：InnoDB 聚簇索引底层是 B+ 树，数据按照主键顺序物理存放。UUID 是完全无序的 36 字符字符串，随机插入会导致数据页频繁发生剧烈的**页分裂（Page Split）**，产生海量磁盘随机 I/O 和碎片空洞；而雪花算法是 64 位整数，最高位由 41 位时间戳构成，**全局趋势单调递增**，插入 MySQL 时永远在页末尾顺序追加写入，性能高且空间利用率极致。
> 
> **Q8：雪花算法生成的主键传给前端页面时，为什么末尾几位数字经常莫名其妙变成 0？**
> - **答**：因为 **JavaScript 的 Number 类型基于 IEEE 754 双精度浮点数表示，其最大安全整数只有 53 位**（即 $2^{53}-1 \approx 9 \times 10^{15}$，16位数字）。而 64 位雪花 ID 高达 19 位数字，直接以 JSON 数值传给浏览器时，超出 53 位的低 3 位会被强制精度截断四舍五入为 0。解决方案是后端通过 `@JsonSerialize(using = ToStringSerializer.class)` 将 Long 统一转为 String 字符串传输。
> 
> **Q9：什么是微服务雪崩效应？熔断器是如何阻止雪崩蔓延的？**
> - **答**：
>   - 雪崩效应是指当下游微服务出现延迟或故障变慢时，上游调用方的线程池会被迅速耗尽卡死，导致故障沿着调用链向上级联蔓延，最终引发全站核心入口瘫痪。
>   - 熔断器通过维护 **Closed、Open、Half-Open 三大状态机**：当下游失败率或慢调用比例突破阈值时，空气开关瞬间跳闸进入 **Open 状态**，后续请求在本地内存直接快速失败（Fast-Fail）并走 Fallback 降级，强行斩断故障调用链路，防止自身线程池被拖垮。
> 
> **Q10：SkyWalking 是如何在不修改业务代码的情况下实现全链路性能监控的？**
> - **答**：依赖 Java 的 **`JavaAgent`（探针）机制** 与 ByteBuddy 字节码增强工具。在 JVM 启动加载 Class 字节码时，SkyWalking Agent 动态拦截目标框架的类（如 Spring MVC、Feign、MyBatis），在核心方法执行前后自动动态织入 AOP 拦截代码，生成 Span、记录耗时并挂载 TraceId，随后通过后台异步 gRPC 线程池批量推送到服务端，实现了对业务代码的完全零侵入。
