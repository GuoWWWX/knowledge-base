## 📖 核心组件与机制全景对照表

| 核心组件 / 机制 | 核心底层原理与技术本质 | 场景类比说明（辅助理解） |
| :--- | :--- | :--- |
| **B+ 树索引** | 非叶子节点仅存储 Key 与指针，叶子节点存储完整行（或主键）且通过双向链表相连。扇出极高，千万级数据仅需 3 层深度（3 次磁盘 I/O）。 | 类比为分级快速检索目录 |
| **聚簇索引 vs 二级索引** | 聚簇索引按主键顺序物理存放完整行；二级索引叶子节点仅存储主键值，查询非覆盖字段必须发起**主键回表**。 | 类比为正文主卷与分词索引目录 |
| **覆盖索引** | 所需查询的字段全部包含在命中二级索引的键值中，直接返回，**0 次主键回表**，极大提升查询效率。 | 类比为在目录条目上直接获取到答案 |
| **MVCC** | 基于隐藏系统列、Undo Log 历史版本链与 ReadView 一致性读视图，实现非阻塞的快照读与读写并发不互斥。 | 类比为多版本历史快照溯源机制 |
| **间隙锁 (Gap Lock)** | 锁定记录之间的开区间范围，专门**阻断并发事务的 INSERT 操作，防御幻读**；与行锁结合为 Next-Key Lock。 | 类比为行与行之间的安全隔离警戒带 |
| **死锁 (Deadlock)** | 多个并发事务相互循环等待对方释放锁资源；InnoDB 通过锁等待图（Wait-for Graph）检测环路，自动回滚代价最小的事务。 | 类比为并发资源请求的环形死循环 |
| **ZSet (跳表 SkipList)** | 哈希表 $O(1)$ 精确查分 + 跳表多层跨度指针 $O(\log N)$ 范围排位，实现高效排行榜。 | 类比为带有多层跳跃快进轨道的索引链表 |
| **写时复制 (COW)** | `BGSAVE` fork 子进程时仅共享物理内存页表；仅当父进程发生写修改时才触发物理页复制，极大节省内存。 | 类比为按需独立复写的内存机制 |
| **布隆过滤器** | 基于多个哈希函数的位图结构；判断不存在则 100% 绝对不存在，判断存在可能有一丁点误判率；缓存穿透第一道防线。 | 类比为快速前置排查的判空哨卡 |
| **HikariCP 连接数** | 并非连接越多越好，连接过多引发 CPU 剧烈上下文切换拖垮内核，公式 `(CPU * 2) + 1` 达到吞吐平衡。 | 类比为系统吞吐吞吐量的最佳并发通道数 |
| **基因分片法** | 将用户 ID 的后几位特征散列融入订单 ID 尾部，使买家查询和订单号查询均能单表直接定位，避免全表广播扫库。 | 类比为将父级特征基因嵌入子级唯一标识 |

## ⚡ 大厂面试“30 秒必杀”高频 10 连问

### Q1：为什么 MySQL 选择 B+ 树而不是 B 树或红黑树？
> **答**：
> 1. **比红黑树/二叉树好**：二叉树太高，千万级数据高度达 20 多层，要发生 20 多次昂贵磁盘 I/O；
> 2. **比 B 树好**：B 树每个节点都存整行数据，导致一个 16KB 数据页存不了几个索引项，树依然太高；而 B+ 树**非叶子节点只存索引 Key 和指针**，一个页可存上千项，千万级大表树高仅 **3 层**（只需 3 次 I/O）；且叶子节点用**双向链表**串联，天然支持高效范围扫描。

### Q2：什么是回表？如何避免回表？
> **答**：
> - **回表**：普通二级索引的叶子节点只存主键 ID。当查询需要其他字段时，必须拿着主键 ID 跑到聚簇索引树上再查一次；
> - **避免**：使用**覆盖索引**（`SELECT id, name`，让所需列全在二级索引中），Extra 显示 `Using index`，0 回表。

### Q3：详细说说 MVCC 的实现原理？
> **答**：
> MVCC 基于三大基石：
> 1. **隐藏列**：每行自带 `trx_id`（最后修改事务 ID）与 `roll_pointer`（指向旧版本）；
> 2. **Undo Log 版本链**：多次修改串联成由近及远的历史链；
> 3. **ReadView**：包含活跃事务列表 `m_ids` 等。查询时拿版本链上的 `trx_id` 逐一比对：
>    - **RC 级别**：每次 `SELECT` 都会生成新 ReadView，因此能看到别人最新提交的数据（不可重复读）；
>    - **RR 级别**：事务中第一次 `SELECT` 生成 ReadView 后一用到底，看到的永远是事务初期的快照，解决不可重复读。

### Q4：MySQL 的间隙锁（Gap Lock）和临键锁（Next-Key Lock）有什么区别？
> **答**：
> - **间隙锁（Gap Lock）**：锁的是两条记录之间的**纯空白开区间**，目的是阻止其他事务在间隙中 INSERT 新记录，专门解决幻读；
> - **临键锁（Next-Key Lock）**：是**记录锁 + 间隙锁的合体**，为左开右闭区间 `(a, b]`，是 InnoDB 在 RR 隔离级别下的默认加锁单位。

### Q5：导致 MySQL 索引失效的场景有哪些？
> **答**：
> 违背最左前缀法则、在索引列上做运算或函数、隐式类型转换（字符串字段不加单引号）、头部模糊匹配（`LIKE '%abc'`）、范围查询阻断后列索引、`OR` 条件中存在未索引列。

### Q6：如何优化超深分页 `LIMIT 1000000, 10`？
> **答**：
> 原始 SQL 会做 100 万次无效回表。优化采用**子查询延迟关联**：
> `SELECT * FROM orders o JOIN (SELECT id FROM orders ORDER BY id LIMIT 1000000, 10) t ON o.id = t.id;`
> 内层查询纯走覆盖索引极速定位 10 个 ID，外层仅回表 10 次。

### Q7：Redis 为什么单线程还能每秒支撑 10 万 QPS？
> **答**：
> 1. **纯内存操作**，读写在数十纳秒级；
> 2. **核心业务逻辑单线程**，杜绝多线程上下文切换和锁竞争开销；
> 3. **基于 epoll 的 I/O 多路复用**，一个线程轻松非阻塞监听上万网络连接。

### Q8：简述 Redis 的 RDB 和 AOF 以及写时复制（COW）原理？
> **答**：
> - **RDB**：全量二进制快照，恢复极快但丢失窗口大；`BGSAVE` fork 子进程时共享物理内存页，只有主进程修改某页时才复制该页（COW），极省内存；
> - **AOF**：写操作命令追加流水账，默认 `everysec` 最多丢 1 秒，通过重写（Rewrite）瘦身；
> - **现代主流**：采用**混合持久化**（前半段 RDB 二进制 + 后半段 AOF 增量），秒级开机恢复且不丢数据。

### Q9：缓存穿透、击穿、雪崩分别是什么？怎么解决？
> **答**：
> - **穿透（查无此人）**：查数据库不存在的数据 -> **布隆过滤器拦截 + 空值短 TTL 缓存**；
> - **击穿（单点爆破）**：单个热点 Key 突然过期 -> **分布式互斥锁（SETNX）控制单线程回源，或逻辑永不过期**；
> - **雪崩（集体崩盘）**：大量 Key 集中在同一秒过期或 Redis 宕机 -> **过期时间加随机打散扰动 + 搭建哨兵/分片高可用集群**。

### Q10：双写一致性中，为什么推荐“先更新数据库，再删除缓存”？
> **答**：
> 如果先删缓存，并发读请求会因为缓存 miss 把数据库的旧值立刻回填进 Redis，紧接着写操作更新 DB，导致 Redis 永远残留旧脏数据。采用 Cache-Aside（先更新 DB 再删缓存），再配合 Canal 监听 binlog 异步重试删除，是目前工业界的最佳标准实践。

## 📜 数据库与存储生产开发“十大约法三章”

1. **【禁止 SELECT *】**：查询必须指明字段，多用覆盖索引消灭回表。
2. **【小事务快跑】**：严禁在 `@Transactional` 里夹杂 RPC 调用、发短信或大计算，锁必须尽快释放。
3. **【索引左前缀】**：联合索引严格按高频过滤度从左到右排序，避免索引列上使用函数或类型隐式转换。
4. **【杜绝生产 KEYS *】**：一律使用 `SCAN` 渐进式遍历，防止单线程主循环卡死。
5. **【防范 BigKey】**：单 String 严禁超 10KB，集合元素严禁超 5000，删除大 Key 必须使用异步 `UNLINK`。
6. **【TTL 必须打散】**：批量写入 Redis 缓存时，过期时间必须加上随机秒数扰动，严防雪崩。
7. **【连接池绝不贪多】**：根据 `(CPU*2)+1` 黄金法则配精简连接池，开启连接泄漏检测阈值。
8. **【防范主从延迟】**：刚写完立即要求读取的敏感业务，使用 Redis 标记或强制路由主库。
9. **【深分页用延迟关联】**：大数据量分页杜绝裸奔大 offset，改用子查询延迟关联或游标滚动。
10. **【分库分表弃用自增】**：分布式场景抛弃单机自增 ID，全面使用单调递增的雪花算法（Snowflake）。
