# 08 · 行为型扩展阅读：中介者、备忘录、解释器与访问者

> **阅读定位**：接续 [[04-行为型模式上-策略-模板方法-责任链]] 与 [[05-行为型模式下-观察者-状态-命令-迭代器]]，补全行为型的另外四种 GoF 模式。“扩展”是学习顺序安排，不是 GoF 之外的分类，也不代表它们在各自领域都不常用。
>
> **先记四个问题**：对象互相认识太多，用中介者；想恢复旧状态，用备忘录；要执行一门小规则语言，用解释器；类型结构稳定、操作不断增加，用访问者。示例均为 Java 17+ 单文件程序，无第三方依赖，只操作内存并打印结果。

---

## 一、中介者模式（Mediator）：把相互调用收口到协调者

### 1. 直白定义与要解决的问题

**中介者把一组对象之间的交互规则集中到协调对象，让参与者不必直接引用其他参与者。** 它改变的是“谁知道谁、谁决定怎样协作”。

例如聊天成员原本要保存彼此的对象引用并检查对方是否在线。改成聊天室统一注册成员、查找收件人和转交消息，成员只知道聊天室及收件人名称。UI 表单中多个控件的启用、校验联动也有类似的协调需求。

### 2. 关键角色

| 角色 | 示例 | 职责 |
| :--- | :--- | :--- |
| 中介者契约 Mediator | `Mediator` | 定义注册和协调通信的入口 |
| 具体中介者 Concrete Mediator | `ChatRoom` | 保存成员注册表，处理查找、合法性检查及转交 |
| 同事对象 Colleague | `User` | 通过中介者发消息，接收回调，不直接持有其他用户 |

### 3. 完整 Java 示例：聊天室转交私信

保存为 `MediatorDemo.java`，执行 `javac -encoding UTF-8 MediatorDemo.java`、`java MediatorDemo`。它是同步内存演示，不是真实聊天服务。

```java
import java.util.LinkedHashMap;
import java.util.Map;
import java.util.Objects;

public class MediatorDemo {
    interface Mediator {
        void register(User user);
        void send(User from, String to, String text);
    }

    static final class ChatRoom implements Mediator {
        private final Map<String, User> users = new LinkedHashMap<>();

        public void register(User user) {
            Objects.requireNonNull(user);
            if (user.room != this) {
                throw new IllegalArgumentException("different room");
            }
            if (users.putIfAbsent(user.name, user) != null) {
                throw new IllegalArgumentException("duplicate name");
            }
        }

        public void send(User from, String to, String text) {
            if (from == null || users.get(from.name) != from) {
                throw new IllegalArgumentException("sender not registered");
            }
            User recipient = users.get(to);
            if (recipient == null) {
                throw new IllegalArgumentException("recipient offline");
            }
            recipient.receive(from.name, Objects.requireNonNull(text));
        }
    }

    static final class User {
        private final String name;
        private final Mediator room;

        User(String name, Mediator room) {
            this.name = Objects.requireNonNull(name);
            this.room = Objects.requireNonNull(room);
        }

        void sendTo(String to, String text) { room.send(this, to, text); }

        void receive(String from, String text) {
            System.out.println(name + " <- " + from + ": " + text);
        }
    }

    public static void main(String[] args) {
        Mediator room = new ChatRoom();
        User alice = new User("Alice", room);
        User bob = new User("Bob", room);
        room.register(alice);
        room.register(bob);
        alice.sendTo("Bob", "hello");
        bob.sendTo("Alice", "received");
    }
}
```

输出 `Bob <- Alice: hello`、`Alice <- Bob: received`。新增成员只需注册，不需修改已存在成员的引用。注册与构造分开，避免在构造尚未结束时把 `this` 交给协调者。实际系统还需处理认证、权限、离线消息、失败和并发；注册表的对象身份检查不能代替网络身份认证。

### 4. 适用与不适用、优缺点、易混模式

- **适用**：多个对象形成复杂相互依赖，且有明确的协调范围，例如一个对话框、一场会议、一间聊天室；需要集中处理交互顺序或路由规则。
- **不适用**：只有两个对象、直接调用已经清楚；只是单向通知多个订阅者；协调范围无限扩大、开始囊括整个系统。
- **优点**：减少参与者之间的引用；交互规则集中，参与者可复用和单独测试；变更协作流程时不必修改每个参与者。
- **缺点**：协调者容易膨胀成上帝对象；集中入口可能成为性能或可靠性瓶颈；错误的职责划分会把所有业务搬进一个类。应按场景拆协调者，而不是做万能总线。

| 易混模式 | 区别 |
| :--- | :--- |
| 观察者 | 重点是一对多事件通知和订阅关系；中介者重点是多对象之间的协作规则。中介者内部可以用观察者传递事件，但两者不等同。 |
| 门面 | 主要给客户端提供简化入口，子系统通常不需要知道门面；中介者的参与者主动通过协调者交互。 |
| 责任链 | 请求沿多个处理节点推进；中介者负责协调参与者，不要求有顺序链。 |

> **面试总结**：Mediator 用一个有边界的协调者替代对象之间网状互相引用。它收敛协作规则，但必须控制协调者的职责和规模；不是把任意 Service 调用集中起来就算设计成功。

## 二、备忘录模式（Memento）：保存状态，但不让历史管理器拆开看

### 1. 直白定义与要解决的问题

**由对象自己生成可恢复的状态快照，外部只保存快照句柄，需要时交回原对象恢复。** 保存与恢复细节留在状态拥有者内部，避免历史管理器到处读取、修改私有字段。

例如文本编辑器要撤销多次修改，不应让历史栈知道文本、光标等内部状态如何布局。编辑器负责创建与恢复快照，历史栈仅负责顺序。

### 2. 关键角色与封装边界

| 角色 | 示例 | 职责 |
| :--- | :--- | :--- |
| 发起人 Originator | `Editor` | 持有真实状态；创建与恢复快照 |
| 备忘录 Memento | 私有 `Snapshot` | 保存不可变状态；通过空接口隐藏内部字段 |
| 管理者 Caretaker | `History` | 保存快照，决定恢复哪一次，不解释快照内容 |

### 3. 完整 Java 示例：文本与光标的多级撤销

保存为 `MementoDemo.java`。使用不可变字符串和整数，避免快照引用原对象中的可变列表。

```java
import java.util.ArrayDeque;
import java.util.Deque;
import java.util.Objects;

public class MementoDemo {
    interface Memento {} // 历史管理器只看得到这个窄接口。

    static final class Editor {
        private String text = "";
        private int cursor;

        private static final class Snapshot implements Memento {
            private final Editor owner;
            private final String text;
            private final int cursor;

            Snapshot(Editor owner, String text, int cursor) {
                this.owner = owner;
                this.text = text;
                this.cursor = cursor;
            }
        }

        void replace(String text) {
            this.text = Objects.requireNonNull(text);
            this.cursor = text.length();
        }

        Memento save() { return new Snapshot(this, text, cursor); }

        void restore(Memento memento) {
            if (!(memento instanceof Snapshot)) {
                throw new IllegalArgumentException("invalid snapshot");
            }
            Snapshot snapshot = (Snapshot) memento;
            if (snapshot.owner != this) {
                throw new IllegalArgumentException("different editor");
            }
            this.text = snapshot.text;
            this.cursor = snapshot.cursor;
        }

        String view() { return text + " @" + cursor; }
    }

    static final class History {
        private final Editor editor;
        private final Deque<Memento> undo = new ArrayDeque<>();

        History(Editor editor) { this.editor = Objects.requireNonNull(editor); }

        void edit(String text) {
            Objects.requireNonNull(text); // 失败的编辑不增加历史。
            Memento before = editor.save();
            editor.replace(text);
            undo.push(before);
        }

        boolean undo() {
            if (undo.isEmpty()) return false;
            editor.restore(undo.peek());
            undo.pop();
            return true;
        }
    }

    public static void main(String[] args) {
        Editor editor = new Editor();
        History history = new History(editor);
        history.edit("A");
        history.edit("AB");
        history.edit("ABC");
        history.undo();
        System.out.println(editor.view()); // AB @2
        history.undo();
        System.out.println(editor.view()); // A @1
    }
}
```

`History` 没有读取快照中的 `text/cursor`。快照还记录来源对象，防止把编辑器 A 的快照恢复到 B。示例只实现撤销；支持重做需再维护 redo 栈，并在新编辑成功时清空分叉的重做历史。快照若包含可变对象，应深拷贝或使用不可变结构；数据库事务与远程副作用不能靠恢复 Java 对象自动撤回。

### 4. 适用与不适用、优缺点、易混模式

- **适用**：编辑器撤销、内存模型的试算回滚、需要恢复一组对象状态且希望保持封装的场景。
- **不适用**：只需保存一两个公开值；对象状态巨大且变化频繁，完整快照代价过高；实际目标是跨数据库或远程服务事务回滚。
- **优点**：保存/恢复责任归属清楚；不暴露内部状态布局；历史管理与业务对象分离。
- **缺点**：消耗内存；深拷贝、版本兼容和多对象一致性较难；历史过长需限制数量、压缩或持久化。只提供快照并不自动具备完整撤销/重做功能。

| 易混模式 | 区别 |
| :--- | :--- |
| 命令 | 保存“做什么动作”，可用逆向命令撤销；备忘录保存“当时是什么状态”。命令也可持有备忘录来实现撤销。 |
| 原型 | 重点是复制已有对象以创建新对象；备忘录重点是保存并恢复原对象状态，同时控制快照的可见边界。 |
| 状态 | 把不同状态下的行为分派给状态对象；备忘录保存过去的数据，不负责定义状态转换规则。 |

> **面试总结**：Memento 的关键不只是“做一份拷贝”，还包括状态由 Originator 保存和恢复、Caretaker 只管理历史、Memento 封装状态。要能说清可变引用、快照成本和撤销/重做边界。

## 三、解释器模式（Interpreter）：把小规则语言变成可执行的表达式树

### 1. 直白定义与要解决的问题

**为一门简单语言的语法规则建立表达式对象，并让这些对象解释输入上下文。** 终结符处理最小判断，非终结符组合判断；规则树可以复用到不同业务数据上。

例如活动资格规则是 `amount >= 10000 && (vip || amount >= 20000)`，金额以分为单位。规则配置变化时，先解析成表达式树，再反复用订单上下文求真假，不必为每个规则组合写新的 Java 分支。

**这里的 Interpreter 是 GoF 模式，不是 JVM 的字节码解释执行器。** 解析器负责把文本转换成结构；解释器模式关注语法对应的对象结构和求值。只有一个 parser 或 `eval()` 方法，并不足以说明采用了这种对象设计。

### 2. 关键角色与本例语法

| 角色 | 示例 | 职责 |
| :--- | :--- | :--- |
| 抽象表达式 Abstract Expression | `Expr` | 统一 `interpret(Order)` 求值契约 |
| 终结符 Terminal Expression | `Vip`、`AmountAtLeast` | 判断会员标志、金额是否达到阈值 |
| 非终结符 Nonterminal Expression | `And`、`Or` | 组合子表达式，递归求值 |
| 上下文 Context | `Order` | 提供本次求值的数据，不保存全局可变规则 |
| 客户端/解析辅助 | `Parser`、`main` | 把文本解析成树，选择上下文执行 |

```text
rule   := or
or     := and ("||" and)*
and    := atom ("&&" atom)*
atom   := "vip" | "amount" ">=" integer | "(" rule ")"
integer := 一个或多个十进制数字（不超过 int 上限）
```

`&&` 优先于 `||`，括号可以改变结合关系。这里只支持两个预定义字段、非负整数和逻辑运算，不调用脚本引擎，也不执行任意 Java 代码。

### 3. 完整 Java 示例：解析、构树与递归求值

保存为 `InterpreterDemo.java`。

```java
import java.util.Objects;

public class InterpreterDemo {
    record Order(int amountCents, boolean vip) {}

    interface Expr { boolean interpret(Order context); }

    record Vip() implements Expr {
        public boolean interpret(Order context) { return context.vip(); }
    }

    record AmountAtLeast(int cents) implements Expr {
        public boolean interpret(Order context) {
            return context.amountCents() >= cents;
        }
    }

    record And(Expr left, Expr right) implements Expr {
        public boolean interpret(Order context) {
            return left.interpret(context) && right.interpret(context);
        }
    }

    record Or(Expr left, Expr right) implements Expr {
        public boolean interpret(Order context) {
            return left.interpret(context) || right.interpret(context);
        }
    }

    static final class Parser {
        private final String source;
        private int pos;

        Parser(String source) { this.source = Objects.requireNonNull(source); }

        Expr parse() {
            Expr expression = parseOr();
            skipSpaces();
            if (pos != source.length()) throw error("unexpected input");
            return expression;
        }

        private Expr parseOr() {
            Expr left = parseAnd();
            while (take("||")) left = new Or(left, parseAnd());
            return left;
        }

        private Expr parseAnd() {
            Expr left = parseAtom();
            while (take("&&")) left = new And(left, parseAtom());
            return left;
        }

        private Expr parseAtom() {
            if (take("(")) {
                Expr inside = parseOr();
                expect(")");
                return inside;
            }
            if (take("vip")) return new Vip();
            if (take("amount")) {
                expect(">=");
                return new AmountAtLeast(number());
            }
            throw error("expected vip, amount or parenthesis");
        }

        private int number() {
            skipSpaces();
            int start = pos;
            while (pos < source.length()
                    && source.charAt(pos) >= '0' && source.charAt(pos) <= '9') {
                pos++;
            }
            if (start == pos) throw error("expected non-negative integer");
            try {
                return Integer.parseInt(source.substring(start, pos));
            } catch (NumberFormatException exception) {
                throw error("integer out of range");
            }
        }

        private boolean take(String token) {
            skipSpaces();
            if (!source.startsWith(token, pos)) return false;
            pos += token.length();
            return true;
        }

        private void expect(String token) {
            if (!take(token)) throw error("expected " + token);
        }

        private void skipSpaces() {
            while (pos < source.length() && Character.isWhitespace(source.charAt(pos))) {
                pos++;
            }
        }

        private IllegalArgumentException error(String message) {
            return new IllegalArgumentException(message + " at " + pos);
        }
    }

    public static void main(String[] args) {
        Expr rule = new Parser("amount >= 10000 && (vip || amount >= 20000)").parse();
        System.out.println(rule.interpret(new Order(12000, false))); // false
        System.out.println(rule.interpret(new Order(12000, true)));  // true
        System.out.println(rule.interpret(new Order(20000, false))); // true
    }
}
```

表达式树在求值时不变，可重复执行；`And/Or` 使用 Java 短路逻辑。解析器会检查尾部垃圾字符、缺失括号和整数越界；它只是小语法演示，没有做复杂错误恢复或输入规模限制。对外开放规则时，应限制文本长度、嵌套深度、节点数和求值预算，并验证业务字段范围，避免深度递归或大表达式消耗资源。

### 4. 适用与不适用、优缺点、易混模式

- **适用**：语法简单、规则组合多且重复求值的业务 DSL，例如有限字段的筛选条件、权限谓词、告警规则；团队能够维护语法与版本。
- **不适用**：单个判断直接写函数即可；语法复杂到接近通用语言；需要优化编译或大量动态函数。此时应评估成熟解析器、规则引擎或更简单的配置方案，而不是无限添加语法类。
- **优点**：语法与对象职责对应清楚；规则可组合、可测试；解析与求值分开，树能复用。
- **缺点**：语法扩展会增加类与解析逻辑；递归求值有成本；语法歧义、优先级、版本兼容与资源上限都需要自行维护。

| 易混概念 | 区别 |
| :--- | :--- |
| JVM 解释器 | 执行字节码的一种 JVM 实现机制；本例解释的是业务 DSL，属于对象设计方式，二者不是同一层次。 |
| 策略 | 在几套完整算法之间选择；解释器把语法元素组成规则树，按上下文递归求值。 |
| 组合 | 表达式树常使用 Composite 的递归结构；解释器进一步赋予语法和解释语义，普通目录树没有这些语义。 |
| 访问者 | 可把表达式树的求值、打印、优化等操作放进访问者；本例把解释操作直接放在表达式对象中。 |

> **面试总结**：Interpreter 为简单语言定义语法对应的表达式类，通过终结符与非终结符解释 Context。要能区分解析文本和求值、解释器模式和 JVM 解释执行，并说明它不适合自行构造复杂通用语言。

## 四、访问者模式（Visitor）：类型结构稳定，让新操作单独扩展

### 1. 直白定义与要解决的问题

**把一组不同类型对象上的某项操作集中到独立访问者，让新增操作不必反复修改这些元素类。** 元素提供 `accept()`，把自己交给访问者的对应处理方法。

例如报表素材包含文档和图片，需要“统计文档页数”“生成审计说明”等不同操作。若每次新增操作都给每个素材类加方法，元素类会不断膨胀；访问者把同一操作下各类型的处理集中在一个类。

### 2. 关键角色与双分派

| 角色 | 示例 | 职责 |
| :--- | :--- | :--- |
| 访问者 Visitor | `Visitor<R>` | 为每种稳定元素类型声明 `visit` |
| 具体访问者 Concrete Visitor | `PageCounter`、`AuditVisitor` | 分别实现页数统计、审计说明 |
| 元素 Element | `Element` | 定义 `accept(visitor)` |
| 具体元素 Concrete Element | `Document`、`Image` | 在自身类型上下文中调用 `visitor.visit(this)` |
| 对象结构 Object Structure | `List<Element>` | 保存需要处理的元素；本例由客户端遍历 |

调用先动态分派到 `Document.accept` 或 `Image.accept`，在那里 `this` 的静态类型确定了对应 `visit` 重载，再动态分派到具体访问者实现。这种协作常称为双分派。**不能仅在客户端对 `Element` 变量调用一个重载方法，就指望 Java 自动按参数的运行时类型选中重载。**

### 3. 完整 Java 示例：同一批素材执行两种操作

保存为 `VisitorDemo.java`。

```java
import java.util.List;

public class VisitorDemo {
    interface Visitor<R> {
        R visit(Document document);
        R visit(Image image);
    }

    interface Element {
        <R> R accept(Visitor<R> visitor);
    }

    static final class Document implements Element {
        final String name;
        final int pages;

        Document(String name, int pages) {
            if (pages < 0) throw new IllegalArgumentException("negative pages");
            this.name = name;
            this.pages = pages;
        }

        public <R> R accept(Visitor<R> visitor) { return visitor.visit(this); }
    }

    static final class Image implements Element {
        final String name;
        final int kilobytes;

        Image(String name, int kilobytes) {
            if (kilobytes < 0) throw new IllegalArgumentException("negative size");
            this.name = name;
            this.kilobytes = kilobytes;
        }

        public <R> R accept(Visitor<R> visitor) { return visitor.visit(this); }
    }

    static final class PageCounter implements Visitor<Integer> {
        public Integer visit(Document document) { return document.pages; }
        public Integer visit(Image image) { return 0; }
    }

    static final class AuditVisitor implements Visitor<String> {
        public String visit(Document document) {
            return "DOC " + document.name + ": " + document.pages + " pages";
        }

        public String visit(Image image) {
            return "IMAGE " + image.name + ": " + image.kilobytes + " KB";
        }
    }

    public static void main(String[] args) {
        List<Element> elements = List.of(
                new Document("guide", 8), new Image("logo", 24),
                new Document("notes", 3));
        Visitor<Integer> counter = new PageCounter();
        Visitor<String> audit = new AuditVisitor();
        int pages = 0;
        for (Element element : elements) {
            pages += element.accept(counter);
            System.out.println(element.accept(audit));
        }
        System.out.println("PAGES=" + pages); // 11
    }
}
```

新增“计算审核费用”操作时，增加一个访问者即可复用这批元素。但新增 `Video` 元素时，要增加相应 `visit(Video)`，并处理所有访问者的兼容性。例子把遍历交给客户端；Visitor 本身不规定遍历顺序，也不会自动递归整个树。

### 4. 适用与不适用、优缺点、易混模式

- **适用**：元素类型集合较稳定，类型相关操作不断增加，如语法树分析、文档导出、静态检查；元素能提供足够但受控的数据访问。
- **不适用**：元素类型经常新增；只有一个简单操作；操作需要暴露大量原本私有的状态才能完成。此时方法多态、策略或模式匹配可能更直接。
- **优点**：同一操作的不同类型处理集中；新增操作不必修改所有元素；不同访问者可返回不同结果。
- **缺点**：新增元素类型通常要修改访问者接口和各实现；元素与访问者相互依赖；为访问者开放内部数据可能削弱封装。它是“新增操作容易、增加类型较难”的取舍，不是所有方向都符合开闭原则。

| 易混模式 | 区别 |
| :--- | :--- |
| 策略 | 替换一个职责的算法；访问者把操作分派到多个具体元素类型上，通常提供多个 `visit` 方法。 |
| 迭代器 | 决定如何逐个取元素；访问者决定拿到不同类型后做什么。二者可以一起使用。 |
| 组合 | 表达部分—整体的对象树；访问者在这棵树上添加独立操作。对象结构也可以是本例的平铺列表。 |

> **面试总结**：Visitor 把稳定元素结构上的可变操作分离成访问者，靠 `accept/visit` 协作实现双分派。务必说明元素类型新增的代价、封装问题，以及访问者与遍历机制的区别。

## 五、扩展阅读自测与横向串联

| 面试追问 | 应答要点 |
| :--- | :--- |
| 中介者就是观察者吗？ | 不是。协调一组对象的交互与一对多事件通知是不同意图；二者可组合。 |
| 用一个 Map 保存对象字段就是备忘录吗？ | 还要明确快照封装、状态拥有者的保存/恢复职责，以及历史管理器的窄接口。 |
| 规则字符串解析出来后，模式体现在哪里？ | 在对应语法元素的表达式对象及其递归解释上下文的职责，而不只在 parser。 |
| Visitor 是否可以不修改代码就新增任意元素？ | 经典访问者通常不行；新增元素会影响访问者接口和实现。 |

- [[05-行为型模式下-观察者-状态-命令-迭代器]] 中的命令可持有备忘录，支持复杂撤销；保存旧值的命令不必强行拆出完整 Memento。
- [[07-结构型扩展-桥接与组合]] 的 Composite 可组织表达式树；Interpreter 赋予它规则语义；Visitor 可以进一步增加打印、分析等操作。
- MVC、DI/IoC、DDD 与设计原则可帮助组织代码，但不额外计入 GoF 23 种。简单工厂也是补充知识，不能把 GoF 创建型从 5 种数成 6 种。
