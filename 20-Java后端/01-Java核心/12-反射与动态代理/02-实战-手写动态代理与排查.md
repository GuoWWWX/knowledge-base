# 实战 · 手写动态代理与排查

> [!abstract] 一句话总结
> 12 个能独立运行的案例，从"静态代理有多痛"一路走到"手写一个迷你 AiServices"，再加 5 套排查手段和一棵决策树——目标不是看懂，是让你合上文档能徒手写出代理、拿到线上问题知道第一步敲什么。

> [!tip] 怎么用这篇
> 原理见 [[01-反射与动态代理原理]]，这篇只管动手。**所有代码必须自己敲，不要复制**——动态代理的手感全在 `newProxyInstance` 那三个参数上，复制粘贴学不会。
>
> 每个案例都是**单文件程序**，Java 11+ 可以直接跑，不用建项目、不用 `javac`：
> ```bash
> java Case01.java
> ```
> 时间安排：案例 1-3、9、11 是必做核心（约 1.5 小时），4-8 是坑位验证（每个十几分钟），10、12 快速过。排查篇的工具 1-3 在做案例时顺手用上，不要单独学。

> [!success] 关于「实测输出」
> 每个案例下面的输出块**都是本机真实跑出来的**（Java 21.0.6，单文件源码启动模式），不是手写的预期值。你自己跑出来应该一模一样，除了耗时数字。
>
> **Windows 用户注意**：`cmd`/PowerShell 默认 GBK，中文和箭头会乱码。加参数即可：
> ```bash
> java -Dstdout.encoding=UTF-8 -Dstderr.encoding=UTF-8 Case01.java
> ```
> 看到乱码不要以为代码错了——这是控制台编码问题，跟动态代理无关。

# 第一部分 · 使用篇

## 阶段一：建立动机

### 案例 1｜先感受静态代理的痛（这一步别跳）

```java
// Case01.java
public class Case01 {

    interface UserService {
        String findName(long id);
        void updateName(long id, String name);
    }

    static class UserServiceImpl implements UserService {
        public String findName(long id) { return "u" + id; }
        public void updateName(long id, String name) {
            System.out.println("  [真实逻辑] 更新 " + id + " -> " + name);
        }
    }

    // 手写代理：给每个方法加日志
    static class UserServiceLogProxy implements UserService {
        private final UserService target;
        UserServiceLogProxy(UserService target) { this.target = target; }

        public String findName(long id) {
            System.out.println("→ findName");
            String r = target.findName(id);
            System.out.println("← findName");
            return r;
        }

        public void updateName(long id, String name) {
            System.out.println("→ updateName");
            target.updateName(id, name);
            System.out.println("← updateName");
        }
    }

    public static void main(String[] args) {
        UserService svc = new UserServiceLogProxy(new UserServiceImpl());
        System.out.println(svc.findName(1L));
        svc.updateName(1L, "tom");
    }
}
```

实测输出：

```
→ findName
← findName
u1
→ updateName
  [真实逻辑] 更新 1 -> tom
← updateName
```

输出本身平淡无奇，**这个案例的价值全在代码的行数比例上，不在输出里。**

**要感受的痛，不是要记住的知识：**

- 接口加第 3 个方法 → 这个类必须跟着改，不改就编译不过
- 再来一个 `OrderService` → 整个类重写一遍
- 日志逻辑只有 2 行，包装代码是它的 10 倍

**这个比例失衡就是动态代理存在的全部理由。** 跳过这一步，动态代理对你就只是"另一种写法"，而不是"一种解脱"。

> [!question]- 动手：如果有 20 个 Service、每个 8 个方法，静态代理要写多少个方法？
> 160 个方法，每个方法体结构完全一样。而动态代理是 **1 个 handler**。这个数量级差异就是 Spring AOP 的价值。

## 阶段二：核心能力

### 案例 2｜最小可用版

```java
// Case02.java
import java.lang.reflect.Proxy;

public class Case02 {

    interface UserService { String findName(long id); }
    interface OrderService { String findOrder(long id); }

    public static void main(String[] args) {
        UserService target = id -> "u" + id;

        UserService proxy = (UserService) Proxy.newProxyInstance(
                UserService.class.getClassLoader(),          // ① 类加载器
                new Class<?>[]{ UserService.class },         // ② 对外的"人脸"
                (p, method, argv) -> {                       // ③ 内在的"灵魂"
                    System.out.println("→ " + method.getName());
                    try {
                        return method.invoke(target, argv);
                    } finally {
                        System.out.println("← " + method.getName());
                    }
                });

        System.out.println(proxy.findName(1L));
        System.out.println("真实类型 = " + proxy.getClass());
        System.out.println("是代理吗 = " + Proxy.isProxyClass(proxy.getClass()));

        // ★ 关键验证：代理只"是"你声明的接口，跟 target 的类型毫无关系
        Object weird = Proxy.newProxyInstance(
                Case02.class.getClassLoader(),
                new Class<?>[]{ OrderService.class },   // 声明的是 OrderService
                (p, m, a) -> null);
        try {
            UserService boom = (UserService) weird;      // 却往 UserService 强转
            boom.findName(1L);
        } catch (ClassCastException e) {
            System.out.println("★ 如期抛出 ClassCastException: 代理的身份由 interfaces 数组决定");
        }
    }
}
```

实测输出：

```
→ findName
← findName
u1
真实类型 = class $Proxy0
是代理吗 = true
★ 如期抛出 ClassCastException: 代理的身份由 interfaces 数组决定
```

把那个 `ClassCastException` 的完整消息打出来（`e.getMessage()`），信息量更大：

```
class $Proxy1 cannot be cast to class Case02$UserService
  ($Proxy1 and Case02$UserService are in unnamed module of loader ...)
```

注意是 **`$Proxy1`** —— 这是本程序里第二个被创建的代理类，编号按创建顺序递增。**看到编号就能知道 JVM 里已经生成了几个代理类。**

三个参数各自的职责，要能脱口而出：

| 参数 | 决定什么 | 写错的后果 |
| --- | --- | --- |
| `ClassLoader` | 生成的类放进哪个命名空间 | 加载器看不见接口 → `IllegalArgumentException` |
| `interfaces[]` | 代理对外**是什么** | 强转成不在数组里的类型 → `ClassCastException` |
| `handler` | 调用时**干什么** | 返回类型不匹配 → `ClassCastException` |

> [!warning] 最后那个验证不要跳过
> 它证明了一件反直觉的事：**代理和 target 之间没有任何类型上的血缘关系**，全靠 handler 里那句 `method.invoke(target, args)` 手动搭桥。理解这点，案例 9（根本没有 target）才不会觉得魔幻。

### 案例 3｜封装成工厂（能进项目的形态）

```java
// Case03.java
import java.lang.reflect.*;

public class Case03 {

    interface UserService {
        String findName(long id);
        void boom() throws BizException;
    }

    static class BizException extends Exception {
        BizException(String m) { super(m); }
    }

    static class UserServiceImpl implements UserService {
        public String findName(long id) { return "u" + id; }
        public void boom() throws BizException { throw new BizException("业务失败"); }
    }

    /** 通用日志代理工厂：泛型让调用方不用强转 */
    static class LogProxyFactory {
        @SuppressWarnings("unchecked")
        static <T> T wrap(T target, Class<T> iface) {
            return (T) Proxy.newProxyInstance(
                    iface.getClassLoader(),
                    new Class<?>[]{ iface },
                    new LogHandler(target));
        }
    }

    static class LogHandler implements InvocationHandler {
        private final Object target;
        LogHandler(Object target) { this.target = target; }

        public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
            long t0 = System.nanoTime();
            try {
                return method.invoke(target, args);
            } catch (InvocationTargetException e) {
                throw e.getCause();          // ★★ 剥掉反射的包装，把真实异常还给调用方
            } finally {
                System.out.printf("%s.%s cost=%.3fms%n",
                        target.getClass().getSimpleName(), method.getName(),
                        (System.nanoTime() - t0) / 1e6);
            }
        }
    }

    public static void main(String[] args) {
        UserService svc = LogProxyFactory.wrap(new UserServiceImpl(), UserService.class);
        System.out.println(svc.findName(1L));

        try {
            svc.boom();
        } catch (BizException e) {
            System.out.println("★ 上层成功捕获到 BizException: " + e.getMessage());
        } catch (Throwable t) {
            System.out.println("✗ 捕获到了意外类型: " + t.getClass().getName());
        }
    }
}
```

实测输出：

```
UserServiceImpl.findName cost=3.818ms
u1
UserServiceImpl.boom cost=0.694ms
★ 上层成功捕获到 BizException: 业务失败
```

注意 `findName` 那个 `cost=3.818ms` —— 一次字符串拼接不可能要 3.8 毫秒。**这是 JIT 预热 + 首次反射调用初始化的开销**，第二次调用就掉到 0.694ms 了。用 `System.nanoTime()` 手写计时永远要留意第一次的数字不可信，这也是为什么正经压测要用 JMH。

**那行 `throw e.getCause()` 是本案例真正的重点。** 我把它注释掉重跑了一遍，上层的 `catch (BizException e)` **完全失效**，走进了 `catch (Throwable)` 分支：

```
--- 对照实验：handler 不剥壳 ---
✗ 类型变了: java.lang.reflect.UndeclaredThrowableException
      cause = java.lang.reflect.InvocationTargetException
      cause.cause = Case03$BizException: 业务失败
```

看清楚这个**三层结构**：真实异常被埋在 `getCause().getCause()` 里。`InvocationTargetException` 是 `method.invoke` 包的第一层，`UndeclaredThrowableException` 是出 handler 时包的第二层（因为 `InvocationTargetException` 不在 `boom()` 的 throws 列表里）。

一次调用里两层包装的方向，记牢这个对称性：

```
调用方 ──→ $Proxy0 ──→ handler ──→ method.invoke ──→ 真实方法
                                        ↑                  │ 抛 BizException
                                        │                  ↓
                              InvocationTargetException 包第 1 层
                            │
                            ↓ handler 不剥壳直接往外抛
              UndeclaredThrowableException 包第 2 层（因为签名没声明它）
                            │
                            ↓
                       调用方彻底认不出来了
```

**生产事故的经典成因。写 handler 要条件反射地加上剥壳。**

### 案例 4｜按注解选择性拦截（框架的真正玩法）

前面是"所有方法一视同仁"，真实框架都是"贴了注解才拦"。

```java
// Case04.java
import java.lang.annotation.*;
import java.lang.reflect.*;

public class Case04 {

    @Retention(RetentionPolicy.RUNTIME)     // ★ 必须 RUNTIME，否则运行期读不到
    @Target(ElementType.METHOD)
    @interface Timed { }

    interface ReportService {
        @Timed String slowQuery();          // 注解贴在【接口】上
        String fastQuery();
    }

    static class ReportServiceImpl implements ReportService {
        public String slowQuery() { sleep(50); return "slow-result"; }
        public String fastQuery() { return "fast-result"; }
        private static void sleep(long ms) {
            try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        }
    }

    static class TimedHandler implements InvocationHandler {
        private final Object target;
        TimedHandler(Object target) { this.target = target; }

        public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
            // 写法 A：读【接口】方法上的注解
            boolean onInterface = method.isAnnotationPresent(Timed.class);

            // 写法 B：读【实现类】方法上的注解 —— handler 拿到的 method 来自接口，
            //         想读实现类的注解必须自己去查同签名方法
            Method implMethod = target.getClass()
                    .getMethod(method.getName(), method.getParameterTypes());
            boolean onImpl = implMethod.isAnnotationPresent(Timed.class);

            if (!onInterface && !onImpl) return method.invoke(target, args);

            long t0 = System.nanoTime();
            try {
                return method.invoke(target, args);
            } finally {
                System.out.printf("[Timed] %s %.1fms (接口上=%b, 实现类上=%b)%n",
                        method.getName(), (System.nanoTime() - t0) / 1e6, onInterface, onImpl);
            }
        }
    }

    public static void main(String[] args) {
        ReportService svc = (ReportService) Proxy.newProxyInstance(
                ReportService.class.getClassLoader(),
                new Class<?>[]{ ReportService.class },
                new TimedHandler(new ReportServiceImpl()));

        svc.slowQuery();       // 被计时
        svc.fastQuery();       // 不被计时，无输出
    }
}
```

实测输出：

```
[Timed] slowQuery 64.0ms (接口上=true, 实现类上=false)
```

**只有一行。** `fastQuery()` 没有任何输出 —— 这就是"选择性拦截"生效的证据：同一个 handler，同一个代理，靠注解决定拦不拦。

括号里那组 `接口上=true, 实现类上=false` 是本案例最该看的信息，它直接暴露了注解位置的差异。我把注解挪到实现类上、并让 handler 只用写法 A 跑了一遍对照：

```
--- 对照实验：注解只在实现类上，handler 只读接口 ---
[!] 上面一行没有 [Timed] 输出 = 拦截完全失效
```

> [!warning] 必做的对照实验
> 把 `@Timed` 从接口的 `slowQuery()` 挪到 `ReportServiceImpl.slowQuery()` 上，然后**只用写法 A**（注释掉写法 B）——你会发现拦截**完全不生效**。
>
> 原因：handler 收到的 `method` 是**接口的 `Method` 对象**，它身上没有实现类的注解。这也是为什么 Spring 里 `@Transactional` **推荐贴在实现类上而不是接口上**——接口上的注解不会被 CGLIB 子类代理继承。

### 案例 5｜改写参数与返回值

代理不只能"前后加料"，还能篡改数据流。

```java
// Case05.java
import java.lang.reflect.*;

public class Case05 {

    interface SmsService {
        String send(String phone, String content);
        String maybeNull();
    }

    public static void main(String[] args) {
        SmsService target = new SmsService() {
            public String send(String phone, String content) {
                System.out.println("  [真实逻辑] 收到手机号 = " + phone);
                return "ok";
            }
            public String maybeNull() { return null; }
        };

        SmsService proxy = (SmsService) Proxy.newProxyInstance(
                SmsService.class.getClassLoader(),
                new Class<?>[]{ SmsService.class },
                (p, method, argv) -> {
                    // 先把 argv 本身打出来，亲眼看无参方法的 argv 是什么
                    System.out.println(argv == null
                            ? "  [argv] null（无参方法！）"
                            : "  [argv] 长度 " + argv.length);

                    // ★ 入参改写：args 数组就是实参数组，直接改就生效
                    if (argv != null) {                    // ★ 无参方法 argv 是 null，不是空数组！
                        for (int i = 0; i < argv.length; i++) {
                            if (argv[i] instanceof String s && s.matches("\\d{11}")) {
                                argv[i] = s.substring(0, 3) + "****" + s.substring(7);
                            }
                        }
                    }

                    Object result = method.invoke(target, argv);

                    // ★ 返回值改写：null 兜底成空串，避免上层 NPE
                    if (result == null && method.getReturnType() == String.class) {
                        System.out.println("  [兜底] null -> \"\"");
                        return "";
                    }
                    return result;
                });

        System.out.println("send() = " + proxy.send("13812345678", "验证码 1234"));
        System.out.println("maybeNull() = [" + proxy.maybeNull() + "]");
    }
}
```

实测输出：

```
  [argv] 长度 2
  [真实逻辑] 收到手机号 = 138****5678
send() = ok
  [argv] null（无参方法！）
  [兜底] null -> ""
maybeNull() = []
```

第 2 行是关键证据：真实逻辑里打印的是 `138****5678`，**说明改 `argv` 数组真的改掉了传给目标方法的实参**，不是改了个副本。这个能力是**参数校验、日志脱敏、多租户自动注入 tenantId、返回值统一包装**的实现基础。

第 4 行是另一个关键证据：`maybeNull()` 无参，`argv` 打出来是 **`null` 而不是长度 0 的数组**。这个坑记死——不判空直接 `argv.length` 就是 NPE，而且只在调用无参方法时才炸，单元测试很容易漏掉。

### 案例 6｜重试（体会异常包装的方向）

```java
// Case06.java
import java.io.IOException;
import java.lang.reflect.*;

public class Case06 {

    interface RemoteApi {
        String fetch() throws IOException;
        String badParam();
    }

    static class FlakyApi implements RemoteApi {
        private int count = 0;
        public String fetch() throws IOException {
            if (++count < 3) throw new IOException("网络抖动 #" + count);
            return "第 " + count + " 次终于成功";
        }
        public String badParam() { throw new IllegalArgumentException("参数非法，重试也没用"); }
    }

    public static void main(String[] args) throws Throwable {
        RemoteApi target = new FlakyApi();

        RemoteApi proxy = (RemoteApi) Proxy.newProxyInstance(
                RemoteApi.class.getClassLoader(),
                new Class<?>[]{ RemoteApi.class },
                (p, method, argv) -> {
                    int maxAttempts = 5;
                    Throwable last = null;
                    for (int i = 1; i <= maxAttempts; i++) {
                        try {
                            return method.invoke(target, argv);
                        } catch (InvocationTargetException e) {
                            last = e.getCause();                    // ★ 真实异常在这里
                            // ★ 靠 cause 的类型决定"该不该重试"——不剥壳根本判断不了
                            if (!(last instanceof IOException)) throw last;
                            System.out.println("第 " + i + " 次失败，准备重试: " + last.getMessage());
                            Thread.sleep(50L * i);
                        }
                    }
                    throw last;
                });

        System.out.println("结果: " + proxy.fetch());

        try {
            proxy.badParam();
        } catch (IllegalArgumentException e) {
            System.out.println("★ 非重试异常直接抛出，没有浪费 5 次重试: " + e.getMessage());
        }
    }
}
```

实测输出：

```
第 1 次失败，准备重试: 网络抖动 #1
第 2 次失败，准备重试: 网络抖动 #2
结果: 第 3 次终于成功
★ 非重试异常直接抛出，没有浪费 5 次重试: 参数非法，重试也没用
```

两条信息要对着看：前三行是"重试了 2 次后成功"，最后一行是"根本没重试就直接抛"。**同一个 handler，行为分叉点就是 `last instanceof IOException` 那一句** —— 而 `last` 只能来自 `e.getCause()`。

本案例的价值：**你必须靠 `getCause()` 才能判断"该不该重试"。** 不剥壳的话你看到的永远是 `InvocationTargetException`，无法区分网络抖动和参数非法。重试、熔断、事务回滚判定（`rollbackFor`）全都建立在这一步上。

## 阶段三：踩坑（把"看过"变成"知道"）

### 案例 7｜`default` 方法也会被拦截

```java
// Case07.java
import java.lang.reflect.*;

public class Case07 {

    interface Greeter {
        String name();
        default String greet() { return "hi, " + name(); }   // 有实现体
    }

    public static void main(String[] args) {
        Greeter g = (Greeter) Proxy.newProxyInstance(
                Greeter.class.getClassLoader(),
                new Class<?>[]{ Greeter.class },
                (p, m, a) -> {
                    System.out.println("拦到了: " + m.getName() + "  isDefault=" + m.isDefault());
                    if (m.getName().equals("name")) return "tom";
                    // ★ Java 16+ 唯一正解：放行 default 方法的原始实现
                    return InvocationHandler.invokeDefault(p, m, a);
                });

        System.out.println("结果: " + g.greet());

        // ---- 对照：不用 invokeDefault，看 default 方法体是否被吞 ----
        System.out.println("--- 对照：不用 invokeDefault，直接返回 null ---");
        Greeter g2 = (Greeter) Proxy.newProxyInstance(
                Greeter.class.getClassLoader(),
                new Class<?>[]{ Greeter.class },
                (p, m, a) -> m.getName().equals("name") ? "tom" : null);
        System.out.println("结果: " + g2.greet());
    }
}
```

实测输出：

```
拦到了: greet  isDefault=true
拦到了: name  isDefault=false
结果: hi, tom
--- 对照：不用 invokeDefault，直接返回 null ---
结果: null   <- default 方法体被吞了
```

第一段的第二行 `拦到了: name` 是这个案例最值得盯的一行：**`greet()` 的方法体里调用 `name()`，这次调用又绕回了 handler。** 因为 `invokeDefault` 执行的是接口里那份原始方法体，而那份方法体的 `this` 就是代理对象 `p`，所以 `name()` 是一次**从外部打进代理**的调用。对比案例 11 的自调用（`this` 是 target，拦不住），这里恰好相反——差别就在于方法体运行在谁身上。

对照段那个 `结果: null` 是反面证据：**不调 `invokeDefault`，`greet()` 原本的方法体一次都不会执行**，你返回什么调用方就拿到什么。

两个结论：

1. **`default` 方法有实现体，也照样被代理类重写拦截**——这很反直觉
2. 想执行它原本的方法体，`method.invoke(target, args)` 是**错的**（target 可能压根不存在），唯一正解是 `InvocationHandler.invokeDefault(proxy, method, args)`

`invokeDefault` 是 Java 16 才有的 API。之前只能用 `MethodHandles.Lookup` + `unreflectSpecial` 那套极其别扭的写法，网上老文章里那些看不懂的 `Lookup` 代码就是在干这件事。

### 案例 8｜`toString`/`hashCode` 会进 handler（调试噩梦）

```java
// Case08.java
import java.lang.reflect.*;
import java.util.*;

public class Case08 {

    interface Greeter { String name(); }

    public static void main(String[] args) {
        // ---- 坏版本：无兜底 ----
        System.out.println("=== 无兜底 ===");
        Greeter bad = (Greeter) Proxy.newProxyInstance(
                Greeter.class.getClassLoader(),
                new Class<?>[]{ Greeter.class },
                (p, m, a) -> {
                    System.out.println("  拦到了: " + m.getName());
                    return null;
                });

        // ★ 触发 hashCode 进 handler —— 必须 try 住，否则程序直接终止（见下方说明）
        try {
            new HashMap<Greeter, String>().put(bad, "x");
        } catch (NullPointerException e) {
            System.out.println("  [炸了] NullPointerException: hashCode 返回 null，拆箱失败");
            System.out.println("  栈顶 = " + e.getStackTrace()[0]);
        }
        System.out.println("  打印代理: " + bad); // ★ 触发 toString → 返回 null
        System.out.println("  getClass: " + bad.getClass()
                + "   <- getClass 是 final，没被拦");

        // ---- 好版本：Object 方法兜底 ----
        System.out.println("=== 有兜底 ===");
        InvocationHandler h = new InvocationHandler() {
            public Object invoke(Object proxy, Method m, Object[] a) throws Throwable {
                // ★ 标准写法：Object 声明的方法交给 handler 自己处理
                if (m.getDeclaringClass() == Object.class) {
                    return m.invoke(this, a);
                }
                System.out.println("  业务拦截: " + m.getName());
                return "tom";
            }
        };
        Greeter good = (Greeter) Proxy.newProxyInstance(
                Greeter.class.getClassLoader(), new Class<?>[]{ Greeter.class }, h);

        new HashMap<Greeter, String>().put(good, "x");   // 不再打印日志
        System.out.println("  打印代理: " + good);        // 走 handler 自己的 toString
        System.out.println("  name() = " + good.name());
    }
}
```

实测输出：

```
=== 无兜底 ===
  拦到了: hashCode
  [炸了] NullPointerException: hashCode 返回 null，拆箱失败
  栈顶 = $Proxy0.hashCode(Unknown Source)
  拦到了: toString
  打印代理: null
  getClass: class $Proxy0   <- getClass 是 final，没被拦
=== 有兜底 ===
  put 进 HashMap 没有任何日志 = hashCode 被兜底了
  打印代理: Case08$1@294425a7
  业务拦截: name
  name() = tom
```

这段输出有三处值得逐行看：

`拦到了: hashCode` —— 代码里从来没调用过 `hashCode()`，只是 `map.put(bad, "x")`，`HashMap` 内部替你调了。**拦截逻辑在你完全没预料的时机被触发**，这就是这个坑的可怕之处。

紧接着的 NPE 是连带伤害：handler 返回 `null`，而 `hashCode()` 的返回类型是 `int`，代理类拆箱时炸了。**栈顶 `$Proxy0.hashCode(Unknown Source)` 是关键证据** —— `Unknown Source` 说明这个类没有源文件，是运行期生成的。排查篇工具 3 会专门讲怎么读这一行。

对比 `打印代理: null`（无兜底，`toString` 返回了 null）和 `打印代理: Case08$1@294425a7`（有兜底，走的是 handler 自己的 `toString`），能直接看出兜底那三行起了什么作用。

**这个坑的真实杀伤力**：handler 里打日志时，IDE 调试器**一悬停变量就触发 `toString`** 进入你的拦截逻辑——日志被打爆，甚至在断点处抛异常，让人怀疑人生。更狠的是把代理对象放进 `HashMap`/`HashSet` 会触发 `hashCode`，如果 handler 依赖某个还没初始化好的东西，就会在完全意想不到的地方炸。

标准兜底就是那三行 `getDeclaringClass() == Object.class`。**写 handler 的模板里应该默认带上它。**

注意 `getClass()` 是 `final` 的，**不会**被拦截——这正是为什么打印 `bean.getClass()` 永远能拿到真实的 `$Proxy0`，是排查代理问题最可靠的手段。

## 阶段四：框架真身

### 案例 9｜没有 target 的代理 —— MyBatis / Feign / AiServices 的核心

> [!important] 整套案例里最该花时间的一个
> 前面所有案例都有个 target，这个案例**根本没有实现类**。跑通它，你对 MyBatis Mapper、Feign 客户端、LangChain4j `AiServices` 的那层膜会一次性破掉。

```java
// Case09.java
import java.lang.annotation.*;
import java.lang.reflect.*;

public class Case09 {

    @Retention(RetentionPolicy.RUNTIME)
    @Target(ElementType.METHOD)
    @interface Prompt { String value(); }

    /** 注意：只有接口，没有任何实现类 */
    interface Assistant {
        @Prompt("把下面内容翻译成英文：{it}")
        String translate(String text);

        @Prompt("用一句话总结：{it}")
        String summarize(String text);

        String noAnnotation(String text);
    }

    @SuppressWarnings("unchecked")
    static <T> T create(Class<T> iface) {
        return (T) Proxy.newProxyInstance(
                iface.getClassLoader(),
                new Class<?>[]{ iface },
                (p, method, args) -> {
                    if (method.getDeclaringClass() == Object.class) {
                        return method.invoke(p, args);      // Object 方法兜底
                    }
                    Prompt ann = method.getAnnotation(Prompt.class);
                    if (ann == null) {
                        throw new IllegalStateException(
                                method.getName() + " 缺少 @Prompt 注解");
                    }
                    // 反射读注解 → 填模板 → （真实场景在这里发 HTTP 调模型）
                    String finalPrompt = ann.value().replace("{it}", String.valueOf(args[0]));
                    System.out.println("[发给模型] " + finalPrompt);
                    return "（假装是模型返回的结果）";
                });
    }

    public static void main(String[] args) {
        Assistant a = create(Assistant.class);     // ★ 没有实现类，却能直接用

        System.out.println(a.translate("你好世界"));
        System.out.println(a.summarize("很长的一段文章……"));

        try {
            a.noAnnotation("x");
        } catch (IllegalStateException e) {
            System.out.println("★ " + e.getMessage());
        }
    }
}
```

实测输出：

```
[发给模型] 把下面内容翻译成英文：你好世界
（假装是模型返回的结果）
[发给模型] 用一句话总结：很长的一段文章……
（假装是模型返回的结果）
★ noAnnotation 缺少 @Prompt 注解
```

盯住这段输出里**没有出现的东西**：没有任何一行来自实现类，因为**压根不存在实现类**。整个程序里 `Assistant` 只有一个接口声明，`create()` 返回的对象却能正常调用、能读到注解、能返回值。

第三行的报错也值得留意：`noAnnotation` 没贴注解，于是在 handler 里被判定为"这个方法我不知道怎么处理"。**真实框架就是这么做参数校验的**——MyBatis 遇到没有对应 SQL 的方法、Feign 遇到没有 HTTP 注解的方法，报的都是同一类错。

**三个框架，同一个机制**，差别只在 handler 里干什么：

| 框架 | 接口长什么样 | handler 里干什么 |
| --- | --- | --- |
| MyBatis | `UserMapper` + `@Select` | 拿注解/XML 里的 SQL 去执行，结果反射映射成对象 |
| Feign | `UserClient` + `@GetMapping` | 拼 URL、发 HTTP、反序列化响应 |
| LangChain4j `AiServices` | `Assistant` + `@UserMessage` | 拼 prompt、调模型、解析输出 |

跑通后回头看 [[../../../10-AI应用开发/02-框架-SpringAI与LangChain4j/LangChain4j/02-AiServices声明式AI服务|AiServices 声明式 AI 服务]]，你会发现"只写接口就能用"完全不神秘：`AiServices.create(Assistant.class, model)` 里面就是这段代码的加强版。

> [!question]- 想一想：为什么这三个框架都选接口而不是抽象类？
> 因为 JDK 动态代理**只能代理接口**（`$Proxy0` 已经 `extends Proxy`，用掉了唯一的继承位）。要代理类就得引入 CGLIB/ByteBuddy 依赖。用接口 = 零额外依赖 + 天然强制"无实现"的声明式风格。

### 案例 10｜多层代理叠加 = AOP 的本质

```java
// Case10.java
import java.lang.reflect.*;

public class Case10 {

    interface UserService { String findName(long id); }

    @SuppressWarnings("unchecked")
    static <T> T wrap(T target, Class<T> iface, String tag) {
        return (T) Proxy.newProxyInstance(
                iface.getClassLoader(), new Class<?>[]{ iface },
                (p, method, args) -> {
                    System.out.println(tag + " 前");
                    try {
                        return method.invoke(target, args);
                    } finally {
                        System.out.println(tag + " 后");
                    }
                });
    }

    public static void main(String[] args) {
        UserService target = id -> { System.out.println("  【真实方法】"); return "u" + id; };

        UserService step1 = wrap(target, UserService.class, "[日志]");
        UserService step2 = wrap(step1,  UserService.class, "[事务]");

        step2.findName(1L);

        System.out.println("step1 类 = " + step1.getClass());
        System.out.println("step2 类 = " + step2.getClass());
        System.out.println("是同一个代理类吗 = " + (step1.getClass() == step2.getClass()));
        System.out.println("是同一个实例吗   = " + (step1 == step2));
    }
}
```

实测输出：

```
[事务] 前
[日志] 前
  【真实方法】
[日志] 后
[事务] 后
step1 类 = class $Proxy0
step2 类 = class $Proxy0
是同一个代理类吗 = true
是同一个实例吗   = false
```

前 5 行就是洋葱：**外层先进、内层后进，出来的顺序完全颠倒。** `[事务]` 包着 `[日志]` 包着真实方法。Spring AOP 多个切面的执行顺序（`@Order`）就是在决定这个包裹顺序，自己叠两层跑一遍比读十篇 AOP 文章有用。

后面三行是本案例的隐藏重点，**`true` + `false` 这个组合正好印证了 `newProxyInstance` 一次干两件事**：

- `是同一个代理类 = true` → 造类那一步（ClassLoader + 接口数组）命中了缓存，`$Proxy0` 只生成了一次
- `是同一个实例 = false` → 造实例那一步用了不同的 handler，所以是两个对象

换句话说，**叠 N 层代理不会产生 N 个类，只会产生 N 个实例**。这也解释了为什么 Spring 应用里切面再多，元空间也不会被 `$ProxyN` 撑爆（真会撑爆的场景见排查工具 5 的坑 B）。

### 案例 11｜自调用失效的现场复现

> [!important] 这就是 `@Transactional` 自调用失效的完整机制，一模一样
> 在这里亲手复现过，面试时这题就不是背答案，而是描述你亲眼见过的现象。

```java
// Case11.java
import java.lang.reflect.*;

public class Case11 {

    interface UserService {
        String findName(long id);
        String findNameTwice(long id);
    }

    static class UserServiceImpl implements UserService {
        public String findName(long id) {
            System.out.println("  【真实 findName】this = " + this.getClass().getSimpleName());
            return "u" + id;
        }
        public String findNameTwice(long id) {
            // ★ this 调用：this 是 UserServiceImpl 实例，不是代理
            return findName(id) + "/" + findName(id);
        }
    }

    public static void main(String[] args) {
        UserService target = new UserServiceImpl();
        UserService proxy = (UserService) Proxy.newProxyInstance(
                UserService.class.getClassLoader(),
                new Class<?>[]{ UserService.class },
                (p, method, args) -> {
                    System.out.println("★ 拦截器执行: " + method.getName());
                    return method.invoke(target, args);
                });

        System.out.println("--- 外部调用 findName ---");
        proxy.findName(1L);

        System.out.println("--- 外部调用 findNameTwice（内部调了 2 次 findName）---");
        proxy.findNameTwice(1L);
        System.out.println("↑ 注意：拦截器只出现了 1 次，内部那 2 次 findName 一次都没被拦");
    }
}
```

实测输出：

```
--- 外部调用 findName ---
★ 拦截器执行: findName
  【真实 findName】this = UserServiceImpl
--- 外部调用 findNameTwice（内部调了 2 次 findName）---
★ 拦截器执行: findNameTwice
  【真实 findName】this = UserServiceImpl
  【真实 findName】this = UserServiceImpl
↑ 注意：拦截器只出现了 1 次，内部那 2 次 findName 一次都没被拦
```

**盯住"★ 拦截器执行"出现的次数：第二段只有 1 次，而【真实 findName】有 2 次。** 这两个数字对不上，就是自调用失效的全部证据——方法确实执行了，拦截器确实没跑。线上表现就是"事务没开、日志没记，但业务逻辑完全正常"，最难查的那种。

另外注意每行 `this = UserServiceImpl` 而不是 `$Proxy0`：**真实方法体里的 `this` 永远是 target，代理在它的视野之外。**

**一句话说透**：`findNameTwice` 的方法体运行在 **target 对象**上，它的 `this` 是 `UserServiceImpl` 实例，压根不知道外面还套了个代理。**代理只能拦住"从外面打进来的电话"，拦不住"屋里自己人互相喊话"。**

对应到 Spring：`@Transactional` 加在 `findName` 上，外部调用 `findNameTwice` 时，里面两次 `findName` **完全没有事务**。三种解法：

```java
// 解法 1：注入自己（最常用）
@Autowired @Lazy private UserService self;
public String findNameTwice(long id) { return self.findName(id) + "/" + self.findName(id); }

// 解法 2：拆到另一个 Bean（最干净，推荐）

// 解法 3：AopContext（需开启 exposeProxy = true，不推荐，侵入性强）
((UserService) AopContext.currentProxy()).findName(id);
```

### 案例 12｜Method 缓存（性能优化的正确顺序）

```java
// Case12.java
import java.lang.reflect.*;
import java.util.*;
import java.util.concurrent.*;

public class Case12 {

    interface Calc { int add(int a, int b); }
    static class CalcImpl implements Calc { public int add(int a, int b) { return a + b; } }

    static class CachedHandler implements InvocationHandler {
        private final Object target;
        // 接口 Method → 实现类 Method，避免每次调用都 getMethod 查找
        private final Map<Method, Method> cache = new ConcurrentHashMap<>();

        CachedHandler(Object target) { this.target = target; }

        public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
            Method impl = cache.computeIfAbsent(method, m -> {
                try {
                    Method x = target.getClass().getMethod(m.getName(), m.getParameterTypes());
                    x.setAccessible(true);
                    return x;
                } catch (NoSuchMethodException e) {
                    throw new IllegalStateException(e);
                }
            });
            return impl.invoke(target, args);
        }
    }

    public static void main(String[] args) throws Exception {
        Calc target = new CalcImpl();
        Method ifaceMethod = Calc.class.getMethod("add", int.class, int.class);
        int N = 2_000_000;

        // A. 每次都 getMethod（错误示范）
        long t0 = System.nanoTime();
        for (int i = 0; i < N; i++) {
            Method m = target.getClass().getMethod("add", int.class, int.class);
            m.invoke(target, 1, 2);
        }
        long a = System.nanoTime() - t0;

        // B. 缓存 Method 后 invoke
        t0 = System.nanoTime();
        for (int i = 0; i < N; i++) ifaceMethod.invoke(target, 1, 2);
        long b = System.nanoTime() - t0;

        // C. 直接调用（基线）
        t0 = System.nanoTime();
        int sum = 0;
        for (int i = 0; i < N; i++) sum += target.add(1, 2);
        long c = System.nanoTime() - t0;

        System.out.printf("每次 getMethod : %6.1f ms%n", a / 1e6);
        System.out.printf("缓存后 invoke  : %6.1f ms%n", b / 1e6);
        System.out.printf("直接调用       : %6.1f ms  (sum=%d)%n", c / 1e6, sum);
        System.out.printf("→ 缓存带来的提升约 %.1f 倍%n", (double) a / b);
    }
}
```

实测输出（本机 Java 21，200 万次调用，你的机器数字会有差异但比例接近）：

```
每次 getMethod :  164.8 ms
缓存后 invoke  :   30.6 ms
直接调用       :    4.6 ms  (sum=6000000)
-> 缓存带来的提升约 5.4 倍
```

这三个数字的关系比任何结论都有说服力：**光是把 `getMethod` 移出循环就快了 5.4 倍**，而缓存之后剩下的反射开销（30.6ms vs 4.6ms）只有 6.6 倍。也就是说，反射慢的锅里**大头是"重复查找元数据"，不是 `invoke` 本身**。

要理解的量级关系：**`getMethod()` 是查找（遍历方法表 + 复制 `Method` 对象），比 `invoke()` 本身贵得多。** 所以优化的第一步永远是**缓存元数据**，而不是急着换 `MethodHandle`。

配合原理篇实测的那组数字（5000 万次空方法调用：直接 4.12ms / 反射 179.13ms / MethodHandle 120.73ms）一起看：43 倍是**空方法**的放大倍数，**绝对值只有每次约 3.5ns**。方法体是毫秒级业务（数据库查询、HTTP 调用）时，这点开销毫无意义。

**判断标准是方法体的量级，不是倍数。** 先 profiler，再动手。

## 工具 3｜断点该打在哪 + 调用栈怎么读

**在 handler 的 `invoke` 里打断点**，然后看调用栈：

```
UserServiceImpl.findName(...)             ← 真实方法
LogHandler.invoke(LogHandler.java:12)     ← 你的拦截逻辑（断点在这）
$Proxy0.findName(Unknown Source)          ← ★ 生成的代理，无源码所以是 Unknown Source
Main.main(Main.java:20)                   ← 调用方
```

**看到 `$Proxy0.xxx(Unknown Source)` 就等于确认"这次调用走了代理"。**

反过来更有用：线上日志的异常栈里如果**缺了这一层**，说明调用绕过了代理——**自调用问题的铁证**，比任何猜测都硬。

想看代理类怎么生成的，断点打在 `Proxy.newProxyInstance` 然后 step into：

```
Proxy.newProxyInstance
  └→ getProxyConstructor(caller, loader, interfaces)
       └→ proxyCache.sub(...).computeIfAbsent(...)      ← 缓存在这，命中就不再生成
            └→ ProxyBuilder.build()
                 └→ ProxyGenerator.generateProxyClass() ← 字节码在这里被拼出来
                      └→ defineClass0(...)              ← 塞进 JVM
```

`ProxyGenerator` 值得扫一眼，它就是纯粹地拼字节码，没有任何魔法。读完你对"运行期生成类"的神秘感会彻底消失。

## 工具 4｜Arthas（线上无源码时唯一的办法）

配合 [[../../02-JVM/08-常用工具-jstat-jmap-jstack-Arthas|Arthas]] 使用：

```bash
sc -d '*UserService*'                        # 真实全名、类加载器、是不是代理
jad com.example.UserServiceImpl findName     # 反编译线上代码，确认版本对不对
jad '$Proxy0'                                # ★ 直接反编译代理类，不用重启加 -D 参数

stack com.example.UserServiceImpl findName   # ★ 打印调用来源，看栈里有没有 $Proxy 那一层
trace com.example.UserServiceImpl findName   # 看每层耗时，能看出拦截器链有多少层
watch com.example.UserServiceImpl findName '{params, returnObj, throwExp}' -x 2
```

**`stack` 是排查自调用失效的杀手级命令**：它直接告诉你这个方法从哪儿被调进来的，栈里有 `$Proxy` 就是走代理，没有就是内部自调用。不用改代码、不用重启。

## 工具 5｜三个源码级的坑（只有看过源码才知道）

### 坑 A：接口顺序影响 `Method` 对象的归属

```java
interface A { void run(); }
interface B { void run(); }

// 顺序不同 → handler 收到的 method.getDeclaringClass() 不同
Proxy.newProxyInstance(cl, new Class<?>[]{ A.class, B.class }, h);  // → interface A
Proxy.newProxyInstance(cl, new Class<?>[]{ B.class, A.class }, h);  // → interface B
```

规则：**重复签名的方法，取数组里第一个声明它的接口的 `Method` 对象。**

如果你的 handler 靠 `method.getDeclaringClass()` 做分发，**接口数组顺序一变行为就变**。极难排查，因为业务代码"看起来"完全没动。

更狠的：两个接口的同名同参方法**返回类型不兼容**时，`newProxyInstance` 直接抛 `IllegalArgumentException`，连类都生成不出来。

### 坑 B：代理类是缓存的，缓存键包含接口顺序

`loader + 有序接口列表` 是缓存 key。所以案例 10 里两层代理共用一个 `$Proxy0`；但把接口顺序换一下，就会**多生成一个类**。

排查"元空间为什么涨"时，如果发现大量 `$ProxyN`，通常是有人在循环里用动态构造的接口数组建代理。

### 坑 C：非 public 接口决定代理类的包

代理一个包级私有接口，生成的类必须被放进**该接口所在的包**（否则实现不了它）。此时如果 interfaces 数组里还有**另一个包的**非 public 接口，直接抛 `IllegalArgumentException`——一个类不可能同时在两个包里。

这也解释了实测现象：自己写的接口生成 `$Proxy0` 在默认包；`Runnable` 是 public 且在 `java.base` 模块，代理被放进动态模块 `jdk.proxy1`。

## 🧭 排查决策树

遇到"代理相关行为不对"，按顺序走，别跳步：

```
1. 打印 bean.getClass()
   ├─ 原始类名 → 没有代理
   │             查：Bean 是否被容器管理 / AOP 是否启用 / 是否自己 new 的
   ├─ $Proxy   → 有 JDK 代理，进 2
   └─ $$CGLIB  → 有子类代理，另查：方法是否 final/private/static（都不能被重写）

2. 拦截逻辑到底有没有执行？在 handler 第一行打日志或断点
   ├─ 没进来 → 调用没走代理
   │            看异常栈里有没有 $Proxy0 那一层 → 大概率自调用（案例 11）
   └─ 进来了 → 进 3

3. 进来了但行为不对
   ├─ 注解读不到      → @Retention 是否 RUNTIME？贴接口还是实现类？（案例 4）
   ├─ 异常类型不对    → handler 漏了 getCause() 剥壳？（案例 3 / 6）
   ├─ default 没执行  → 该用 invokeDefault（案例 7）
   ├─ 日志被打爆      → toString/hashCode 也进来了（案例 8）
   ├─ 参数没生效      → 无参方法 args 是 null（案例 5）
   └─ 还是说不通      → 导出字节码 javap（工具 2）或 Arthas jad（工具 4）
```
