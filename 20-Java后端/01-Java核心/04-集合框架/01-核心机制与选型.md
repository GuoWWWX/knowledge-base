# 集合框架-核心机制与选型

## 📌 这是什么：集合家族全景

两棵家族树。**记住一句话：Set 就是"只用 key 的 Map"；Queue/Deque 是"有队首队尾语义的 Collection"**。

> [!tip] 两个维度别混：接口体系 vs 实现体系
> - **接口体系（是什么）**：`Set extends Collection`——Set 在语义上是"不重复的单元素容器"，API（add/remove/contains）与 Collection 一致，所以属于 Collection 家族。
> - **实现体系（怎么做）**：`HashSet` 内部**组合**了一个 `HashMap`（`private final HashMap<E,Object> map`）委托干活，**不是 HashMap 的子类**（`new HashSet<>() instanceof HashMap` 是 false）。
> - 类比：Set 是"用哈希表实现的不重复集合"——语义归 Collection，手段借 Map。所以 `Map.keySet()` 返回的就是 Set。

```
Collection（单元素容器）
├── List（有序、可重复、按下标访问）
│   ├── ArrayList      —— 数组实现（默认首选）      → 05 课
│   └── LinkedList     —— 双向链表                 → 05 课
├── Set（不重复）
│   ├── HashSet        —— 底层 HashMap（默认首选）   → 06 课
│   ├── LinkedHashSet  —— 底层 LinkedHashMap（保插入序）→ 06 课
│   └── TreeSet        —— 底层 TreeMap（按排序）     → 06 课
└── Queue/Deque（队列/双端队列）
    ├── ArrayDeque     —— 循环数组（默认首选）       → 09 课
    └── PriorityQueue  —— 二叉堆（按优先级出队）     → 09 课

Map（键值映射，不继承 Collection）
├── HashMap           —— 哈希表（默认首选）          → 07 课
├── LinkedHashMap     —— HashMap + 双向链表（保序/LRU）→ 08 课
└── TreeMap           —— 红黑树（按 key 排序）        → 08 课

遗留类（面试认识即可，生产别用）：Vector、Stack、Hashtable —— 方法全 synchronized，性能差
```

## 🤔 解决什么问题 / 为什么需要

- **选型错误 = 线上慢接口**：`List.contains` 是 O(n)，`HashSet.contains` 平均 O(1)——循环里调用 10 万次就是 10 万倍差距。本课第一目标是**会选**。
- **公共机制决定正确性**：equals/hashCode 契约、fail-fast、迭代器是所有实现共用的地基，任何一个用错都会出隐蔽 bug。
- **面试的"框架层"考点都在这**：Collection vs Collections、fail-fast 是不是并发安全、为什么声明用接口类型、equals/hashCode 为什么必须一起重写。

## 🧩 一图选型：先看语义，再看复杂度

| 接口 | 实现 | 底层结构 | 顺序 | 允许 null | 查/增 复杂度 | 什么时候用 |
| ---- | ---- | ---- | ---- | ---- | ---- | ---- |
| List | **ArrayList** | `Object[]` | 保序(按下标) | 允许 | 按下标查 O(1)；尾增摊还 O(1)；中间插删 O(n) | **默认列表**：读多、尾增、要下标 |
| List | LinkedList | 双向链表 | 保序 | 允许 | 按下标查 O(n)；头尾增删 O(1) | 频繁头尾操作（一般用 ArrayDeque 更好） |
| Set | **HashSet** | HashMap | 无序 | 允许 1 个 | contains O(1) 平均 | **默认去重**、快速 contains |
| Set | LinkedHashSet | LinkedHashMap | 插入序 | 允许 1 个 | O(1) 平均 | 去重 + 要保插入顺序 |
| Set | TreeSet | TreeMap(红黑树) | 按比较器排序 | 不允许 | O(log n) | 去重 + 要排序/范围查询 |
| Map | **HashMap** | 数组+链表/红黑树 | 无序 | key/value 均允许 | get/put O(1) 平均 | **默认键值**、缓存、计数 |
| Map | LinkedHashMap | HashMap+双向链表 | 插入序/访问序 | 允许 | O(1) 平均 | 保序 Map；accessOrder=true 做 LRU（最近最少使用淘汰，见 05 篇） |
| Map | TreeMap | 红黑树 | 按 key 排序 | key 不允许 | O(log n) | 排序、范围查询(floorEntry 等) |
| Queue | **ArrayDeque** | 循环数组 | FIFO | 不允许 | 头尾操作 O(1) | **默认队列/栈** |
| Queue | PriorityQueue | 二叉堆 | 按优先级 | 不允许 | 入/出 O(log n) | 任务按优先级处理、TopK |

**选型三步**（背下来，面试直接答）：
1. 是键值对 → Map；单元素 → Collection。
2. 要不要去重 → Set；要不要保序/下标 → List；FIFO/栈 → Queue。
3. 具体实现看"顺序"和"复杂度"两列：**默认就选加粗的四个**（ArrayList/HashSet/HashMap/ArrayDeque），有特殊顺序需求才换 Linked/Tree 变体。

## 🔍 公共源码机制（所有集合共用）

### 机制 1：接口层次与通用方法

```java
// 根接口：Iterable —— 能 for-each
public interface Iterable<T> { Iterator<T> iterator(); }

// Collection 接口的核心方法（所有单元素容器共有）
public interface Collection<E> extends Iterable<E> {
    boolean add(E e);            // 返回是否改变（Set 返回 false 表示重复）
    boolean remove(Object o);    // 按 equals 删，返回是否删除
    boolean contains(Object o);  // 按 equals 查（复杂度取决于实现！）
    int size(); boolean isEmpty(); void clear();
    Iterator<E> iterator();
    default Stream<E> stream() { ... }   // JDK 8+
}

// Map 不继承 Collection！它是一套独立的键值 API
public interface Map<K, V> {
    V put(K key, V value);       // 返回旧值（没有返回 null）
    V get(Object key);           // 没有返回 null
    boolean containsKey(Object key);
    V remove(Object key);
    Set<K> keySet(); Collection<V> values(); Set<Map.Entry<K,V>> entrySet();
}
```

**面试必答点**：
- `Map` 为什么**不继承 Collection**？语义不同：Collection 是"单元素容器"，Map 是"键值对容器"。若 Map 继承 Collection，那 `add(e)` 语义是什么（加 key？加 entry？）说不清，所以设计上分家。
- **为什么声明用接口类型**（`List<String> list = new ArrayList<>()` 而不是 `ArrayList<String>`）？面向接口编程：换实现（如换 LinkedList）不用改业务代码；`Collections` 工具类、Stream API 都按接口操作。
- `contains/remove/equals` 判断"相等"用的都是 `equals` 方法——这就是契约的地基。

### 机制 2：equals/hashCode 契约（哈希容器的地基）

所有基于哈希的容器（HashSet/HashMap/Hashtable 系列）依赖两条规则：

1. **相等对象 hashCode 必须相等**：`a.equals(b)` 为 true ⇒ `a.hashCode() == b.hashCode()`。违反它 → 相等的对象散到不同桶 → contains/get 找不到。
2. **hashCode 相等不代表相等**：不同对象可能同桶（哈希冲突），由 equals 最终判断。

```java
// 正确写法（手写规则）：
@Override public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof User u)) return false;
    return id == u.id && Objects.equals(name, u.name);   // 参与比较的字段
}
@Override public int hashCode() { return Objects.hash(id, name); }  // 必须与 equals 用同一组字段
```

**面试必答点**：
- 只重写 equals 不重写 hashCode → 相等的对象 hashCode 不同 → 散到不同桶 → `contains` 返回 false（"我明明 add 了却查不到"）。
- **参与计算的字段必须不可变**：对象放进 Set/Map 后若修改了这些字段 → 桶位错乱，对象"丢失"（还在集合里但查不到）。
- 现代写法：`record User(long id, String name) {}` 自动生成正确配套的 equals/hashCode（见 [[../14-Java新特性-Record与密封类]]）。

### 机制 3：modCount 与 fail-fast（为什么迭代时报 ConcurrentModificationException）

```java
// 所有"可结构性修改"的集合（ArrayList/HashMap 等）都维护一个修改计数：
// protected transient int modCount;   // 每次 add/remove/clear 都 +1

// 迭代器内部（以 ArrayList.Itr 为例）：
private class Itr implements Iterator<E> {
    int expectedModCount = modCount;              // 创建迭代器时"快照"
    public E next() {
        checkForComodification();                 // 每次 next 都检查
        ...
    }
    final void checkForComodification() {
        if (modCount != expectedModCount)
            throw new ConcurrentModificationException();  // 发现被改过就抛
    }
}
```

**逐点看懂**：迭代器创建时记下 `expectedModCount`；任何结构修改（add/remove/clear）都会 `modCount++`。下次 `next()` 发现两边不一致 → 抛异常。**增强 for 本质就是迭代器**，所以循环内 `list.remove(x)` 必然触发。

**面试必答点**：
- fail-fast 是**并发安全机制吗？** 不是。它只做"检测"：尽早暴露"迭代过程中被结构性修改"这个错误，**不保证一定能检测到**（比如删除后再加回，modCount 可能恰好不变），更不提供并发保护。
- 正确删除方式：`iterator.remove()`（它同步维护 expectedModCount）；或收集要删的元素，遍历结束后批量删除。

### 机制 4：迭代器与遍历方式对比

```java
// 三种遍历方式：
for (int i = 0; i < list.size(); i++) { list.get(i); }   // ① 下标遍历（仅 List 可用）
for (String s : list) { }                                // ② 增强 for = 迭代器（有 fail-fast 保护）
list.forEach(s -> { });                                  // ③ Lambda（底层还是迭代器）
// ④ Stream（06 课）：适合过滤/转换/分组，遍历+处理一体
```

**面试必答点**：
- 增强 for 是语法糖，反编译就是 `Iterator` 的 `hasNext/next`——所以循环内直接 `list.remove()` 抛 ConcurrentModificationException。
- 迭代时修改集合的三种正确姿势：`iterator.remove()`、收集后批量删（`list.removeAll(toRemove)`）、`removeIf`（JDK 8+，一行）。
- **subList 陷阱**：`list.subList(0, 2)` 返回的是**视图**（不是新列表），对原 list 的结构修改会让视图失效抛 `ConcurrentModificationException`；subList 的修改会反映到原 list。

### 机制 5：Collections 工具类（面试高频）

```java
List<String> list = new ArrayList<>(...);
Collections.sort(list);                       // 排序（List 用）
Collections.reverse(list);                    // 反转
Collections.shuffle(list);                    // 打乱
Collections.max(list); Collections.min(list); // 最大/最小
Collections.frequency(list, "a");             // 统计出现次数
Collections.copy(dest, src);                  // 拷贝（PECS 标准样例，见 01 课）

// 不可变视图（只读包装，改动抛 UnsupportedOperationException）：
List<String> ro = Collections.unmodifiableList(list);
Map<String, Integer> rom = Collections.unmodifiableMap(map);

// 空集合与单元素集合：
Collections.emptyList(); Collections.emptyMap();
Collections.singletonList("a");
// JDK 9+ 更推荐：List.of() / Map.of("a", 1) —— 不可变
```

**面试必答点**：`Collection`（接口）vs `Collections`（工具类）vs `Arrays`（数组工具类）——三者名字别搞混；`Collections` 的 `synchronizedXxx` 包装方法现在不推荐（用并发容器，见并发章节）。

## 🛠️ 排查 / 实践要点（公共）

- 慢接口先看**容器 + 复杂度**：`List.contains` O(n) vs `HashSet.contains` O(1)；循环内调用要乘外层次数（`for users -> roles.contains(x)` 是 O(n×m)）→ 换 HashSet 或倒排。
- 去重/查找失效：先查 equals/hashCode 是否同时重写、参与字段是否可变。
- 迭代异常：查增强 for 中是否直接 remove → 改 `iterator.remove()`/`removeIf`。
- 大批量插入前预估容量：`new ArrayList<>(n)`、`new HashMap<>(n/0.75f + 1)`（理由见 05/07 课源码）。

## ⚠️ 踩坑与注意事项（公共）

- 声明用实现类型而非接口类型（`ArrayList<String> list`），换实现就要改代码。
- 把 HashMap 迭代顺序当稳定行为（不保证顺序；要保序用 LinkedHashMap，见 08 课）。
- 修改放进集合后的对象字段（破坏 hashCode）。
- `Arrays.asList(...)` 结果直接 add/remove → `UnsupportedOperationException`（定长视图）；要可变就 `new ArrayList<>(Arrays.asList(...))`。
- 单线程场景用并发容器（性能浪费）；并发场景用普通容器（数据错乱）——正确选择见并发章节。

## 🎯 面试问题（框架层）

> [!question] 高频问题
> - Q: Collection 和 Collections 的区别？
>   - A: Collection 是集合框架的根接口（List/Set/Queue 继承它）；Collections 是操作集合的静态工具类（sort/reverse/unmodifiableXxx）。
> - Q: Map 为什么不继承 Collection？
>   - A: 语义不同：Collection 是单元素容器（add(e)），Map 是键值对容器（put(k,v)）；强行继承会使 add 语义混乱，所以设计上分家。
> - Q: 为什么声明变量用接口类型？
>   - A: 面向接口编程：换实现不改业务代码，且工具方法按接口操作。也便于测试时替换实现。
> - Q: fail-fast 是并发安全机制吗？
>   - A: 不是。modCount 检测只是尽早暴露"迭代中结构被修改"，不保证检测到所有情况，也不是同步保护。
> - Q: 为什么 equals 和 hashCode 必须一起重写？
>   - A: 哈希容器先用 hashCode 定位桶、再用 equals 判相等；只重写一个会导致相等对象找不到、去重失效。
> - Q: 迭代时怎么安全删除元素？
>   - A: iterator.remove()、收集后批量删除、或 removeIf；直接 list.remove 会抛 ConcurrentModificationException。

## 🧪 最小验证

```java
// 1. fail-fast
List<Integer> list = new ArrayList<>(List.of(1, 2, 3));
Iterator<Integer> it = list.iterator();
list.add(4);
it.next();   // ConcurrentModificationException

// 2. 契约破坏
class BadKey { int id; }          // 没重写 hashCode
Set<BadKey> s = new HashSet<>();
s.add(new BadKey());
System.out.println(s.contains(new BadKey()));   // false：hashCode 不同，桶都不同

// 3. 去重保序一行流
List<String> dup = List.of("b", "a", "b", "c");
System.out.println(new ArrayList<>(new LinkedHashSet<>(dup)));  // [b, a, c]

// 4. 视图陷阱
List<String> sub = list.subList(0, 2);
list.add("x");        // 修改原 list
sub.size();           // ConcurrentModificationException（视图失效）
```

生产排障：集合慢接口先列"容器/数据量/操作/复杂度"四列；去重与查找问题先查 equals/hashCode；迭代异常先查循环内 remove。
