## 2. 简历项目包装与面试应答黄金法则

大厂面试官在评估项目经历时，核心考察三点：
1. **真实性（Authenticity）**：技术细节是否经得起追问？能不能说清关键表结构、配置参数和异常踩坑？
2. **第一性原理与权衡取舍（Trade-off）**：为什么选方案 A 而不选方案 B？引入新组件后带来了什么副作用？
3. **数据量化成果（Metrics）**：改造前后 QPS、P99 延迟、错误率、机器资源消耗有何质的飞跃？

```text
======================= 简历描述量化黄金公式 =======================
【动词】+【业务痛点与技术挑战】+【基于何种架构/算法/设计模式进行攻坚】+【最终达成的量化性能/可用性指标】
例：通过采用“Feistel伪随机置换算法 + Base62编码”，实现百亿短码0碰撞生成；

    P99 响应时间由 180ms 压降至 2.1ms。
```

## 3. 大厂项目实战面试 30 秒绝杀 10 连问

### Q1：秒杀系统中，Redis 预扣库存成功了，但 RocketMQ 发送网络超时抛异常，你怎么保证少卖问题？
> **答题标杆**：采用“**资格预留流水（Reservation）+ 后台看门狗守护线程定时对账**”。预扣成功时写入一条带 30 秒有效期的临时凭证，后台守护线程扫描超期的孤儿预留，若核对 MySQL 确认既未出单也无消费流水，判定投递中断，通过 Lua 脚本原子将 Redis 库存加回并移除用户已抢标记，彻底规避少卖风险。

### Q2：为什么短链服务用 302 重定向而坚决不用 301？
> **答题标杆**：301 是永久重定向，会被浏览器硬缓存到本地磁盘。后续用户点击短链直接从浏览器本地跳往长地址，请求根本不再经过短链服务器，导致全平台的 PV/UV 统计、来源渠道分析、黑产风控和违规短链随时下线功能彻底瘫痪；302 临时重定向配合 `no-cache` 能保证每次都经过网关，牢牢掌握数据与控制权。

### Q3：自增 ID 转短链有被黑客连续猜测遍历的风险，如何低成本破解？
> **答题标杆**：摒弃纯随机（碰撞率随数据增加几何级飙升、查重慢）。采用 **64位 Feistel 伪随机置换算法 + Base62 编码**。自增 ID 经 Feistel 置换后，在数论上保持绝对的一对一双射映射（0 碰撞率），但输出呈高度离散的伪随机分布，黑客无法连续暴力枚举。

### Q4：订单超时关单和晚到的支付回调在同一毫秒并发到达，怎么防止“钱扣了但单关了”引发客诉？
> **答题标杆**：推进状态采用数据库行锁 CAS 条件更新（`WHERE status = 'WAIT_PAY'`）。若关单任务抢先成功，晚到的支付回调发现状态已为 `CANCELLED`，绝不强行将订单改回已支付；而是记录异常流水，并在当前事务中自动调用第三方支付渠道的“原路退款 API”，完成自动退款闭环。

### Q5：买家按用户 ID 查订单，商家按店铺 ID 查订单，分库分表后如何做到双端查询都不跨库广播？
> **答题标杆**：核心交易库使用“**分片基因法**”，将 `userId` 的后几位二进制基因强行嵌入到 `orderNo` 末尾，买家查订单单库精准路由；同时利用 Canal 监听 MySQL Binlog，准实时将订单宽表打入 Elasticsearch（按 `merchantId` 路由分片），供商家端进行超高并发的多条件筛选，交易与查询物理彻底隔离。

### Q6：在 Spring Cloud Gateway 的 GlobalFilter 中调用阻塞式 JDBC 或同步 RestTemplate 会导致什么灾难？
> **答题标杆**：Spring Cloud Gateway 底层基于 Netty 反应式编程，其 EventLoop 线程数极少（仅等于 CPU 核心数）。在过滤器中执行阻塞调用会直接挂起 EventLoop 线程。只要并发进入几个慢请求，网关的工作线程池瞬间被全部耗尽，导致全公司所有路由转发全线卡死瘫痪。必须使用 `WebClient` 等非阻塞 API 或调度到独立的 `boundedElastic` 线程池。

### Q7：全链路灰度中，微服务使用 Feign 调用下游时，如何保证灰度染色标签不丢失？
> **答题标杆**：配置 OpenFeign 的 `RequestInterceptor` 拦截器。在发起 HTTP 调用前，拦截器从当前线程的 `RequestContextHolder`（或 OpenTelemetry 上下文）中提取 `X-Gray-Tag` 和 `X-Trace-Id`，并自动注入到 Feign 的请求头中，实现跨服务透明透传。多线程异步场景下配合 `TransmittableThreadLocal`（TTL）包装线程池。

### Q8：线上 Java 进程 CPU 100%，如何在 30 秒内精准定位到具体的代码行？
> **答题标杆**：四步闪电定位法：
> 1. `top` 找出最高 CPU 消耗的 Java 进程 PID；
> 2. `top -H -p <PID>` 找出该进程内 CPU 最高的线程 TID；
> 3. `printf "%x\n" <TID>` 将十进制 TID 转为十六进制；
> 4. `jstack <PID> | grep -A 20 "0x<十六进制>"` 直接输出对应代码堆栈行号。使用阿里 Arthas 则只需一条命令：`thread -n 3`。

### Q9：生产环境发生 OOM，如何利用 MAT（Memory Analyzer）分析 dump 文件并揪出真凶？
> **答题标杆**：
> 1. 打开 MAT 的 **Dominator Tree（支配树）**，按 **深堆（Retained Heap）** 降序排列，找出连带占用内存最大的可疑对象；
> 2. 对可疑对象右键选择 `Path to GC Roots`，并勾选 `exclude all phantom/weak/soft references` 排除所有非强引用；
> 3. 展开剩下的唯一强引用链，直接追溯到根对象（如静态线程池复用导致 ThreadLocal 未 remove、或无界缓存容器），精确定位泄漏源头。

### Q10：生产环境中突发 JVM 堆外内存暴涨（Direct Memory OOM），但 Java 堆很小，怎么排查？
> **答题标杆**：这是典型的 Netty ByteBuf 或 NIO 直接缓冲区泄漏。排查步骤：
> 1. 启动参数开启 Native Memory Tracking：`-XX:NativeMemoryTracking=detail`，利用 `jcmd <PID> VM.native_memory baseline` 与 `detail.diff` 观察直接内存增量；
> 2. 针对 Netty 开启内存泄漏检测级别：`-Dio.netty.leakDetection.level=PARANOID`；
> 3. 日志会精准打印未被 `ReferenceCountUtil.release()` 释放的 ByteBuf 的原始分配调用栈，补充释放逻辑即可根治。
