# Java 项目实战：本章总结与复习

> [!abstract] 一句话总结
> 本章把秒杀、短链、订单履约、微服务治理和 JVM 排障组织成可落地的实战蓝图，统一要求从最小闭环出发，用失败注入、指标、日志、压测与一致性检查把“会设计”变成“有证据可复现”。

| --- | --- | --- | --- |

| 短链服务 | 短码生成、低延迟跳转、缓存、防刷与容量规划 | 创建短链 -> Redis/DB 解析 -> 302 -> 异步统计；命中率、回源比例、冲突次数、热点 P95 | [[02-项目-短链服务]] |

## 快速复习

1. 每个实战都遵循同一验收口径：有运行入口和成功链路，有数据/依赖说明，有失败路径，有量化指标，也有可重放的日志、命令或脚本证据。
2. 秒杀项目不是“Redis + MQ”组合展示，而是证明入口不会打穿 DB、固定库存不会超卖、重复用户最多一单、MQ/消费/关单异常最终可补偿。
3. 秒杀正确性依靠多层防线：Redis Lua 原子预扣和已购标记负责快速裁流，`requestId` 与数据库唯一索引负责幂等，状态条件更新处理支付/关单竞态，Outbox、DLQ 和对账负责恢复。
4. 短链项目的主链是创建与跳转分离：号段/雪花 ID 经 Base62 生成短码，跳转优先 Redis，miss 回源并防穿透，302 后异步记录访问；验收重点是命中率、回源比、热点延迟和风控。
5. 订单履约项目以状态机为骨架。订单、状态日志和 Outbox 在本地事务中一致，支付回调和关单靠 `WAIT_PAY` 条件更新互斥，库存、履约与退款通过幂等消息、补偿任务和人工队列收敛。
6. 治理脚手架要证明“新服务能按规范接入”和“故障不会无声扩散”：注册发现、动态配置、Gateway、限流熔断、日志与 Trace 要能被一次慢响应/报错故障串联验证。
7. JVM 排障按现象选证据：CPU 高用 `top -H`、`jstack`、Arthas；堆高用 GC 日志、`jmap`、heap dump；堆不高但 RSS 高查 NMT/Direct Memory；阻塞查死锁与锁竞争；慢接口用 `trace` 拆耗时。
8. JVM 故障的闭环是“现象 -> 命令 -> 证据 -> 根因 -> 修复 -> 复验”，调大堆、重启实例或背一组命令都不能代替根因证据。
9. 项目证据应能回答取舍：为什么异步、为什么用 302、为什么不用分布式大事务、为什么某层只重试一次、为什么某个指标能证明修复有效。
10. 当前最重要的推进方式是逐个完成未勾选开发任务，并把计划中的 QPS/P99、命中率、MQ lag、补偿成功率、线程栈和一致性 SQL 变成真实结果，而不是继续扩充架构名词。

## 自测问题

1. 秒杀固定库存 1000、并发请求 10000 时，你会采集哪些指标和 SQL，怎样证明无超卖、无重复用户且失败资格已正确回补？
2. 短链跳转命中率突然下降并拖慢 MySQL 时，如何区分正常过期、缓存穿透、热点失效和恶意扫描？修复后用什么数据复验？
3. 支付成功但订单未发货时，如何沿订单状态日志、Outbox、MQ、消费者幂等记录、履约单和补偿任务还原链路？
4. `stock-service` 慢响应导致订单接口 P99 上升时，脚手架中的 timeout、限流、熔断、降级、Trace 和动态配置应分别提供什么证据？
5. 应用 CPU 90% 但 GC 正常时，如何从热点线程定位到 Java 方法？若 CPU 来自 GC，证据会有什么不同？
6. 选择任一项目，能否用一分钟说清场景约束、核心设计、一次失败注入、定位证据、修复动作和复验结果？其中哪些目前仍只是计划？
