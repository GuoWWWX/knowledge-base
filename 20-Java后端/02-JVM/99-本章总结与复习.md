# JVM：本章总结与复习

> [!abstract] 一句话心智模型
> JVM 是一个**全自动化、具备自我保护与自愈能力的现代工业园区**：
> - **空间**：堆内分代运转，堆外元空间与保税区（直接内存）零拷贝直通；
> - **制造**：对象严格经历类加载检查、TLAB 极速无锁分配、零值初始化、对象头赋能与构造函数装配；
> - **清扫**：可达性分析判定生死，8:1:1 标记-复制整洁无碎片，三色标记与写屏障杜绝漏标；G1 棋盘格软实时掌控停顿，ZGC 染色指针与读屏障自愈实现亚毫秒极限并发；
> - **执行**：JIT 分层编译让热点代码从解释执行蜕变为媲美 C++ 的纯机器码，标量替换让对象根本无需入堆；
> - **运维**：证据链驱动排障，掌握 CPU 100% 抓凶、堆 Dump 分析与 OOM 急救 SOP。

## 🗺️ 工业园区心智模型全景对照表

| 工业园区概念 | JVM 核心组件 | 物理归属与生命周期 | 核心机制与关键参数 |
| :--- | :--- | :--- | :--- |
| **物料生产大车间** | **堆内存 (Heap)** | 线程共享，伴随 JVM 进程 | `-Xms` / `-Xmx`，弱分代假说，Eden:S0:S1=8:1:1，TLAB 无锁快速分配。 |
| **工人个人工位** | **虚拟机栈 (Stack)** | 线程私有，伴随线程生命周期 | `-Xss`，栈帧（局部变量表 Slot、操作数栈、动态链接、方法返回），天然线程安全。 |
| **工人工序进度指针** | **程序计数器 (PC)** | 线程私有 | 记录下一条字节码行号地址，CPU 轮转恢复上下文。**唯一不抛 OOM 的区域**。 |
| **中央档案与图纸库** | **元空间 (Metaspace)** | 线程共享，置于操作系统本地内存 | `-XX:MetaspaceSize` / `-XX:MaxMetaspaceSize`，存放类元数据、常量池。废除永久代根治 OOM。 |
| **保税区专用码头** | **直接内存 (Direct Memory)** | 堆外物理内存 | `-XX:MaxDirectMemorySize`，NIO / Netty 零拷贝，DirectByteBuffer 通过虚引用 Cleaner 清理。 |
| **图纸防伪与审核处** | **类加载子系统 (ClassLoader)** | 运行时动态加载 | 加载 -> 验证 -> 准备 -> 解析 -> 初始化 `<clinit>`。**双亲委派（啃老机制）**防篡改。 |
| **数控机床与优化专家** | **JIT 即时编译器** | 执行引擎核心 | 分层编译（C1/C2），热点探测计数器，方法内联，逃逸分析（标量替换、锁消除）。 |
| **网格化智能清扫队** | **G1 收集器** | 垃圾收集器 (JDK 9+ 默认) | 2048 个 Region，RSet 解决跨区引用，SATB 防漏标，`-XX:MaxGCPauseMillis=200` 软实时预测。 |
| **量子传送自愈清扫队**| **ZGC 收集器** | 下一代超低延迟 (JDK 17+ 生产就绪) | 染色指针（地址内嵌标记）+ 读屏障自愈（转发表），全阶段并发整理，STW < 1ms。 |

## ⚡ 大厂面试必杀 10 连问（第一性原理直击要害）

> [!question]- Q1：为什么新生代 Eden 与两个 Survivor 的比例设计为 8:1:1？
> 基于**弱分代假说**的大量统计，Java 90% 以上的对象“朝生夕灭”，经历 Minor GC 存活率通常低于 10%。为了使用零碎片的“标记-复制算法”，划分两块 Survivor 轮流作为中转站（一块使用、一块保持全空备用），8:1:1 既保证了全代高达 90%（80%+10%）的极高空间利用率，又刚好能完整容纳下 10% 的存活幸存者。

> [!question]- Q2：为什么对象分代年龄最大只能是 15？
> 这是底层物理存储限制！在 64 位 HotSpot 的对象头 Mark Word 中，用于记录对象 GC 年龄的比特位**仅仅分配了 4 个 bit**。4 位无符号二进制数的最大值是 $2^4 - 1 = 15$（二进制 `1111`）。无论参数怎么配，物理上都放不下 16。

> [!question]- Q3：高并发下大量线程在 Eden 区分配对象，如何保证并发安全且不发生严重锁竞争？
> 依靠 **TLAB（Thread Local Allocation Buffer，线程本地分配缓冲区）**。JVM 在 Eden 区为每个线程预先分配一块独占的小内存。线程创建对象时直接在各自的 TLAB 内部通过“指针碰撞”无锁极速分配；只有当前 TLAB 用完需要申请新 TLAB 时，才使用 CAS 锁与全局 Eden 指针交互一次。

> [!question]- Q4：为什么堆内存大小不能随意设置成 33GB？
> 因为 **指针压缩（Compressed OOPs）在超过 32GB 时强制失效**！JVM 利用 8 字节对齐（末尾三位为 0）的数学特性，将 32 位指针左移 3 位，刚好能寻址 $2^{32} \times 8 = 32\text{GB}$ 内存。一旦设置 `-Xmx33g`，指针压缩失效，所有对象引用从 4 字节膨胀到 8 字节，导致可用对象容量反而比 31GB 时缩水近 20%！

> [!question]- Q5：三色标记法中的“并发漏标”是如何发生的？如何解决？
> - 漏标发生在“黑色对象新插入了指向白色对象的引用”同时“灰色对象断开了对该白色对象的引用”，导致活着的白色对象永远无法被扫描到，最终被误杀！
> - 解决机制依靠**写屏障**：CMS 采用**增量更新**（记录新插入引用的黑色对象并将其变灰，重新标记 STW 时重扫）；G1 采用**原始快照 SATB**（在灰色断开引用的一瞬间保存旧引用，仍按并发标记开始时的快照扫完该白色对象）。

> [!question]- Q6：G1 的 Garbage-First 到底体现在哪里？
> G1 打破固定物理分代，将堆切为 2048 个 Region。G1 会根据历史回收收益和耗时建立动态预测模型。在用户设定的期望停顿时间（如 200ms）内，**优先挑选垃圾最多、回收空间性价比最高的 Region 组合进行回收**，故称 Garbage-First。

> [!question]- Q7：ZGC 凭什么做到 16TB 超大堆依然把停顿时间控制在 1ms 以内？
> ZGC 依靠 **染色指针（Colored Pointers）**（标记信息直接写入 64 位指针地址本身）和 **读屏障（Load Barrier）+ 指针自愈**。传统收集器最耗时的是对象搬迁与引用更新阶段，ZGC 将其全部转化为并发执行。业务线程读取正在搬迁的对象时，读屏障拦截并查询转发表，顺手原地更新栈上指针为新地址（自愈），全流程几乎无需 STW 挂起业务。

> [!question]- Q8：双亲委派机制是什么？Tomcat 为什么要打破它？
> - 双亲委派是类加载器在加载类时，优先委托父加载器加载，父加载器搞不定才由自己加载，核心目的是**保证 Java 核心类库的唯一性与防篡改安全性**。
> - Tomcat 打破双亲委派是为了**多应用类版本隔离**。同一 Tomcat 容器下部署两个应用，分别依赖 Spring 4 和 Spring 5，若按双亲委派委托给 AppClassLoader 会导致全局只能存在一个版本而冲突。Tomcat 的 `WebappClassLoader` 采用 Child-First 策略，优先加载应用自身的 `/WEB-INF/classes` 和 `/WEB-INF/lib`，实现容器隔离。

> [!question]- Q9：生产 Docker/K8s 容器环境下，Java 进程频繁报 Exit Code 137 是什么原因？
> 容器被 Linux 内核的 **OOM Killer 强杀（SIGKILL，kill -9）**！原因在于容器真实占用内存（RSS）不仅包含 `-Xmx` 堆内存，还包含元空间、线程栈（每个 1MB）、直接内存和 JVM 自身 C++ 内存。如果把 `-Xmx` 设得接近容器 limit，总内存瞬间超标。正确做法是配置 `-XX:+UseContainerSupport` 并使用 `-XX:MaxRAMPercentage=75.0`，为堆外预留 25% 安全缓冲空间。

> [!question]- Q10：Java 对象一定是在堆上分配的吗？
> **不一定**！通过 JIT 编译器的**逃逸分析（Escape Analysis）**，如果确定一个对象的作用域不会逃出当前方法，JIT 会执行**标量替换（Scalar Replacement）**，将该对象打散成若干个基本数据类型的局部变量直接保存在栈帧的局部变量表或寄存器中，根本不需要在堆上分配，完全不产生 GC 压力！

## 📜 生产排查与规约十诫（血泪经验总结）

1. **【堆大小对齐】**：生产环境云主机上，`-Xms` 必须与 `-Xmx` 设置为完全一致，杜绝任何运行期内存扩容与收缩导致的系统调用抖动。
2. **【容器预留缓冲】**：K8s 容器中禁止将 `-Xmx` 设满容器 limit，必须使用 `-XX:MaxRAMPercentage=75.0` 为堆外预留 25% 空间，防范 Exit Code 137 暴毙。
3. **【保留作案现场】**：所有生产实例**强制开启** `-XX:+HeapDumpOnOutOfMemoryError` 并指定持久盘路径 `-XX:HeapDumpPath=/data/logs/`，这是 OOM 现场破案的唯一真凭实据。
4. **【日志滚动归档】**：开启统一 GC 滚动日志，限制单个文件 100MB、保留 5 个文件，杜绝把磁盘打满。
5. **【禁止大堆盲目 dump】**：在几十 G 的大堆线上节点上，严禁在高峰期执行 `jmap -dump` 或 `jmap -histo:live`，这会触发全局 Full GC 和严重 STW 卡死服务！应在低峰期、摘流后或利用从节点执行。
6. **【ThreadLocal 必清】**：使用 ThreadLocal 必须在 `finally` 块中显式执行 `remove()`，防范线程池核心线程长期存活导致 Value 内存泄漏。
7. **【直接内存必放】**：使用 Netty ByteBuf，业务终点必须显式调用 `ReferenceCountUtil.release()` 释放堆外直接内存。
8. **【SQL 必带分页】**：任何后台查询和报表导出，SQL 必须强制加 `LIMIT`，严禁将数十万条数据全量加载入堆内存 List 中。
9. **【动态代理加缓存】**：使用 CGLIB、Javassist 或 Groovy 动态脚本解析时，必须复用类加载器或开启类缓存，防止元空间无节制溢出。
10. **【Arthas 谨慎使用】**：线上使用 Arthas 的 `watch` 或 `trace` 命令时，高频接口**必须附加过滤条件**（如 `'#cost > 200'`），严禁无条件抓取导致大量序列化开销压垮生产。
