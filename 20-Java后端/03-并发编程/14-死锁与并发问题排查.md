## 🔒 什么是死锁（Deadlock）？

死锁是指**两个或两个以上的线程在执行过程中，因争夺互斥资源而造成的一种互相等待的僵局（Frozen State）**。

其本质在于形成了**资源循环等待闭环（Circular Wait）**：线程 1 持有锁 A 并请求锁 B，同时线程 2 持有锁 B 并请求锁 A。在没有外部干预的情况下，双方互不相让，线程被永久阻塞，导致业务链路彻底停滞。

## 💥 亲手写一个 100% 触发的死锁代码

保存为 `DeadLockDemo.java`：

```java
public class DeadLockDemo {
    private static final Object LOCK_A = new Object();
    private static final Object LOCK_B = new Object();

    public static void main(String[] args) {
        System.out.println("========== 死锁演示程序已启动 ==========");
        System.out.println("提示：两个线程即将互相死锁，进程将保持停滞以供排查。");

        // 线程 1：先拿 A，睡眠后尝试拿 B
        new Thread(() -> {
            synchronized (LOCK_A) {
                System.out.println("【Deadlock-Thread-1】已锁定资源 A，准备获取资源 B...");
                sleep(200); // 确保让线程 2 先拿到锁 B
                synchronized (LOCK_B) {
                    System.out.println("【Deadlock-Thread-1】顺利拿到资源 B！");
                }
            }
        }, "Deadlock-Thread-1").start();

        // 线程 2：先拿 B，睡眠后尝试拿 A（顺序完全相反！）
        new Thread(() -> {
            synchronized (LOCK_B) {
                System.out.println("【Deadlock-Thread-2】已锁定资源 B，准备获取资源 A...");
                sleep(200); // 确保让线程 1 先拿到锁 A
                synchronized (LOCK_A) {
                    System.out.println("【Deadlock-Thread-2】顺利拿到资源 A！");
                }
            }
        }, "Deadlock-Thread-2").start();
    }

    private static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException ignored) {}
    }
}
```

### 🛠️ 本地动手实操排查（完整命令与实测步骤）

按照以下步骤在终端中动手跑一次，亲身体验线上死锁抓凶手：

#### 第 1 步：编译并在当前终端启动
```bash
javac DeadLockDemo.java
java DeadLockDemo
```
终端会输出两行准备获取日志后**永久停滞（死锁发生）**，不要关闭该窗口。

#### 第 2 步：打开第二个终端窗口，找到进程号 PID
```bash
jps -l
```
输出示例（找到 `DeadLockDemo` 前面的数字，例如 `9380`）：
```text
9380 DeadLockDemo
11628 jdk.jcmd/sun.tools.jps.Jps
```

#### 第 3 步：执行 `jstack` 抓取死锁诊断报告
```bash
jstack 9380
```
直接翻到输出内容的**最底部**，JVM 会自动输出死锁分析报告（见下文详解）。

#### 第 4 步：实验完毕，在终端中终止测试进程
- **Windows**：`taskkill /F /PID 9380`
- **Linux / macOS**：`kill -9 9380`
- 或在第 1 步运行的终端直接按 `Ctrl + C`。

## 🛡️ 死锁的 4 大必要条件与化解之道

计算机科学家早已证明：**死锁必须同时满足以下 4 个条件，只要打破其中任何 1 个，死锁就会灰飞烟灭！**

| 必要条件 | 含义 | 如何打破它？（化解招数） |
| :--- | :--- | :--- |
| **1. 互斥条件** | 资源只能一人独占（锁的本性） | 锁本身就是为了互斥，通常无法打破。 |
| **2. 请求与保持** | 自己霸占着锁 A，还贪婪地申请锁 B | **一次性申请全部资源**，或者拿不到第二把锁时主动释放第一把锁（用 `ReentrantLock.tryLock()`）。 |
| **3. 不可剥夺** | 别人手里的锁，你不能强行抢过来 | 采用支持中断退出的显式锁（`lockInterruptibly()`）。 |
| **4. 循环等待** | A 等 B，B 等 A（形成环形依赖） | **🌟 最核心招数：按统一顺序加锁！**（所有人都必须“先拿 A，再拿 B”，绝不许逆序加锁！）。 |

### 💡 生产经典：转账业务防死锁（按账号排序）
两个人互相转账时（A 给 B 转，同时 B 给 A 转），如果各自锁自己的账户就会死锁！
**解法：根据账号的主键 ID 大小排序！**
```java
Account firstLock = fromAccount.getId() < toAccount.getId() ? fromAccount : toAccount;
Account secondLock = fromAccount.getId() < toAccount.getId() ? toAccount : fromAccount;

// 所有人按相同的升序顺序加锁，绝无形成环状死锁的可能！
synchronized (firstLock) {
    synchronized (secondLock) {
        // 执行转账事务
    }
}
```

## 🚨 线上三大紧急险情排查 SOP

### 场景一：接口死锁排查（5 秒抓出元凶）

如果线上服务卡死，怀疑发生死锁：
1. 查看 Java 进程 PID：`jps -l`
2. 输出线程堆栈：`jstack <PID>` 或 `jcmd <PID> Thread.print`
3. **直接拉到输出内容的最底部**！JVM 内置了死锁检测算法，会直接打印诊断结论：

```text
Found one Java-level deadlock:
=============================
"Deadlock-Thread-1":
  waiting to lock monitor 0x000001df4b5b4e00 (object 0x00000007138090b8, a java.lang.Object),
  which is held by "Deadlock-Thread-2"

"Deadlock-Thread-2":
  waiting to lock monitor 0x000001df4b5b4800 (object 0x00000007138090a8, a java.lang.Object),
  which is held by "Deadlock-Thread-1"

Java stack information for the threads listed above:
===================================================
"Deadlock-Thread-1":
        at DeadLockDemo.lambda$main$0(DeadLockDemo.java:50)
        - waiting to lock <0x00000007138090b8> (a java.lang.Object)
        - locked <0x00000007138090a8> (a java.lang.Object)
        at java.lang.Thread.runWith(java.base@21.0.6/Thread.java:1596)
        at java.lang.Thread.run(java.base@21.0.6/Thread.java:1583)

"Deadlock-Thread-2":
        at DeadLockDemo.lambda$main$1(DeadLockDemo.java:61)
        - waiting to lock <0x00000007138090a8> (a java.lang.Object)
        - locked <0x00000007138090b8> (a java.lang.Object)
        at java.lang.Thread.runWith(java.base@21.0.6/Thread.java:1596)
        at java.lang.Thread.run(java.base@21.0.6/Thread.java:1583)
```
**看这一段诊断结论：**
1. 上半部分直白指出：`Deadlock-Thread-1` 在等被 `Deadlock-Thread-2` 持有的锁；反之亦然。
2. 下半部分精准定位到代码行号：`DeadLockDemo.java:50` 和 `DeadLockDemo.java:61`，凶手和作案现场当场被抓个现行！

### 场景二：生产 CPU 飙高 100% 排查（经典四步定位法）

服务器报警 CPU 100% 满负荷运转，多半是多线程死循环、或 CAS 空转、或频繁 Full GC 导致：

```mermaid
flowchart LR
    A["1. top 找进程 PID"] --> B["2. top -Hp 找线程 TID"]
    B --> C["3. printf 转 16 进制"]
    C --> D["4. jstack 定位代码行"]
```

| 步骤 | 执行命令示例 | 核心职责 |
| :--- | :--- | :--- |
| **1. 找进程** | `top` | 找出占用 CPU 最高的 Java 进程 PID（如 `8888`） |
| **2. 找线程** | `top -Hp 8888` | 找出该进程下消耗 CPU 最高的具体线程 TID（如 `8899`） |
| **3. 转进制** | `printf "%x\n" 8899` | 将十进制线程 ID 转为十六进制（如 `0x22c3`），对应 JVM 的 `nid` |
| **4. 抓代码** | `jstack 8888 \| grep -A 20 0x22c3` | 从线程栈中精准过滤并定位到具体出问题的代码行数 |

> 🌟 **极速神器：Arthas（阿里开源阿尔萨斯）**
> 生产环境装了 Arthas，只需一条命令秒杀：
                    > ```bash
> thread -n 3
> ```
> Arthas 会直接列出当前占用 CPU 最高的前 3 个线程及其完整调用栈，一秒抓出罪魁祸首！

### 场景三：线程池被打满，狂抛拒绝异常（RejectedExecutionException）

- **现象**：大批用户报错，日志里不断刷 `RejectedExecutionException`。
- **排查方向**：
  1. 绝大部分情况**不是并发数太高，而是下游变慢了！**
  2. 检查当前活跃线程在干什么：打印线程栈，看这些线程是不是都卡在某一个慢 SQL、或者调用某个无响应的第三方 HTTP 接口处；
  3. **解法**：立刻给所有外部 I/O 调用加上严格的 **ConnectTimeout 和 ReadTimeout 超时时间**；核心链路做熔断降级（Sentinel / Resilience4j）。
