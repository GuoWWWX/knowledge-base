## 🔒 核心心智模型：独木桥上的两个人（死锁）

现实中最经典的死锁场景：

> - **张三** 拿着家门钥匙，想进卧室；但李四把卧室门反锁了，在里面等家门钥匙。
> - **李四** 拿着卧室钥匙，想出门；但张三把大门反锁了，在门外等卧室钥匙。
> - 两个人互不相让，谁也不肯先交出钥匙，结果双双在屋里屋外冻死！

## 💥 亲手写一个 100% 触发的死锁代码

保存为 `DeadLockDemo.java`：

```java
public class DeadLockDemo {
    private static final Object LOCK_A = new Object();
    private static final Object LOCK_B = new Object();

    public static void main(String[] args) {
        // 线程 1：先拿 A，再拿 B
        new Thread(() -> {
            synchronized (LOCK_A) {
                System.out.println("线程 1：已锁定资源 A，准备获取资源 B...");
                sleep(100); // 故意睡一下，让线程 2 先拿到 B
                synchronized (LOCK_B) {
                    System.out.println("线程 1：顺利拿到资源 B！");
                }
            }
        }, "Deadlock-Thread-1").start();

        // 线程 2：先拿 B，再拿 A（顺序相反！）
        new Thread(() -> {
            synchronized (LOCK_B) {
                System.out.println("线程 2：已锁定资源 B，准备获取资源 A...");
                sleep(100);
                synchronized (LOCK_A) {
                    System.out.println("线程 2：顺利拿到资源 A！");
                }
            }
        }, "Deadlock-Thread-2").start();
    }

    private static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException ignored) {}
    }
}
```

### 运行现象：
程序打印出两行准备获取之后，**永久停滞，既不退出也不报错，进入死锁！**

## 🛡️ 死锁的 4 大必要条件与化解之道

计算机科学家早已证明：**死锁必须同时满足以下 4 个条件，只要打破其中任何 1 个，死锁就会灰飞烟灭！**

| 必要条件 | 含义 | 如何打破它？（化解招数） |
| :--- | :--- | :--- |
| **1. 互斥条件** | 资源只能一人独占（锁的本性） | 锁本身就是为了互斥，通常无法打破。 |
| **2. 请求与保持** | 自己霸占着锁 A，还贪婪地申请锁 B | **一次性申请全部资源**，或者拿不到第二把锁时主动释放第一把锁（用 `ReentrantLock.tryLock()`）。 |
| **3. 不可剥夺** | 别人手里的锁，你不能强行抢过来 | 采用支持中断退出的显式锁（`lockInterruptibly()`）。 |
| **4. 循环等待** | A 等 B，B 等 A（形成环形依赖） | **🌟 最核心招数：按统一顺序加锁！**（所有人都必须“先拿 A，再拿 B”，绝不许逆序加锁！）。 |

### 💡 生产经典：转账业务防死锁（按账号排序）
两个人互相转账时（A 给 B 转，同时 B 给 A 转），如果各自锁自己的账户就会死锁！
**解法：根据账号的主键 ID 大小排序！**
```java
Account firstLock = fromAccount.getId() < toAccount.getId() ? fromAccount : toAccount;
Account secondLock = fromAccount.getId() < toAccount.getId() ? toAccount : fromAccount;

// 所有人按相同的升序顺序加锁，绝无形成环状死锁的可能！
synchronized (firstLock) {
    synchronized (secondLock) {
        // 执行转账事务
    }
}
```

## 🚨 线上三大紧急险情排查 SOP

### 场景一：接口死锁排查（5 秒抓出元凶）

如果线上服务卡死，怀疑发生死锁：
1. 查看 Java 进程 PID：`jps -l`
2. 输出线程堆栈：`jstack <PID>` 或 `jcmd <PID> Thread.print`
3. **直接拉到输出内容的最底部**！JVM 内置了死锁检测算法，会直接打印诊断结论：

```text
Found one Java-level deadlock:
=============================
"Deadlock-Thread-1":
  waiting to lock monitor 0x000002... (object 0x..., a java.lang.Object)
  which is held by "Deadlock-Thread-2"
"Deadlock-Thread-2":
  waiting to lock monitor 0x000001... (object 0x..., a java.lang.Object)
  which is held by "Deadlock-Thread-1"

Java stack information for the threads listed above:
===================================================
"Deadlock-Thread-1":
        at DeadLockDemo.lambda$main$0(DeadLockDemo.java:12)
        - waiting to lock <0x...B>
        - locked <0x...A>
```
**看这一段，不仅指出了死锁的线程名字，连代码在哪一行互相等锁都清清楚楚！**

### 场景二：生产 CPU 飙高 100% 排查（经典四步定位法）

服务器报警 CPU 100% 满负荷运转，多半是多线程死循环、或 CAS 空转、或频繁 Full GC 导致：

```mermaid
flowchart LR
    S1["1. top<br/>找到最耗 CPU 的 Java 进程 PID (如 8888)"] --> S2["2. top -Hp 8888<br/>找出该进程下吃 CPU 的具体线程 TID (如 8899)"]
    S2 --> S3["3. printf '%x\n' 8899<br/>把线程 ID 转成 16 进制 (如 0x22c3)"]
    S3 --> S4["4. jstack 8888 | grep -A 20 0x22c3<br/>精准定位到具体代码行数！"]
```

> 🌟 **极速神器：Arthas（阿里开源阿尔萨斯）**
> 生产环境装了 Arthas，只需一条命令秒杀：
> ```bash
> thread -n 3
> ```
> Arthas 会直接列出当前占用 CPU 最高的前 3 个线程及其完整调用栈，一秒抓出罪魁祸首！

### 场景三：线程池被打满，狂抛拒绝异常（RejectedExecutionException）

- **现象**：大批用户报错，日志里不断刷 `RejectedExecutionException`。
- **排查方向**：
  1. 绝大部分情况**不是并发数太高，而是下游变慢了！**
  2. 检查当前活跃线程在干什么：打印线程栈，看这些线程是不是都卡在某一个慢 SQL、或者调用某个无响应的第三方 HTTP 接口处；
  3. **解法**：立刻给所有外部 I/O 调用加上严格的 **ConnectTimeout 和 ReadTimeout 超时时间**；核心链路做熔断降级（Sentinel / Resilience4j）。
