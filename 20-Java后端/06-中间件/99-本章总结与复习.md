# 中间件：本章总结与复习

> [!abstract] 一句话心智模型
> 中间件是分布式架构的**基建血脉与安全防线**：
> - **异步与缓冲（MQ）**：Kafka 用 PageCache、顺序写与 `sendfile` 零拷贝支撑海量日志；RocketMQ 用 CommitLog 物理大一统顺序写与二阶段半消息打通金融级事务；
> - **注册与调度（Nacos）**：从 1.x 短轮询升级到 2.x gRPC 双向长连接，坚守 AP 模式的高可用可用性红线，以保护阈值抵御雪崩；
> - **动态政令（配置中心）**：以长轮询（Long Polling）MD5 挂起机制兼顾秒级实时与轻量，依靠 `@RefreshScope` 丢弃旧 Bean 缓存实现运行时无感热更新；
> - **海关大门（API 网关）**：基于 Reactor 响应式非阻塞 EventLoop 模型，辅以 Redis 分布式令牌桶精准应对突发洪峰；
> - **立体缓冲（多级缓存）**：Caffeine 本地微秒直取抗单点热点，Redis 集群抗跨节点共享，Canal 监听 Binlog 广播保障最终一致。

| **服务注册与发现** | **Nacos Discovery** | 2.x 基于 gRPC 双向长连接流、Distro 协议（AP 临时节点无主集群）、客户端本地持久化容灾快照。 | 容器部署必须同时对外映射暴露 `8848`（HTTP）与 `9848`（gRPC）端口；设置保护阈值防抖动雪崩。 | 类比为动态服务通讯录与健康检查黄页 |
| **动态配置中心** | **Nacos Config** | 30 秒长轮询（Long Polling）挂起唤醒、MD5 指纹比对、`@RefreshScope` 作用域缓存清空惰性重建。 | 生产环境严格按 Namespace 划分环境隔离；客户端本地缓存防范配置中心服务端单点宕机。 | 类比为集群参数指令的集中广播发布中枢 |

| **高性能多级缓存** | **多级缓存体系** | Caffeine 堆内纳秒直取 + Redis 集群共享 + Canal 监听 MySQL Binlog 异步广播失效。 | 必须保证 Canal 异步失效能清理所有 Pod 本地 Caffeine；突发热点 HotKey 需毫秒级热探测并推入本地内存兜底。 | 类比为本地极速货架与共享主仓储结合 |

## ⚡ 大厂面试必杀 10 连问（精准金句提炼）

> [!question]- Q1：Kafka 为什么读写吞吐量如此恐怖？
> 四大底层黑科技：① **磁盘顺序追加写**，利用顺序 I/O 避免机械寻道，写入速度堪比内存；② **操作系统 PageCache**，消息优先走内核页缓存，完全不占 JVM 堆，零 GC 负担；③ **Linux `sendfile` 零拷贝**，数据直接从内核缓冲区走 DMA 拷贝到网卡，消除了 CPU 拷贝与多余的上下文切换；④ **客户端批量累积与压缩**，极大节省网络带宽与磁盘 I/O。

> [!question]- Q2：RocketMQ 的底层存储设计为什么比 Kafka 更能抗海量 Topic？
> Kafka 每一个 Partition 对应一个独立的物理文件，Topic 上千时，数万个文件并发读写退化为严重的磁盘随机 I/O。而 RocketMQ 采用**CommitLog 大一统存储**，所有 Topic 的消息不分彼此顺序追加写入同一个 1GB 物理文件中，磁盘永远保持单文件纯粹顺序写；每个队列仅维护固定 20 字节的微型索引 **ConsumeQueue**，几乎全部命中内存 PageCache。

> [!question]- Q3：RocketMQ 的二阶段事务消息是如何实现的？
> 1. 生产端先发 Half Message（半消息），Broker 改存到内部专用主题，下游消费者不可见；
> 2. 生产端开始执行本地数据库事务；
> 3. 本地事务成功则向 Broker 发送 Commit，使消息对下游可见；失败发送 Rollback 抛弃；
> 4. 若 Commit/Rollback 途中网络中断或进程崩溃，Broker 超时后会**主动向生产者集群发起本地事务状态回查**，根据查询结果做出最终 Commit 或 Rollback 裁决。

> [!question]- Q4：在消息队列中，如何确保一条消息“绝不丢失”？
> 端到端三方联合防线：
> - **生产端**：开启同步发送并检查返回的 ACK，配置 `retries > 3` 失败重试；
> - **Broker 端**：配置多副本强同步（Kafka `acks=all + min.insync.replicas=2`，RocketMQ 同步双写 `SYNC_MASTER`）；
> - **消费端**：关闭自动提交（`enable.auto.commit=false`），必须在本地业务逻辑完全执行无误且数据库事务落库成功后，才手动提交消费位点。

> [!question]- Q5：为什么分布式消息几乎无法保证 Exactly-Once？消费端如何实现幂等？
> - 因为网络两将军问题，网络超时重试必定会导致消息重复投递，所以 MQ 只能保证 At Least Once。
> - 幂等由消费端业务实现：① **状态机前置拦截**（如 `where status = 'UNPAID'`，更新行数为 0 则忽略）；② **数据库业务主键防重表**（利用全局唯一业务号如 `order_id` 建立唯一索引，重复插入抛冲突异常自动吞掉）；③ **分布式 Redis SETNX 拦截**。

> [!question]- Q6：生产环境突然积压了 2000 万条消息，如何紧急救火？
> - 核心原则：**如果 Topic 只有 4 个 Partition，盲目加 Consumer 毫无作用！**
> - 紧急方案：① 快速修复下游消费瓶颈，非核心业务降级；② 紧急申请一个拥有 30~50 个 Partition 的临时 Topic；③ 上线一组极简的临时中继程序，只负责将原积压消息批量轮询分发至临时 Topic；④ 部署 30~50 个真实的业务 Consumer 实例全并发消费临时 Topic，瞬间将消费吞吐拉大 10 倍泄洪！

> [!question]- Q7：Nacos 2.x 相比 1.x 做了什么重大重构？
> 1.x 基于 **HTTP 1.1 短轮询**，万级实例下频繁的 TCP 握手和心跳轮询给服务端造成沉重负担。2.x 全面升级为基于 **Netty + gRPC 的双向流长连接**，一个客户端一条长连接搞定心跳与多路复用，事件变更服务端主动毫秒级推送，连接数下降 90%，单集群性能支撑提升 10 倍。

> [!question]- Q8：Spring Cloud 中的 `@RefreshScope` 是如何实现动态刷新配置的？
> `@RefreshScope` 是一个自定义作用域，底层由 `GenericScope` 维护 Bean 缓存。当配置中心推送变更触发刷新事件时，Spring 执行 `scope.destroy()` **清空该 Scope 缓存中的旧 Bean 实例**。当下次业务请求调用该 Bean 时，Spring 发现缓存为空，重新执行完整的创建生命周期并把最新的配置注入到新 Bean 中。

> [!question]- Q9：Spring Cloud Gateway 为什么性能远超 Zuul 1.x？写过滤器时最忌讳什么？
> - Zuul 1.x 基于 Servlet 阻塞 I/O，一个请求绑定一个线程，并发上限极低；Gateway 基于 **Spring 5、Project Reactor 和 Netty** 构建，采用**异步非阻塞的事件驱动模型（EventLoop）**，少数几个线程即可处理海量并发连接。
> - **最大禁忌**：**绝对严禁在 Gateway 过滤器中执行任何阻塞操作（如 `Thread.sleep()`、同步读 DB/Redis 等）**，否则会瞬间卡死 EventLoop 核心线程，导致整个网关入口全线瘫痪！

> [!question]- Q10：什么是热点 Key？线上遭遇热点 Key 该如何防范与自愈？
> - 热点 Key 是指瞬时遭遇数十万并发请求的单个 Key（如秒杀爆品）。因为单 Key 只能落在单个 Redis 节点上，会直接把单机的 CPU 和网卡带宽打爆。
> - **治理之道**：事前可增加随机后缀备份分流；事中接入 **Sentinel 或 HotKey 自动探测引擎**，在毫秒级识别出热点 Key，并将该数据**自动推送到所有微服务 Pod 的本地内存（Caffeine）中**，让 99% 的请求在各实例的 JVM 内存层直接短路返回，彻底化解打向 Redis 的流量。
