## 🔥 核心高频绝杀考题

### Q1: JMM（Java 内存模型）解决什么问题？Happens-Before 原则如何理解？
> **30 秒绝杀版**：
> JMM 是为了屏蔽不同操作系统与 CPU 硬件（x86/ARM）在内存访问上的物理差异，为 Java 开发者提供的一套跨平台并发规范。它抽象出“主内存”与“线程私有工作内存”，定义了变量的**可见性、有序性与原子性**。`Happens-Before` 是 JMM 面向开发者的逻辑契约：只要操作 A happens-before 操作 B，A 的修改就必定对 B 可见且有序。
>
> **2 分钟深度展开**：
> - **底层硬件矛盾**：CPU 有多级私有缓存（L1/L2/L3）与写缓冲区，且指令流水线会乱序重排，导致多核并发时出现数据不一致。
> - **八大 Happens-Before 核心规则**：
>   1. **程序次序规则**：同一个线程内，前面的代码 happens-before 后面的代码；
>   2. **监视器锁规则**：同一个锁的 `unlock()` 必定 happens-before 后续对该锁的 `lock()`；
>   3. **volatile 变量规则**：对一个 volatile 变量的写操作必定 happens-before 随后对该变量的读操作；
>   4. **传递性规则**：若 $A \text{ hb } B$ 且 $B \text{ hb } C$，则 $A \text{ hb } C$；
>   5. **线程启动与终止规则**：`Thread.start()` 先于子线程所有操作；子线程结束先于 `Thread.join()`。
> - **底层落地**：JMM 契约在底层是由 JVM 编译器在合适位置插入 **硬件内存屏障（LoadLoad / StoreStore / LoadStore / StoreLoad）** 兑现的。

### Q2: `volatile` 关键字的底层原理是什么？为什么单例模式 DCL 必须加 volatile？
> **30 秒绝杀版**：
> `volatile` 提供两大核心保障：**保证线程间可见性**、**禁止指令重排序**，但**绝不保证复合操作的原子性**（如 `count++` 依然非线程安全）。DCL 单例中，`new Singleton()` 包含“分配空间、初始化对象、引用赋值”三步，指令重排可能导致引用先赋值而对象未完成初始化，并发线程可能拿到半初始化的脏对象，必须加 volatile 彻底禁止重排！
>
> **2 分钟深度展开**：
> - **汇编级底层实现**：在对 volatile 变量进行写操作时，JIT 编译生成的汇编代码会多加一个 **`lock addl $0x0,(%esp)`** 前缀指令。
> - **CPU 硬件连锁反应**：
>   1. 立即将当前 CPU 核心写缓冲区（Store Buffer）中的数据**强行刷新回主存**；
>   2. 触发 **MESI 缓存一致性协议**，通过总线嗅探将其他 CPU 核心中该变量所在的缓存行（Cache Line）**强制置为 Invalid（失效）**；
>   3. 其他核心下次读取时被迫重新从主存拉取最新物理值，达成秒级可见。
> - **DCL 单例指令重排风险**：
>   ```text
>   步骤 1: memory = allocate();   // 分配内存
>   步骤 2: ctorInstance(memory);  // 执行构造方法初始化
>   步骤 3: instance = memory;      // 引用指向分配的地址
>   若重排为 1 -> 3 -> 2，当线程 A 执行完 3 尚未执行 2 时，线程 B 进来判断 instance != null，直接取走未初始化的对象使用，当场抛出空指针或数据错乱异常！
>   ```

### Q3: `synchronized` 底层如何实现？JDK 6 之后的“锁升级”全过程是怎样的？
> **30 秒绝杀版**：
> `synchronized` 是基于 JVM 底层管程（`Monitor`）实现的，编译后生成 `monitorenter` 和 `monitorexit` 字节码。JDK 6 引入自适应锁升级优化：**无锁 $\to$ 偏向锁 $\to$ 轻量级锁 $\to$ 重量级锁**，状态记录在对象头的 **Mark Word** 中，锁升级过程**单向不可逆**。
>
> **2 分钟深度展开**：
> - **四种锁状态演进路径**：
>   1. **无锁（001）**：无竞争。
>   2. **偏向锁（101，JDK 15后默认废弃）**：一段代码长期只被同一个线程访问，直接将该线程的 Thread ID 记入 Mark Word，后续该线程进出临界区无需任何 CAS 竞争，开销极低。
>   3. **轻量级锁（000）**：一旦发生多线程交替竞争，偏向锁撤销，升级为轻量级锁。线程在各自的栈帧中建立 **Lock Record（锁记录）**，尝试通过 **CAS** 将对象头的 Mark Word 替换为指向自身 Lock Record 的指针。成功即获得锁；
>   4. **重量级锁（010）**：若 CAS 自旋多次依然失败，或者有第三个线程竞争，轻量级锁升级为重量级锁。Mark Word 指针指向底层的 `ObjectMonitor`，未抢到锁的线程进入 `_EntryList` 队列并被操作系统内核 **挂起休眠（陷入用户态到内核态的繁重上下文切换）**。
> - **配套编译器优化**：
>   - **锁消除**：JIT 逃逸分析判定对象不可能逃逸出方法，自动消除锁（如方法内的局部 `StringBuffer`）；
>   - **锁粗化**：将一连串连续对同一对象的加解锁操作合并为一个更大的锁区间，避免频繁 CAS。

### Q4: 什么是 CAS？它有什么缺陷？`AtomicInteger` 和 `LongAdder` 怎么选？
> **30 秒绝杀版**：
> CAS（Compare-And-Swap）是无锁原子操作，底层对应 CPU 的 `cmpxchg` 汇编指令。三大缺陷：**ABA 问题**、**高并发自旋 CPU 100% 消耗**、**只能保证单个共享变量的原子性**。超高并发计数场景必须选 `LongAdder`，其通过**分段累加数组（Cell[]）**将锁竞争稀释数十倍，性能吊打 `AtomicInteger`。
>
> **2 分钟深度展开**：
> - **ABA 问题与解法**：变量从 A 变成 B 又变回 A，CAS 判定成功但实际被篡改过。解法：引入带版本号的 **`AtomicStampedReference`**（比对引用同时比对版本戳 stamp）。
> - **LongAdder 的分段设计哲学**：
>   - `AtomicLong` 是多个线程同时自旋 CAS 修改同一个 `volatile value`，并发越高失败率越高，CPU 白白浪费在自旋上；
>   - `LongAdder` 继承自 `Striped64`，采用**空间换时间**：内部维护一个 `base` 变量和一个 `Cell[]` 数组。当无竞争时直接更新 `base`；一旦发生竞争，根据当前线程的 HashCode 映射到不同的 `Cell` 槽位，各线程只原子累加自己的 Cell；最终读取 `sum()` 时遍历全部 Cell 求和，将热点彻底打散。

### Q5: AQS（AbstractQueuedSynchronizer）的底层原理是什么？独占锁和共享锁如何协同？
> **30 秒绝杀版**：
> AQS 是 JUC 的并发同步基石。核心架构是：**一个 `volatile int state` 同步状态量** + **一个基于双向链表的 CLH 变种阻塞队列**。获取锁失败的线程被封装成 `Node` 节点入队自旋，并通过 `LockSupport.park()` 精准阻塞；释放锁时通过 `unpark()` 唤醒后继节点。
>
> **2 分钟深度展开**：
> - **ReentrantLock 独占实现**：
>   - `state` 代表重入次数。0 代表未锁定，1 代表已被抢占。
>   - 线程抢锁执行 `compareAndSetState(0, 1)`；若当前线程正是锁持有者，执行 `state++`（实现可重入）。释放锁时 `state--`，直到 `state == 0` 才彻底解绑 ExclusiveOwnerThread。
> - **公平锁 vs 非公平锁的区别**：
>   - **非公平锁（默认）**：新线程进来直接调用 `CAS` 尝试插队抢锁；抢不到才执行 `acquire` 进入排队；
>   - **公平锁**：新线程进门必须先调用 `hasQueuedPredecessors()`，如果队列里已经有排队的前驱节点，必须老老实实去排队，严禁插队。
> - **读写锁（ReentrantReadWriteLock）的高低位复用**：
>   - 用一个 32 位的 `int state` 变量同时表达读写锁：**高 16 位表示读锁持有的总计数（共享），低 16 位表示写锁的重入次数（独占）**。

### Q6: 线程池的核心参数有哪些？任务提交流程是怎样的？生产如何配置参数？
> **30 秒绝杀版**：
> 七大核心参数：核心线程数、最大线程数、存活时间、时间单位、阻塞队列、线程工厂、拒绝策略。提交流程：**先看核心线程 $\to$ 核心满则进阻塞队列 $\to$ 队列满则启非核心线程至最大 $\to$ 达到最大且队列满触发拒绝策略**。严禁使用 `Executors` 快速创建，防止无界队列 OOM！
>
> **2 分钟深度展开**：
> - **四种标准拒绝策略**：
>   1. `AbortPolicy`（默认）：直接抛出 `RejectedExecutionException`；
>   2. `CallerRunsPolicy`：由**调用者所在的主线程**亲自同步执行该任务（天然限流降速）；
>   3. `DiscardPolicy`：静默丢弃，不报错；
>   4. `DiscardOldestPolicy`：丢弃队列头最老的任务，尝试重新提交。
> - **生产线程数配置黄金公式**：
>   - **CPU 密集型（复杂计算/加解密）**：$\text{核心数} + 1$（防止缺页中断）；
>   - **I/O 密集型（查数据库/远程RPC/HTTP）**：
>     $$\text{线程数} = \text{CPU核心数} \times \left(1 + \frac{\text{I/O 等待时间}}{\text{CPU 计算时间}}\right)$$
>     （通常按 $2N \sim 4N$ 预设，生产结合 DynamicTp / Hippo4j 实现**动态线程池调优与告警**）。

### Q7: `ThreadLocal` 为什么会引发内存泄漏？弱引用（WeakReference）到底背了黑锅吗？
> **30 秒绝杀版**：
> `ThreadLocalMap` 的 `Entry` 继承了 `WeakReference`，它的 **Key 是弱引用，而 Value 是强引用**。如果外部强引用断开且发生了 GC，Key 会变成 null，但与线程生命周期绑定的 Value 强引用无法被释放！在线程池长寿线程复用下，累积导致严重的内存泄漏。**弱引用不仅没背锅，反而让 JVM 能够通过 key == null 感知过期脏数据；根治的唯一铁律是使用完毕必须在 `finally` 块中显式执行 `remove()`！**
>
> **2 分钟深度展开**：
> - **强引用链条还原**：`Thread (长寿线程) -> ThreadLocalMap -> Entry -> Value (业务大对象)`。只要线程不退出，Value 永远可达。
> - **ThreadLocal 的启发式清理**：在调用 `get()`、`set()` 时，ThreadLocal 内部会顺带遍历清理掉部分 `key == null` 的脏 Entry，但这并不彻底。
> - **跨线程传递陷阱**：子线程无法读取父线程的 ThreadLocal；若需跨线程透传（如 TraceId），必须使用阿里开源的 **`TransmittableThreadLocal`（TTL）** 配合修饰后的线程池，在提交任务时克隆快照。

### Q8: `ConcurrentHashMap` 在 JDK 7 和 JDK 8 中的实现有什么本质不同？
> **30 秒绝杀版**：
> JDK 7 采用 **分段锁（Segment + ReentrantLock + HashEntry[]）**，最多支持 16 个并发写；JDK 8 彻底废弃 Segment，采用 **Node 数组 + CAS + synchronized 锁桶头节点 + 红黑树**，并发度从 16 飙升到数组长度（默认 16，随扩容增长至数千），锁粒度从“段”极致细化到了“槽位”。
>
> **2 分钟深度展开**：
> - **JDK 8 的并发控制细节**：
>   - **读操作**：完全无锁！利用 `volatile Node.val` 和 `volatile Node.next` 保证多线程读可见性；
>   - **写操作**：
>     1. 若桶为空，通过 **CAS** 无锁写入头节点；
>     2. 若桶非空，仅对**当前链表/红黑树的头节点加 `synchronized`**，仅阻塞命中同一个 Hash 槽位的并发线程；
>   - **协同扩容（ForwardingNode）**：当某线程写入时发现节点为 `MOVED`（Hash 为 -1），不仅不阻塞，反而**主动协助当前扩容线程一起迁移数据**（分段搬迁），极大地缩短了全表扩容的全局停顿时间。
