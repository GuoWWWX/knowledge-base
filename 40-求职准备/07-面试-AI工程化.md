# 面试-AI工程化

> [!abstract] 一句话总结
> AI 工程化的核心是把不稳定的大模型调用变成可评估、可观测、可限流、可降级、可回滚、可审计的生产系统。

## 🎯 回答框架

1. **先给结论**：AI 调用不是普通 RPC，输出不稳定、成本高、延迟长、风险大。
2. **展开治理**：结构化输出、评估集、Trace、限流、降级、缓存、安全、灰度。
3. **结合项目**：落到 RAG、Agent、MCP、Spring Boot 后端系统。
4. **补充取舍**：质量、成本、延迟、稳定性、安全之间要平衡。

## ✅ 上线前检查清单

| 类别 | 检查项 |
| ---- | ------ |
| 输入 | 参数校验、敏感词、权限上下文、Prompt 注入检测 |
| 输出 | JSON Schema、字段校验、置信度、拒答策略 |
| 模型 | 模型版本、超时、重试、fallback、限流 |
| RAG | 检索评估、引用溯源、权限过滤、索引版本 |
| Agent | 工具白名单、风险分级、人工审批、幂等审计 |
| 观测 | requestId、trace、token、latency、error、cost |
| 评估 | 离线评估集、badcase、回归阈值 |
| 发布 | 灰度、回滚、配置开关、降级方案 |

## 📊 可观测指标面板

| 指标 | 含义 | 作用 |
| ---- | ---- | ---- |
| QPS | AI 请求量 | 容量和限流 |
| P50/P95/P99 | 延迟 | 体验和瓶颈定位 |
| Error Rate | 错误率 | 稳定性告警 |
| Timeout Rate | 超时率 | 模型或工具故障 |
| Input/Output Tokens | token 使用 | 成本拆解 |
| Cost per Request | 单次成本 | 成本优化 |
| Cache Hit Rate | 缓存命中 | 降成本降延迟 |
| RAG Recall@K | 检索召回 | 知识库质量 |
| Faithfulness | 忠实度 | 幻觉控制 |
| Tool Success Rate | 工具成功率 | Agent 稳定性 |
| Human Handoff Rate | 人工接管率 | 风险控制 |

## 🔁 限流、熔断、重试、降级矩阵

| 问题 | 策略 | 注意点 |
| ---- | ---- | ------ |
| 模型超时 | 设置超时 + fallback | 不要无限等待 |
| 模型 5xx | 退避重试 | 限制次数，避免放大故障 |
| 模型限额 | 限流/排队/降级小模型 | 明确用户提示 |
| RAG 检索失败 | 降级为无知识库回答或拒答 | 不能假装有依据 |
| Rerank 失败 | 使用初召回排序 | 质量可能下降，要记录 |
| 工具失败 | 低风险重试，高风险转人工 | 保证幂等 |
| 成本过高 | 模型分层、缓存、压缩 Prompt | 用评估集验证质量 |

## 🚀 灰度发布与回滚

- Prompt 版本化：`prompt_name + version`。
- 模型版本化：记录模型 id、参数、temperature、topP。
- 检索策略版本化：chunk、embedding、TopK、rerank 参数要可回溯。
- 灰度人群：内部用户、低风险租户、小流量比例。
- 回滚策略：Prompt 回滚、模型回滚、检索参数回滚、关闭 Agent 工具自动执行。
- 对比指标：质量分、错误率、投诉率、P95、成本。


## 🧪 高频问题

### Q1: AI 应用上线前要做哪些工程化准备？

> 至少要有结构化输入输出、超时重试、限流降级、日志追踪、成本统计、评估集、安全拦截和回滚开关。AI 调用不是普通 RPC，输出不稳定，所以必须有验证、回退和人工兜底。

### Q2: 如何观测一次 LLM 调用链路？

> 记录 requestId、用户意图、Prompt 版本、模型、Token、延迟、工具调用、检索命中文档、最终结果和失败原因。RAG/Agent 项目里还要把检索、重排、生成、工具执行分段埋点。

### Q3: AI 应用成本过高怎么优化？

> 先用监控拆分成本来源，再按场景做模型分层、Prompt 压缩、缓存、批处理、检索 TopK 控制和失败重试收敛。不能只换便宜模型，要用评估集确认质量没有明显下降。

### Q4: 大模型输出 JSON 不稳定怎么办？

> 使用结构化输出或 JSON Schema，服务端做解析校验和重试修复；关键业务不要直接信任模型输出，必须经过规则校验和人工兜底。

### Q5: 如何做 AI 应用灰度？

> 按租户、用户、场景或流量比例灰度，同时版本化 Prompt、模型、检索参数和工具权限。观察质量、错误率、延迟、成本和人工接管率，异常时快速回滚。

### Q6: 如何处理 Prompt 注入？

> RAG 文档和用户输入都不可信。要做指令分层、资料包边界、工具权限控制、敏感操作审批和输出校验，不能只靠一句“忽略恶意指令”。

## 🎤 项目版回答

在企业知识库 RAG 项目里，我会把每次请求拆成 query rewrite、retrieve、rerank、prompt、generation 几段记录 trace，跟踪 Recall@K、Faithfulness、P95 和 token 成本。在业务 Agent 项目里，我会额外记录 tool call、审批、幂等键和人工接管率。上线时先小流量灰度，评估集通过后再放量；如果模型、Rerank 或工具失败，可以降级到初召回、拒答、草稿或人工处理。
