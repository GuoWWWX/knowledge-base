# 面试：MySQL 与 Redis 核心高频硬核题库与大厂绝杀宝典

> [!abstract] 一句话总结
> 存储与缓存面试的答题主线是**“磁盘 I/O 与内存物理鸿沟 $\to$ B+树与跳表索引推导 $\to$ MVCC 与锁并发隔离 $\to$ 双写一致性与缓存三大灾难治理”**。回答必须能够手推 3 层 B+ 树容量公式、讲清 Read View 四大字段比对算法、指出 Redis 单线程与 6.0 多线程的网络边界，先给 30 秒结论，再展开 2 分钟原理。

## 🎯 大厂答题黄金框架

1. **先给第一性原理结论**：如“B+树是为了在磁盘页（16KB）限制下达到极高的扇出比（Fan-out），用最少的磁盘 I/O 找到目标”。
2. **严谨数理公式推导**：3 层 B+ 树计算：$1170 \times 1170 \times 16 \approx 2190$ 万条记录。
3. **软硬件结合**：Page Cache 刷盘策略、WAL、Epoll 多路复用。
4. **生产避坑与架构权衡**：慢 SQL 排查 SOP、Canal 监听 Binlog 解决双写一致性。

## 🔥 核心高频绝杀考题

### Q1: MySQL InnoDB 为什么选择 B+ 树作为索引结构？而不是 B 树、红黑树或哈希表？
> **30 秒绝杀版**：
> 核心是**为了最大化利用磁盘预读（局部性原理）并最小化磁盘 I/O 次数**。
> - 相比 **B 树**：B+ 树非叶子节点只存“索引键 + 指针”，不存数据行，单页（16KB）可容纳更多键，**扇出（Fan-out）极大、树高极矮（通常 3~4 层即可支撑 2000 万数据）**；且叶子节点用双向链表相连，**天然支持极高吞吐的范围扫描**。
> - 相比 **红黑树/AVL 树**：二叉树树高太深，在千万级数据下需 20+ 次磁盘 I/O，且不具备磁盘页友好性；
> - 相比 **哈希表**：哈希只支持等值查询，无法支持范围查询与排序。
>
> **2 分钟数理推导展开**：
> - **单页容量推算（3 层 B+ 树为什么能抗 2000 万数据？）**：
>   1. InnoDB 默认数据页大小为 **16KB**；
>   2. 假设主键使用 `BIGINT` 占 8 字节，子节点物理指针占 6 字节，一个索引项占 $8 + 6 = 14$ 字节；
>   3. 非叶子节点单页可容纳的索引指针数：$16\text{KB} / 14\text{B} \approx 1170$ 个；
>   4. 假设叶子节点单条业务数据占 1KB，单页可存储 16 条完整行记录；
>   5. **3 层 B+ 树的最大承载容量**：
>      $$N = 1170 \times 1170 \times 16 \approx 21,902,400 \text{ 条（约 2190 万行！）}$$
>   6. 根节点长驻内存，访问任意一行数据，**最多仅需 2 次真正的磁盘 I/O**！

### Q2: 什么是聚簇索引与非聚簇索引？什么是“回表”与“索引下推（ICP）”？
> **30 秒绝杀版**：
> - **聚簇索引（Clustered Index）**：叶子节点存放的是**完整的物理行记录**（InnoDB 主键索引）；
> - **非聚簇索引（二级索引/辅助索引）**：叶子节点存放的是**主键值（Primary Key）**。
> - **回表（Table Lookup）**：先走二级索引查出主键，再拿着主键去聚簇索引中重新查出完整行数据的二次寻址过程。
> - **索引下推（ICP）**：MySQL 5.6 引入的优化，**将部分 WHERE 条件过滤从 Server 层下沉到存储引擎层执行**，在回表前提前过滤，大幅减少回表次数。
>
> **2 分钟深度展开**：
> - **如何避免回表？——覆盖索引（Covering Index）**：
>   若查询字段全部包含在联合索引中（如建立 `idx_user(name, age)`，查询 `SELECT age FROM t_user WHERE name = 'Tom'`），存储引擎直接从二级索引叶子节点就能拿到数据返回，**0 回表，性能暴增**！
> - **索引下推（ICP）的底层时序对比**：
>   - *未开启 ICP*：二级索引命中 `name LIKE '张%'` 后，无条件把所有主键全部回表拉取完整记录，传回 Server 层后再由 Server 过滤 `age = 20`；
>   - *开启 ICP（Using index condition）*：InnoDB 在遍历二级索引树时，直接在引擎层判断 `age == 20`，不符合条件的直接抛弃，**只对完全满足条件的主键执行回表**，I/O 减少 90%！

### Q3: MySQL InnoDB 的 MVCC（多版本并发控制）底层是如何实现的？Read View 机制是什么？
> **30 秒绝杀版**：
> MVCC 是通过 **Undo Log 版本链** + **Read View（读视图）** 实现的“快照读”，实现**“读不加锁，读写不冲突”**。每次更新都会在行记录隐藏字段 `roll_ptr` 上形成单向旧版本链；事务在查询时生成一个 `Read View`，根据可见性算法判断版本链中哪一条历史快照对当前事务是可见的。
>
> **2 分钟深度展开**：
> - **行记录的三大隐藏字段**：`DB_TRX_ID`（最近修改该行的事务ID）、`DB_ROLL_PTR`（回滚指针，指向 Undo Log）、`DB_ROW_ID`（隐式主键）。
> - **Read View 四大核心属性**：
>   1. `m_ids`：生成该 Read View 时，系统内部**所有正在活跃（未提交）的事务 ID 列表**；
>   2. `min_trx_id`：活跃事务中最小的那个 ID；
>   3. `max_trx_id`：系统即将分配给下一个事务的 ID（当前最大事务 ID + 1）；
>   4. `creator_trx_id`：创建当前 Read View 的事务自身 ID。
> - **快照可见性比对四部曲（判断版本链中的 `trx_id` 能否被看到）**：
>   - ① 若 `trx_id == creator_trx_id`：当前事务自己改的，**可见**！
>   - ② 若 `trx_id < min_trx_id`：修改早已提交，**可见**！
>   - ③ 若 `trx_id >= max_trx_id`：修改在该事务之后才诞生，**不可见**！
>   - ④ 若 `min_trx_id <= trx_id < max_trx_id`：判断 `trx_id` 是否在 `m_ids` 列表中：
>     - 在列表中：说明生成快照时该事务仍未提交，**不可见**！沿指针找上一版本；
>     - 不在列表中：说明已提交，**可见**！
> - **RC vs RR 隔离级别的根本区别**：
>   - **RC（读已提交）**：**每次执行 SELECT 时都重新生成一个全新的 Read View**，因此能看到别人最新提交的数据（不可重复读）；
>   - **RR（可重复读）**：**仅在第一次执行 SELECT 时生成 Read View**，后续查询复用同一个 Read View，彻底实现可重复读。

### Q4: 如何利用 EXPLAIN 分析慢 SQL？关键指标看什么？
> **30 秒绝杀版**：
> 核心看三列：**`type`（访问类型）**、**`key`（实际使用索引）**、**`Extra`（额外信息）**。
> - `type` 性能从优到劣：`system > const > eq_ref > ref > range > index > ALL`。生产底线要求至少达到 `range` 或 `ref`，严禁全表扫描 `ALL`！
> - `Extra` 出现 `Using filesort`（文件排序）或 `Using temporary`（内存临时表）属于危险红线，必须调优消除！
>
> **2 分钟深度展开**：
> - **`type` 常见级别剖析**：
>   - `const`：主键或唯一索引等值查询，单次 I/O 搞定；
>   - `eq_ref`：多表关联查询中，关联键是唯一索引或主键；
>   - `ref`：普通非唯一二级索引等值匹配；
>   - `range`：索引范围查询（`BETWEEN`、`<`、`>`、`IN`）；
>   - `index`：全索引树扫描（无需回表但扫描了整棵二级索引树）；
>   - `ALL`：全表物理扫描（数据量大时必死）。
> - **慢 SQL 生产调优三步法**：
>   1. 检查是否存在**隐式类型转换**（如字符串字段未加引号导致全表扫描、编码字符集 utf8 与 utf8mb4 不一致）；
>   2. 检查是否违背了**最左前缀法则**，或把范围查询放到了联合索引的最前面；
>   3. 避免 `SELECT *`，建立联合索引实现**覆盖索引**，彻底消灭回表与 `Using filesort`。

### Q5: Redis 为什么单线程还能支撑 10 万+ QPS？Redis 6.0 引入多线程是在哪一部分？
> **30 秒绝杀版**：
> Redis 之所以快主要靠三点：**纯内存操作（纳秒级）**、**单线程模型彻底消灭了多线程上下文切换与锁竞争**、**基于 Linux Epoll 的 I/O 多路复用非阻塞网络模型**。Redis 瓶颈不在 CPU，而在网络 I/O。**Redis 6.0 引入的多线程仅仅用于“网络数据的读取解析和写入写回”，命令的真正路由与执行仍然是严格由单线程按序执行的，完全保留了内存操作的无锁与原子性！**
>
> **2 分钟深度展开**：
> - **单线程避免的代价**：现代多核多线程在超高并发下，CPU 上下文切换、线程阻塞与唤醒开销、以及全局互斥锁的竞争（如 Hash 扩容加锁）会消耗 40% 以上的算力。Redis 单线程无锁执行，代码干净且极致高效。
> - **I/O 多路复用（Reactor 模型）**：
>   单线程死等网络 Socket 会导致卡死。Redis 使用 Linux 内核的 `epoll`，一个线程同时监听数万个连接。当某个客户端 Socket 真正有数据写入内核缓冲区时，内核通知 Redis 处理，没有数据时 Redis 不阻塞，高效穿梭。
> - **6.0 多线程架构拆解**：
>   随着万兆网卡的普及，单线程从网络拷贝几百 MB 数据变得吃力。Redis 6.0 启动多线程帮助 Master 单线程分担 `read/write` 系统调用，主线程只负责执行命令，两全其美。

### Q6: 缓存穿透、缓存击穿、缓存雪崩的本质区别是什么？大厂如何防御？
> **30 秒绝杀版**：
> - **穿透**：数据在**缓存和数据库都没有**（黑客恶意扫描）；对策：**布隆过滤器拦截 + 空对象缓存（60s TTL）**。
> - **击穿**：**单一超级热点 Key 突然过期**，海量并发瞬间击垮 DB；对策：**分布式互斥锁（Redisson Double Check）+ 逻辑不过期**。
> - **雪崩**：**大量 Key 同一时间集中过期，或 Redis 集群宕机**；对策：**TTL 加随机漂移打散（如 1h ± 5min）+ 多级本地缓存 Caffeine + 熔断限流**。
>
> **2 分钟深度展开**：
> - **布隆过滤器（BloomFilter）防穿透原理**：
>   由一个极大的 Bit 数组和 $K$ 个独立 Hash 函数构成。数据存入时，将 $K$ 个 Hash 映射的位全部置为 1。
>   - **数学铁律**：**“判定不存在，则百分之百必定不存在；判定存在，可能存在极小误判（假阳性）”**。
>   - 请求进门先查布隆，直接在内存中掐死 99.99% 的虚假恶意 ID。

### Q7: 缓存与数据库一致性：为什么选“先写 DB，再删 Cache”？生产终极方案是什么？
> **30 秒绝杀版**：
> 严禁直接更新缓存（引发并发写覆盖脏写），必须采用删除缓存。
> - “先删缓存再写 DB”并发读写时，读线程会回源拿到未提交的旧值回填，**导致缓存永久留存脏数据**！
> - “先写 DB 再删缓存”产生脏数据的概率极低（因写 DB 耗时远超读 DB）。
> **生产终极标准解法：业务代码只管提交 MySQL 事务 $\to$ 由 Canal / Debezium 伪装从库监听 Row Binlog $\to$ 投递至高可靠 MQ $\to$ 异步消费者执行 Redis 删除与死信重试，彻底解耦并保障 BASE 最终一致性！**
