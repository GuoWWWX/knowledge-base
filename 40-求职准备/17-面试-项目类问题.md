# 面试-项目类问题

> [!abstract] 一句话总结
> 项目面试不是按开发流水账复述，而是用“背景 -> 职责 -> 方案 -> 难点 -> 指标 -> 复盘”证明你真正做过、想清楚过，并能扛住追问。

## 🎯 总回答框架

1. **先给定位**：这个项目解决什么业务问题，为什么值得做。
2. **明确职责**：你负责哪条链路、哪些模块、哪些关键决策。
3. **展开方案**：讲核心架构、关键流程、数据模型、异常路径。
4. **突出难点**：并发、一致性、性能、权限、安全、评估、可观测。
5. **给出指标**：QPS、P95/P99、错误率、成本、召回率、成功率、故障恢复时间。
6. **补充取舍**：为什么这么选，没选其他方案的原因，后续怎么优化。

## 🧭 2 分钟项目介绍模板

```text
这个项目的背景是【业务问题】。我主要负责【核心模块/链路】。
整体方案是【一句话架构】，核心流程包括【步骤1、步骤2、步骤3】。
里面最难的是【并发/一致性/性能/权限/评估】，我通过【关键技术方案】解决。
上线或压测后，指标是【QPS/P95/准确率/成本/成功率】，同时我也做了【监控/补偿/降级/复盘】。
如果后续继续优化，我会重点看【瓶颈和演进方向】。
```

## 📦 项目一：高并发秒杀系统

关联：[[../20-Java后端/09-项目实战/01-项目-高并发秒杀系统]]

### 2 分钟介绍稿

这个项目是为了训练高并发下的库存扣减和异步下单能力。秒杀的核心问题是库存少、请求瞬时集中，如果所有请求直接进入数据库，会造成连接池耗尽、行锁竞争甚至超卖。

我负责的核心链路是“活动预热、秒杀下单、Redis 预扣、MQ 异步落库、支付超时关单和库存对账”。整体方案是入口先限流，活动开始前把库存预热到 Redis；用户请求进入后用 Lua 原子完成库存校验、扣减和已购标记；扣减成功后发送 MQ 或写 outbox，消费者异步创建订单；数据库用 `(activity_id,user_id)` 唯一索引和状态机条件更新做兜底。

这个项目最难的是防超卖、重复下单和异常补偿。我用了 Redis Lua 保证缓存层原子性，用 requestId、已购标记和 DB 唯一约束保证幂等；Redis 扣减成功但 MQ 失败时，通过 outbox 重试或回补库存；支付成功和超时关单用 `WHERE status='WAIT_PAY'` 条件更新互斥。

压测时我会固定库存，比如 1000，发起 10000 或 50000 请求，验证成功订单数不超过库存、重复用户数为 0，同时记录 QPS、P95/P99、MQ lag、MySQL TPS 和库存一致性 SQL。

### 技术亮点

- Redis Lua 原子扣减库存。
- MQ 异步削峰。
- DB 唯一索引兜底防重复。
- Outbox / 重试 / DLQ 保证异常可恢复。
- 支付和关单状态机互斥。
- 压测和一致性校验证明方案有效。

### 高频追问

> [!question] 追问树
> - Q: 为什么不直接扣数据库库存？
>   - A: 秒杀是热点高并发写，直接打 DB 会形成行锁竞争和连接池压力。Redis Lua 可以把大部分请求挡在 DB 前，DB 只处理成功资格。
> - Q: Redis 扣成功但 MQ 失败怎么办？
>   - A: 使用 outbox 或事务消息。超过重试上限则回补 Redis 库存和购买标记，并把请求结果置为失败。
> - Q: 如何防重复下单？
>   - A: 接口 requestId、Redis 已购集合、消费者幂等、订单唯一索引多层兜底。
> - Q: 如何证明没有超卖？
>   - A: 压测后校验成功订单数、库存流水、Redis 剩余库存和 DB 库存字段，且重复用户数为 0。
> - Q: 热点 key 怎么处理？
>   - A: 限流、分段放量、库存分片、本地缓存活动状态。库存分片要处理汇总和少卖补偿。
> - Q: MQ 堆积怎么办？
>   - A: 先区分生产突增、消费者慢、下游 DB 慢、单分区热点和坏消息，再扩容消费者、限流入口、优化下游或进 DLQ。

### 简历 bullet 示例

```text
设计并实现高并发秒杀核心链路，基于 Redis Lua 完成库存原子预扣，结合 MQ 异步下单、订单唯一索引、请求幂等和 outbox 补偿机制，保证固定库存压测场景下无超卖、无重复下单，并沉淀 QPS、P95/P99、MQ lag 和库存一致性校验指标。
```

## 📦 项目二：JVM 故障排查演练

关联：[[../20-Java后端/09-项目实战/05-项目-JVM故障排查演练]]

### 2 分钟介绍稿

这个项目主要是把 JVM 理论转成可复现的线上排障能力。我设计了一组 Spring Boot 故障接口，分别模拟 CPU 飙高、堆 OOM、Metaspace OOM、Direct Memory OOM、线程死锁、频繁 Full GC 和慢接口。

我的排查方法是先根据监控判断问题属于 CPU、内存、GC、线程阻塞还是慢调用，再选择对应工具。CPU 高时用 `top -H` 找热点线程，再转十六进制到 `jstack` 里定位 Java 栈，必要时用 Arthas `thread/trace` 定位方法；堆 OOM 用 `jstat`、`jmap -histo` 和 heap dump 找 GC Roots；堆外内存用 NMT 和 `jcmd VM.native_memory`；死锁用 `jstack` 或 Arthas `thread -b`。

每类故障我都会保留现象、命令、证据、根因、修复和复验指标。这个项目的价值是面试时不只会背 JVM 参数，而能完整讲一次线上故障怎么定位和闭环。

### 高频追问

> [!question] 追问树
> - Q: CPU 飙高怎么定位？
>   - A: `top -H` 找线程，线程 id 转十六进制，`jstack` 找对应 nid，看栈顶热点方法，再用 Arthas trace/watch 验证。
> - Q: OOM 怎么排查？
>   - A: 先区分 Heap、Metaspace、Direct Memory、Native Thread，再用对应工具取证。Heap 看 histo 和 dump，Direct 看 NMT。
> - Q: Full GC 频繁一定是内存泄漏吗？
>   - A: 不一定。可能是内存泄漏，也可能是分配过快、新生代过小、大对象或批处理峰值，要看 Full GC 后 Old 区是否下降。
> - Q: 死锁怎么修？
>   - A: 先通过 jstack 找循环等待，再统一加锁顺序、缩小锁范围、避免锁内 RPC，必要时用 tryLock 超时。

### 简历 bullet 示例

```text
搭建 JVM 故障演练项目，模拟 CPU 飙高、Heap/Metaspace/Direct Memory OOM、死锁和频繁 Full GC 等场景，沉淀 top、jstack、jmap、jcmd、JFR、Arthas 的排查流程，形成“现象-证据-根因-修复-复验”的故障复盘模板。
```

## 📦 项目三：企业知识库 RAG 系统

关联：[[../10-AI应用开发/08-项目实战/03-项目-企业知识库RAG系统]]

### 2 分钟介绍稿

这个项目是面向企业内部文档问答的 RAG 系统。普通大模型不知道企业私有制度、产品手册和故障文档，而且容易幻觉，所以我设计了一套“先检索证据，再基于证据回答，并提供引用溯源”的系统。

我负责的核心链路包括文档上传、解析、结构化切分、Embedding、向量入库、Hybrid Search、Rerank、Prompt 组装、流式回答、引用溯源、权限过滤和评估观测。离线侧会把文档解析成带 `tenantId`、`titlePath`、`pageNo`、`aclTags` 的 chunk；在线侧先做问题改写和权限过滤，再用向量检索 + 关键词检索召回候选，Rerank 后拼 Prompt，要求模型只基于资料回答。

这个项目的难点是答案质量不可只凭感觉，所以我准备评估集，关注 Recall@K、MRR、Faithfulness、Answer Relevancy、拒答准确率、P95 延迟和 Token 成本，并用 Langfuse 记录 query、retrieved chunks、prompt、answer 和用户反馈，方便 badcase 复盘。

### 高频追问

> [!question] 追问树
> - Q: RAG 答案错了怎么排查？
>   - A: 先看正确资料是否召回，再看排序是否靠前，再看 Prompt 是否包含资料，最后看模型是否忠实生成。
> - Q: 为什么需要 Hybrid Search？
>   - A: 向量适合语义，关键词适合编号、错误码、专有名词，企业知识库两类需求都有。
> - Q: Rerank 一定要加吗？
>   - A: 不一定。候选多、文档相似、质量要求高时加；文档少或延迟敏感时可以先不加。
> - Q: 如何防越权？
>   - A: 检索阶段按 tenant、space、role、acl metadata 强过滤，不能把无权资料放进 Prompt。
> - Q: 如何证明效果？
>   - A: 用评估集和 Langfuse，看 Recall@K、Faithfulness、拒答准确率、延迟和成本的版本对比。

### 简历 bullet 示例

```text
基于 Spring AI + Milvus/pgvector 构建企业知识库 RAG 系统，实现文档解析、结构化切分、Hybrid Search、Rerank、引用溯源、权限过滤和 Langfuse 观测，并通过评估集跟踪 Recall@K、Faithfulness、P95 延迟和 Token 成本，支持 badcase 回归优化。
```

## 📦 项目四：业务 Agent 系统

关联：[[../10-AI应用开发/08-项目实战/07-项目-业务Agent系统]]

### 2 分钟介绍稿

这个项目是把 RAG、多轮记忆、MCP 工具和 Skills 组合成一个可控的业务 Agent。我的设计原则是 Agent 不能直接拥有无限权限，模型只负责提出计划和工具调用意图，真正的权限、参数、风险和审计必须由 Java 服务端控制。

系统整体分成 Planner、Plan Validator、Executor、Tool Gateway、Memory、RAG 和 Audit Log。用户提出目标后，Planner 生成计划，Validator 判断风险，Executor 按状态机执行。所有工具调用都经过 Tool Gateway，做工具白名单、租户权限、参数校验、风险分级和幂等控制。低风险动作可以自动执行，高风险动作进入人工确认，禁止动作只能转人工工单。

这个项目的重点是生产治理：比如智能客服场景里，查询订单是 L0，只读；生成回复草稿是 L1；打标签是 L2；退款发券是 L3，需要审批；改权限和转账是 L4，禁止自治。整个过程会记录 Langfuse trace 和审计日志。

### 高频追问

> [!question] 追问树
> - Q: Agent 和普通工作流区别？
>   - A: 工作流路径固定、可控性强；Agent 更灵活但风险更高。生产上通常用状态机/工作流约束 Agent。
> - Q: 如何防止 Agent 越权？
>   - A: 工具白名单、服务端鉴权、参数级校验、风险分级、人工审批和审计日志。
> - Q: 工具调用失败怎么办？
>   - A: 低风险临时失败可退避重试，高风险失败转人工；所有调用要有幂等键和状态记录。
> - Q: Memory 怎么设计？
>   - A: 分会话记忆、任务轨迹、用户偏好和长期知识，必须可授权、可删除、可审计。
> - Q: 如何评估 Agent？
>   - A: 看任务完成率、工具调用成功率、人工接管率、错误率、平均步骤数、P95 延迟和 Token 成本。

### 简历 bullet 示例

```text
设计业务 Agent 系统，将 RAG、多轮记忆、MCP 工具和 Skills 编排到统一状态机中，通过 Tool Gateway 实现工具白名单、参数校验、风险分级、人工审批、幂等和审计，支持智能客服场景下订单查询、回复草稿、补偿审批等端到端任务。
```

## 🧨 通用高频项目追问

### Q1: 介绍项目时怎么避免流水账？

> 用“背景、目标、职责、方案、难点、结果”压成 2 分钟版本。重点放在自己负责的决策和结果指标，不要按开发流程从建表讲到写接口。

### Q2: 面试官追问技术选型时怎么答？

> 先讲约束：数据量、并发、团队熟悉度、交付周期和风险；再讲为什么选当前方案，以及没有选另一个方案的代价。最后补一句上线后的验证指标。

### Q3: 项目里没有真实大流量怎么办？

> 不要硬编数据。可以讲你如何设计压测、容量估算、缓存策略、降级方案和观测指标，并明确哪些是实测结果、哪些是方案推演。

### Q4: 被问“这个项目是不是 demo”怎么办？

> 重点回答生产化能力：权限、幂等、异常补偿、可观测、评估、压测、部署、回滚和 badcase 复盘。如果暂时只是个人项目，要明确哪些已经实现，哪些是生产化设计。

### Q5: 项目数据量不大，怎么体现 5 年经验？

> 用工程完整度体现经验：容量估算、瓶颈分析、压测设计、故障注入、监控指标、扩展方案和取舍理由。不要夸大数据，而要证明你知道大流量下会发生什么。
