# 面试-系统设计

> [!abstract] 一句话总结
> 系统设计题要先澄清目标和指标，再做容量估算、数据模型、核心链路、异常补偿、高可用和观测验证；高级候选人必须能把设计题落到项目证据和指标上。

## 🎯 回答框架

1. **澄清范围**：用户是谁，核心场景是什么，不做什么。
2. **确定指标**：QPS、峰值、数据量、延迟、可用性、一致性要求。
3. **数据模型**：核心实体、状态机、索引、分库分表预案。
4. **核心链路**：读路径、写路径、异步路径、状态流转。
5. **异常场景**：重复、乱序、超时、失败、补偿、对账。
6. **高可用**：限流、熔断、降级、重试、隔离、容灾。
7. **观测验证**：日志、指标、Trace、压测、告警和复盘。
8. **演进取舍**：先做简单可用，再按瓶颈演进。

## 🧭 通用开场模板

```text
我先澄清一下需求边界：这个系统主要服务【用户/场景】，核心能力是【功能】。
我会先按【QPS/数据量/延迟/一致性】做容量估算，然后设计核心数据模型和主链路。
接着重点处理【高并发/一致性/可用性/权限/评估】几个风险点。
最后用压测、监控和对账指标证明设计有效。
```

## 📌 题型一：秒杀系统

关联：[[../20-Java后端/08-系统设计/04-秒杀系统设计]]、[[../20-Java后端/09-项目实战/01-项目-高并发秒杀系统]]

### 答题骨架

- 业务目标：有限库存，高并发抢购，不超卖，体验可控。
- 容量估算：库存 1000，预约 10 万，峰值 1 万~5 万 QPS。
- 核心链路：静态页/限流 -> 资格校验 -> Redis Lua 预扣 -> MQ 异步下单 -> DB 唯一约束 -> 支付/关单。
- 数据模型：活动、库存、订单、库存流水、outbox。
- 异常兜底：MQ 失败回补、重复消费幂等、支付关单互斥、对账补偿。
- 指标：QPS、P95/P99、限流拒绝率、MQ lag、成功订单数、重复订单数、库存一致性。

### 高频追问

> [!question] 追问
> - 为什么不直接扣数据库？
> - Redis 扣减成功但 MQ 失败怎么办？
> - 如何证明没有超卖？
> - 热点 key 怎么处理？
> - 支付成功和超时关单并发怎么办？

## 📌 题型二：订单系统

关联：[[../20-Java后端/08-系统设计/07-订单系统设计]]、[[../20-Java后端/09-项目实战/03-项目-订单履约系统]]

### 答题骨架

- 业务目标：管理订单从创建、支付、履约、完成到售后的生命周期。
- 核心抽象：订单状态机。
- 数据模型：订单表、订单项、支付单、状态日志、outbox、补偿任务。
- 核心链路：创建订单 -> 支付单 -> 支付回调 -> 履约事件 -> 发货 -> 完成/退款。
- 并发问题：重复下单、重复支付回调、支付与关单并发。
- 一致性：本地事务 + outbox + MQ + 幂等消费 + 补偿对账。

> - 订单状态机怎么设计？
> - 支付回调重复怎么办？
> - 支付和关单并发怎么办？
> - 为什么要订单快照？
> - 跨服务一致性怎么保证？

## 📌 题型三：企业知识库 RAG 系统

关联：[[../10-AI应用开发/08-项目实战/03-项目-企业知识库RAG系统]]

### 答题骨架

- 业务目标：基于企业私有文档回答问题，降低幻觉，支持引用溯源。
- 离线链路：文档上传 -> 解析 -> 清洗 -> Chunk -> Embedding -> 向量库。
- 在线链路：问题改写 -> 权限过滤 -> Hybrid Search -> Rerank -> Prompt -> LLM -> 引用。
- 数据模型：document、chunk、embedding version、acl tags、eval case。
- 质量保障：Recall@K、MRR、Faithfulness、Answer Relevancy、拒答准确率。
- 生产治理：权限隔离、Langfuse Trace、badcase 回归、索引更新。

> [!question] 追问
> - RAG 答案错了怎么排查？
> - 为什么不用纯向量检索？
> - Rerank 放在哪里？
> - 如何防止越权召回？
> - 如何证明 RAG 效果提升？

## 📌 题型四：业务 Agent 系统

关联：[[../10-AI应用开发/08-项目实战/07-项目-业务Agent系统]]

### 答题骨架

- 业务目标：让 Agent 完成可控的业务任务，不是无限自治。
- 核心架构：Planner、Validator、Executor、Tool Gateway、Memory、Audit。
- 状态机：CREATED -> PLANNING -> EXECUTING -> WAIT_HUMAN -> COMPLETED/FAILED。
- 工具治理：白名单、参数校验、权限校验、风险分级、人工审批。
- 可观测：任务轨迹、工具调用、token、latency、人工接管率。
- 安全边界：模型不是安全主体，服务端才是权限裁决点。

### 高频追问

> [!question] 追问
> - Agent 和 Workflow 怎么取舍？
> - 如何防止 Agent 越权？
> - 高风险工具如何审批？
> - 工具失败如何重试和补偿？
> - 如何评估 Agent 效果？

## 📌 题型五：短链系统

关联：[[../20-Java后端/08-系统设计/05-短链系统设计]]

### 答题骨架

- 业务目标：长链接转短码，支持跳转、统计、防刷。
- 容量估算：短链生成 QPS、跳转 QPS、存储量、缓存命中率。
- 短码生成：自增 ID Base62、号段发放、随机码去重。
- 数据模型：short_code、long_url、creator、expire_time、status。
- 读路径：短码 -> 缓存 -> DB -> 301/302 跳转。
- 风险：短码冲突、热点短链、防刷、恶意链接、过期清理。

## 📌 题型六：IM / 即时通讯系统

关联：[[../20-Java后端/08-系统设计/06-即时通讯系统设计]]

### 答题骨架

- 业务目标：单聊/群聊、在线消息、离线消息、已读未读。
- 连接层：WebSocket/TCP 长连接，连接网关管理在线状态。
- 消息链路：发送 -> 持久化 -> 投递 -> ACK -> 离线补偿。
- 数据模型：会话、消息、收件箱、用户连接、群成员。
- 一致性：消息至少一次、客户端去重、递增序号。
- 指标：在线连接数、消息 TPS、投递延迟、ACK 成功率。

## 🧨 通用高频问题

### Q1: 系统设计题怎么开场？

> 先澄清业务范围和核心指标，再做容量估算，然后设计数据模型、接口、核心链路、高可用和扩展点。不要一上来画架构图。

### Q2: 如何设计高可用？

> 从冗余部署、故障隔离、超时重试、限流熔断、降级、数据备份和观测告警构建闭环。高可用不是多部署几台机器，而是故障发生时能隔离、降级、恢复和复盘。

### Q3: 如何证明架构能扛住流量？

> 给出 QPS、峰值、缓存命中率、数据库容量、MQ lag、线程池、连接池、压测指标和瓶颈位置，而不是只画架构图。

### Q4: 面试官说“如果流量扩大 10 倍”怎么办？

> 先判断瓶颈在哪：入口、Redis、DB、MQ、下游 RPC、带宽还是模型服务。然后按瓶颈给演进方案，例如限流、缓存、分片、异步化、读写分离、分库分表、降级和扩容。

### Q5: 一致性和可用性怎么取舍？

> 先看业务是否能接受最终一致。交易金额、库存扣减等关键状态要强约束或状态机兜底；通知、积分、履约等可以事件驱动最终一致；所有最终一致都要有幂等、补偿和对账。
