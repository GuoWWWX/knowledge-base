# 面试-LLM基础

> [!abstract] 一句话总结
> 本文用于把 面试-LLM基础 的知识点整理成可直接复习和模拟面试的问答，回答时遵循“先结论、再原理、再项目落地、最后风险取舍”，重点面向 AI 应用、RAG、Agent 岗位。

## 🎯 回答框架

1. **先给结论**：一句话回答面试官问题。
2. **展开原理**：讲核心机制、边界和常见误区。
3. **结合项目**：落到 RAG、Agent、工具调用、评测、监控或服务化架构。
4. **补充取舍**：说明为什么这样选，以及失败时怎么兜底。

## 面试官最想听到的 6 个意识

- **模型不是越大越好**：要看任务类型、成本、延迟、稳定性和可控性。
- **上下文不是越长越好**：长上下文会带来更高成本、更高延迟，以及注意力被噪声稀释的问题。
- **Prompt 不是唯一解**：很多问题本质要靠检索、工具、流程控制、输出校验来解决。
- **能用结构化输出就别只要自然语言**：便于程序消费、监控和失败重试。
- **Agent 的核心不是“会思考”，而是“可观测、可约束、可回滚”**。
- **上线标准不是 Demo 跑通，而是可评估、可监控、可降级**。

## 高频问题

### Q1: LLM 的一次调用大致经历什么过程？

> 输入先经过 tokenizer 切成 token，系统再把 system prompt、user prompt、历史消息、检索上下文、工具结果拼接进上下文窗口，模型按采样参数逐 token 生成输出。工程上最需要关注的是 **token 成本、首字延迟、总延迟、结构化输出成功率、工具调用成功率**。

可继续展开：

- **输入阶段**：清洗用户输入、拼接上下文、裁剪历史消息。
- **推理阶段**：模型根据上下文分布预测下一个 token。
- **解码阶段**：受 temperature、top-p、max tokens 等参数影响。
- **后处理阶段**：做 schema 校验、敏感信息过滤、引用补全、失败重试。

### Q2: token、cost、latency 三者怎么一起看？

> 我通常把它们看成一个联动三角：**输入 token 决定成本底座，输出 token 决定不确定成本和尾延迟，模型大小决定单 token 推理时延和价格档位**。优化时先减无效上下文，再控输出长度，最后再考虑换模型或缓存。

面试时建议这样回答：

- **token**：上下文、历史消息、检索片段、工具结果都会消耗 token。
- **cost**：通常由 input tokens + output tokens + 工具/检索链路成本组成。
- **latency**：可拆成检索耗时、编排耗时、模型首字延迟、流式输出耗时、工具往返耗时。

实战优化点：

1. **先减输入**：去重、摘要历史消息、压缩检索片段。
2. **再控输出**：限定输出字段、限制 max tokens、优先 JSON 而不是长自然语言。
3. **模型分层**：路由小模型做分类/重写，大模型做最终生成。
4. **缓存策略**：静态 system prompt、常见问答、检索结果、embedding 结果可缓存。
5. **并行化**：检索、改写、工具预取能并行就并行。

### Q3: 上下文窗口越大越好吗？

> 不是。更大的上下文窗口提升了可容纳信息量，但不天然提升回答质量；如果把无关内容都塞进去，模型更容易被噪声干扰，成本和延迟也会上升。生产里更合理的是 **检索、重排、压缩、引用定位** 四步走。

可落到项目：

- RAG 场景先召回 20~50 段，再用 reranker 压到 5~10 段。
- 对长文档做 **chunk + metadata + 标题层级保留**，避免语义割裂。
- 保留 **来源 ID / 页码 / chunk ID**，便于回答附引用与回溯。

### Q4: 结构化输出为什么重要？怎么做？

> 结构化输出的价值不只是“格式整齐”，而是让 LLM 输出可以直接进入程序链路，便于校验、重试、审计和统计。AI 应用里，凡是要进入数据库、工作流、工具调用、审批流的结果，我都会优先要求 JSON/Schema 化输出。

面试可讲 3 层：

- **第一层：Prompt 约束**：明确字段名、枚举值、缺失时返回 null。
- **第二层：Schema 校验**：用 JSON Schema / Pydantic / Java DTO 校验。
- **第三层：失败兜底**：校验失败则重试一次；再失败则降级成人工审核或自然语言结果。

典型场景：

- 工单分类：`category`、`priority`、`confidence`、`reason`。
- RAG 问答：`answer`、`citations[]`、`confidence`、`need_human`。
- Agent 规划：`goal`、`steps[]`、`required_tools[]`、`stop_condition`。

### Q5: 工具调用和普通文本生成的本质区别是什么？

> 普通生成是在“说”，工具调用是在“做”。对 Agent 岗来说，关键不是让模型多会说，而是让它在什么条件下触发什么工具、拿到什么结果、如何校验结果、什么时候停止。

回答要点：

- **工具调用适合外部事实、实时数据、执行动作**，例如查数据库、搜知识库、发请求、操作工单系统。
- **模型负责决策，工具负责取真值或执行动作**。
- **要做权限边界**：哪些工具可调用、参数白名单、超时控制、幂等设计。
- **要做观测**：记录 tool name、参数、耗时、成功率、重试次数。

面试加分点：

- 将工具结果再次喂给模型前，标注其角色为 `tool/context`，避免被当成高优先级指令。
- 对高风险工具采用 **先规划、后执行、执行前确认、执行后核验** 的流程。

### Q6: Temperature、Top-P、Max Tokens 怎么调？

> 我的经验是先按任务类型分层，再做离线评测微调，而不是拍脑袋。**分类、抽取、SQL 生成、工具参数生成** 这类任务偏低温；**营销文案、头脑风暴、改写扩写** 可以适当提高温度。

一个常用口径：

- **temperature**：控制随机性，越低越稳定。
- **top-p**：控制候选 token 的概率质量范围。
- **max tokens**：限制输出长度，也直接影响成本和尾延迟。
- **stop sequences**：适合截断固定格式输出或多轮协议边界。

工程实践：

- 不建议同时大幅调高 temperature 和 top-p。
- 调参要绑定任务评测集，看准确率、格式成功率、人工偏好和稳定性。
- 工具调用类任务一般优先稳定，创意类任务才追求多样性。

### Q7: 幻觉为什么会发生？如何治理？

> 幻觉不能完全消灭，但可以显著压低。它本质上来自 **参数记忆的近似性、上下文证据不足、Prompt 约束不足、工具缺失、输出校验缺失**。所以治理思路不是只改 Prompt，而是从数据、流程、约束、评测四个面一起做。

常见治理手段：

1. **RAG 补充外部事实**，并要求引用。
2. **先判断是否有证据再作答**，无证据就明确说不知道。
3. **结构化输出 + 置信度字段**。
4. **双阶段生成**：先抽取证据，再基于证据生成答案。
5. **高风险场景加规则或人工审核**，例如客服赔付、医疗、法律。

面试里的好回答不是“我会降低 temperature”，而是能说出 **证据约束、引用链路、拒答策略、离线评测指标**。

### Q8: 拒答是越少越好吗？

> 不是。面向企业应用时，拒答率和幻觉率往往要一起看。很多业务里，**宁可在低置信度时拒答或转人工，也不要自信地乱答**。关键不是追求“绝不拒答”，而是追求“在该答时答得准，在不该答时拒得稳”。

可以这样落地：

- 定义 **可答 / 不可答 / 需澄清 / 转人工** 四类结果。
- 对缺少证据、命中敏感规则、工具失败、输出校验失败等情况触发拒答或澄清。
- 在线上记录拒答原因分布，区分是召回不足、Prompt 问题还是模型能力问题。

### Q9: RAG 和微调分别适合解决什么问题？

> 如果问题主要是“模型不知道你的私有知识”，优先 RAG；如果问题主要是“模型输出风格、格式、决策边界不稳定”，再考虑微调或蒸馏。多数企业知识问答、客服助手、内部 Copilot，第一选择还是 RAG + Prompt + 工具链。

区分口径：

- **RAG**：补充最新、私有、可回溯知识。
- **微调**：固化输出风格、任务模式、领域术语映射。
- **工具**：补实时数据、补执行能力。

### Q10: 怎么评估一个 AI 应用做得好不好？

> 我会把评估拆成四层：**模型层、任务层、系统层、业务层**。只看模型主观感觉没有意义，必须结合真实任务指标和线上行为指标。

可用指标示例：

- **模型层**：格式成功率、拒答率、幻觉率、引用准确率。
- **任务层**：检索命中率、答案正确率、工具调用成功率、任务完成率。
- **系统层**：P50/P95 延迟、token 成本、超时率、重试率。
- **业务层**：解决率、转人工率、用户满意度、线索转化率。

## 项目回答模板

### 模板 1：AI 应用 / RAG 项目

1. **业务目标**：要解决什么问题，原流程哪里慢、贵、不准。
2. **方案结构**：输入改写、检索、重排、上下文拼接、LLM 生成、输出校验。
3. **关键取舍**：为什么选这个模型、为什么需要 reranker、为什么要结构化输出。
4. **效果指标**：准确率、命中率、延迟、成本、转人工率改善多少。
5. **踩坑与优化**：如 chunk 切分不合理、上下文噪声过多、工具超时、幻觉偏高。
6. **兜底策略**：拒答、澄清、人工接管、缓存、降级模型。

### 模板 2：Agent 项目

1. **任务目标**：Agent 要完成什么多步任务。
2. **工具集合**：有哪些工具，调用权限如何控制。
3. **规划机制**：是单步决策还是 plan-act-observe 循环。
4. **终止条件**：什么时候停止，什么时候重试，什么时候转人工。
5. **观测指标**：单任务平均步数、工具成功率、任务完成率、平均成本。
6. **风险控制**：Prompt 注入、错误工具调用、循环调用、越权操作怎么防。

## 一套适合面试现场的回答句式

- **先结论**：在企业场景里，我不会把 LLM 当成单纯聊天模型，而是当成一个需要被检索、工具、校验和监控包起来的概率组件。
- **讲方法**：我的设计重点一般是上下文治理、结构化输出、工具调用边界和失败兜底。
- **讲项目**：比如在 RAG 项目里，我会先做召回和重排，再让模型基于证据回答，并输出引用与置信度。
- **讲取舍**：这样做的代价是链路更长，但能换来更可控的准确率和更清晰的线上问题定位。

## 追问准备

- 你们是怎么控制 token 成本的？有没有做缓存、摘要、模型路由？
- 你们如何判断是检索问题还是生成问题？
- 为什么不直接上更大模型？什么时候值得上更大模型？
- 工具调用失败时，系统是重试、降级还是人工接管？
- 有没有做线上评测看板？你最关注哪些 P95 和成功率指标？
