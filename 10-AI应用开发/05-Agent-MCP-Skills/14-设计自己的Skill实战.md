# 🛠️ 设计自己的 Skill 实战

> [!abstract] 一句话总结
> 先想清楚任务、输入和边界，再写指引与配套文件，最后用正例、负例和异常情况验证。下面沿用 [[13-Skills详解]] 的周报例子。

## 📌 先确定要解决什么问题

假设团队每周要把工作记录整理成周报。我们希望 Agent 根据已有记录生成草稿，分为“已完成、进行中、风险”；没有提供的信息标为待确认，不编造成果，也不主动发送。
这个流程有稳定的输入、输出和复用价值，适合写成 Skill。Skill 不需要把每种事情都包进去：会议纪要的输入和输出不同，可以单独设计，不必塞进周报 Skill。

## ⚙️ 第一步：写清名称和描述

名称标识 Skill，描述帮助宿主判断它适合什么任务。按 Agent Skills 规范，`name` 与目录名一致，长度为 1～64 个字符，只能使用小写字母、数字和连字符，连字符不能在开头、结尾或连续出现；`description` 必填且非空，最多 1024 个字符，写清要做的事和适用场景。

```yaml
name: weekly-report
description: 根据用户提供的工作记录整理周报；仅解释周报写法时不使用。
```

描述太宽，例如“处理工作相关内容”，容易和其他 Skill 混淆；写得过窄，例如只认“帮我写周报”几个字，又可能漏掉“整理本周工作”。是否选中还受宿主和模型影响，不能仅凭描述保证触发正确。

## 🧩 第二步：编写流程和模板

在支持 Skills 的宿主中，创建下面两个文件。这里以 Claude Code 的项目级目录为例，路径从项目根目录开始；其他宿主的发现路径可能不同。

```text
.claude/skills/weekly-report/
├── SKILL.md
└── references/
    └── report-template.md
```

先写 `SKILL.md`：

```markdown
---
name: weekly-report
description: 根据用户提供的工作记录整理周报；仅解释周报写法时不使用。
---

# 整理周报

1. 确认统计范围，读取用户提供或已授权的工作记录。
2. 按已完成、进行中、风险归类；无法确认的内容标记待确认。
3. 参考 references/report-template.md 输出草稿，不编造成果。
4. 没有足够记录时说明缺什么；不要自行发送周报。
```

再写 `references/report-template.md`：

```markdown
# 周报

## 已完成

## 进行中

## 风险与待确认
```

正文写主要步骤和边界，模板则保留固定的输出结构；通过路径让 Agent 知道需要时去哪里找。资料较长时也可以放在 `references/`，需要程序处理时再添加 `scripts/`。如果没有脚本或参考资料，就不必为了目录齐全而创建空文件夹。

> [!tip] 把含糊要求改成可检查的动作
> “整理得专业一些”很难检查；“按三类归纳，缺失信息标待确认”则更容易比较结果，也更方便后续测试。

### 什么时候需要代码

模型适合归纳工作内容；日期转换、金额计算等有明确规则的步骤可以交给程序。比如明确知道年份后，Java 可以用 `LocalDate.of(year, month, day)` 校验日期并生成标准日期。年份不明时保留原文并标记待确认，不要用当前年份猜测；日期无效时应返回错误，由使用者核对。
是否需要把程序放进 `scripts/` 取决于任务和宿主：要写明如何运行、输入输出与失败处理，并验证环境有运行条件。不要把目录里放了脚本当成“脚本一定会自动执行”。

## 🧪 第三步：让宿主发现并测试

下面以已安装并能正常使用的 Claude Code 为例，验证思路也适用于其他支持 Skills 的宿主，但具体命令和界面要查对应文档。
1. 在项目根目录按上面的路径创建两个文件，从该项目启动 Claude Code；如果是在运行中的会话新建了顶层 Skills 目录，可按产品提示重新加载 Skills。
2. 查看 `/skills` 列表，确认能看到 `weekly-report`；找不到时检查目录、文件名、YAML、当前项目及宿主配置。
3. 输入“帮我写周报：完成订单查询接口；正在排查登录失败；风险尚未确认”，检查是否选用了该 Skill、是否按三类输出。
4. 也可以显式输入 `/weekly-report`，再提供同一段记录；这一步验证显式调用，不能代替自动触发测试。

示例中的结果应保留“风险尚未确认”，不能凭空补出负责人、完成日期或具体故障原因。查看宿主提供的执行记录或加载提示，确认确实读取了 Skill；只有输出格式相似，不足以证明触发成功。如果宿主不展示加载记录，可先检查 Skill 列表、显式调用，再结合可用的日志排查。

> [!note] 示例说明
> 以上是可按步骤搭建的示例，本文没有实际连接 Claude Code 或执行测试；具体菜单、权限与重载方式以当前宿主文档为准。

## 🔍 第四步：准备正反例和异常例

保留输入与预期结果，修改 `description`、正文或模型后重复测试：

| 类型 | 输入 | 期望 |
| ---- | ---- | ---- |
| 正例 | 给出工作记录，请求“整理本周工作” | 选中周报 Skill，按模板整理 |
| 负例 | “周报一般包含哪些内容？” | 回答写法，不要求生成周报 |
| 边界例 | “帮我写周报”，没有提供记录 | 询问或说明还缺哪些材料，不编造 |
| 异常例 | 指定从工单系统读取，但连接失败 | 说明哪些数据未获取，不能声称查到了 |

异常例需要先配置相应的数据工具；没有配置时，应识别为能力不可用，而不是把示例当成已连通。测试时分别记录是否正确触发、步骤是否执行、输出是否准确。模板或脚本改名、MCP 工具参数变化、模型更换后，都值得重跑受影响的样例；具体评测方法见 [[19-Agent评估]]。

## ⚠️ 常见问题

- 不触发：先确认宿主能发现 Skill，再检查描述是否覆盖用户的说法。
- 总是误触发：检查适用范围是否过宽，补充相似但不适用的负例。
- 找不到模板：检查相对路径、文件名和宿主是否允许读取该文件。
- 内容不准确：核对输入与工具返回，检查是否把缺失信息写成了事实。
- 工具不可用：说明缺失的数据，能基于现有材料完成的部分继续交付。

## 🎯 自测

> [!question]- 设计 Skill 的第一步是什么？
> 先确定适用任务、输入、输出与边界，再判断流程是否值得复用；高频任务和低频但关键的任务都可能适合。

> [!question]- 显式调用成功，能说明自动触发也正常吗？
> 不能。显式调用验证的是按名称加载；还要使用自然语言正例、负例分别测试自动选择。

> [!question]- 为什么还要测试脚本和模板？
> `SKILL.md` 只是指引。脚本可能缺少运行环境，模板可能路径错误，模型也可能没有按预期使用它们。

## ✅ 精通检查清单

- 能写出任务清晰、范围合适的 `name` 和 `description`。
- 能创建周报 Skill 的入口文件与模板，并验证宿主能否发现。
- 能区分显式调用和自动选择，设计正例、负例和异常例。
- 知道模型、工具、模板或脚本变化后，要检查相关样例。
