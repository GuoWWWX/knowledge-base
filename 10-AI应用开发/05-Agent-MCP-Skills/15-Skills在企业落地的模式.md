# 🏢 Skills 在企业落地的模式

> [!abstract] 一句话总结
> 团队共享 Skill 时，除了写好流程，还要解决谁维护、如何发布、怎么验证和出现问题后如何恢复。

## 📌 从一个 Skill 到团队共享

[[14-设计自己的Skill实战]] 中的 `weekly-report` 由一个人使用时，可以自己修改、自己测试。多人共用后，一次修改可能同时影响多个项目：例如描述改得太宽，导致普通问答也选中周报 Skill；模板路径改了，旧环境却找不到新文件。
因此企业落地要关注六件事：**组织复用、版本管理、分发、权限、评测和维护**。不必一开始就建设平台，先让一个团队用小范围流程跑通即可。

## 🗂️ 组织与复用

可以把通用 Skill 放在共享仓库，项目专属 Skill 随项目维护。例如：

```text
team-skills/
├── weekly-report/
│   ├── SKILL.md
│   └── references/report-template.md
├── code-review/
│   └── SKILL.md
└── README.md
```

README 说明每个 Skill 的用途、维护者、安装方式和适用宿主；数量多时，可以增加索引。团队先在一个项目验证，再将真正通用的部分提取共享；不同部门的周报模板不必强行做成同一份。

## 📦 版本、分发与回滚

Skill 的正文、模板和脚本都会影响结果，应一起纳入 Git，提交时记录改动原因。修改后由维护者评审，并用固定样例测试，再发布到实际使用的环境。发布可以先覆盖少量团队，确认效果后扩大范围。
常见分发方式如下，具体目录和可用机制取决于宿主：

| 方式 | 适用情况 | 注意事项 |
| ---- | -------- | -------- |
| 项目内目录 | 只服务当前项目 | 随项目版本维护，确认宿主能发现 |
| 共享仓库 | 多项目复用 | 记录所用版本或提交号 |
| 制品包 | 跨团队交付 | 打包入口文件及其依赖，核对完整性 |
| 宿主或平台配置 | 集中管理分配 | 确认生效范围、权限和更新方式 |

例如周报模板从“风险”改成“风险与待确认”，应同时发布新的 `SKILL.md` 和模板，避免只更新其中一个。若新版本造成明显回归，先定位指引、模型或依赖变化；需要时回退到可用版本，并重新验证。格式校验通过不代表指引一定有效，发布后仍要看实际输出。

## 🔐 谁能修改，谁能执行

共享 Skill 建议指定维护者，通过版本库权限和评审控制新增、修改、下线。引入外部 Skill 时，除了阅读正文，还应检查它引用的脚本、安装来源和外部访问；恶意指引可能诱导 Agent 泄露数据或执行不必要的操作。
Skill 的维护权限和运行时权限是两回事：即使 `weekly-report` 写了“查询工单”，宿主、MCP Server 和业务系统仍应分别校验是否允许访问。对发送邮件、写入数据等有外部影响的操作，应按实际授权和组织规则执行。

> [!warning] 指引不能代替安全边界
> 用户提供的文档、工具返回或外部 Skill 都可能含有误导性指令。限制工具权限、校验数据来源并保留可追溯记录，相关风险见 [[20-Agent安全与防注入]] 和 [[21-Agent权限治理与分级自治]]。

## 🧪 怎么评测与观察

先准备一组真实但已脱敏的请求，包含需要周报的正例、只问周报写法的负例，以及缺少材料或工单服务不可用的异常例。固定 Skill 版本、样例与评判标准，再比较修改前后的表现。

| 检查什么 | 怎么看 |
| -------- | ------ |
| 是否选对 Skill | 分别统计正例漏触发和负例误触发 |
| 步骤是否完成 | 检查模板、数据来源和失败处理是否符合要求 |
| 输出是否合格 | 抽查事实、分类和待确认项，必要时由业务人员评审 |
| 依赖是否可用 | 观察工单工具或脚本的失败、超时及影响 |

例如有 10 条应触发的请求，其中 8 条选中了周报 Skill，就有 2 条漏触发；还需要单独看不该触发的请求，不能只用总正确数掩盖误触发。这个数字仅用于说明统计方法，不代表实测结果。
具体可观测能力由宿主和应用提供：若能记录 Skill 名称、版本、工具调用、结果及失败原因，就能更快定位问题；不能假设所有平台都有 `skill.name` 等统一字段。日志还应避免记录不必要的敏感信息，详见 [[18-Agent可观测]] 和 [[19-Agent评估]]。

## 🔄 维护与下线

定期检查 Skill 是否仍有人使用、内容是否过时、维护者是否明确。工单接口、工具参数、模型或模板变化后，重跑受影响的样例；使用量低不等于应该立即删除，先确认它是否承担低频但重要的任务。
确定下线前，查找引用和使用方，通知相关维护者并提供替代方案；保留必要的历史版本，方便排查和恢复。依赖不可用时的降级与成本取舍见 [[22-Agent成本控制与降级]]。

## 🎯 自测

> [!question]- 为什么 Skill 改了文字也需要评审和测试？
> 描述会影响是否被选中，正文和配套文件会影响执行结果。即使文件格式正确，也可能误触发或生成不合格内容。

> [!question]- 周报 Skill 获准发布后，就能访问所有工单吗？
> 不能。发布权限只决定谁能提供指引；数据访问仍受宿主、工具和业务系统的授权约束。

> [!question]- 怎么判断一次修改是否退化？
> 固定样例、Skill 版本和评判标准，对比触发、执行与输出结果；出现差异时再排查模型或依赖是否也发生变化。

## ✅ 精通检查清单

- 能说明共享 Skill 的组织、分发和版本回滚方式。
- 能区分 Skill 修改权限与工具、数据的运行时权限。
- 能设计正例、负例和异常例，并分别观察漏触发与误触发。
- 知道模型或依赖变化后要回归，低频 Skill 下线前要确认影响。
