# ⚡ Prompt Caching 提示词缓存

> [!abstract] 一句话总结
> Prompt Caching 在服务支持时复用重复输入前缀的计算，可能减少延迟或输入费用；命中与计费规则取决于模型和服务商。

## 🎯 为什么需要缓存？

一个助手每次请求都带同一份较长的系统说明，后面才是每次不同的用户问题。若服务可以复用前面的计算，后续请求就可能减少重复处理。它缓存的是输入处理相关状态，不是直接把上次的答案返回给用户。

## ⚙️ 固定内容放前面

```text
固定前缀：系统规则 + 可共享的制度内容
动态后缀：当前用户允许查看的信息 + 当前问题
```

两次请求的前缀越一致，通常越有机会复用；如果开头混入时间戳、用户信息或顺序不稳定的工具列表，公共前缀可能变短。具体匹配粒度、长度门槛、缓存时间和路由规则以服务商文档为准。

## 🧩 和 CAG、上下文窗口的关系

缓存用于复用重复计算；长上下文指单次请求能容纳较多内容；CAG 是预加载知识的一种方案。缓存内容仍要计入上下文窗口，不代表模型一定理解全部信息。详细比较见 [[../03-知识库技术-RAG/02-RAG工业级进阶与检索调优|CAG 与长上下文]]。

## 💰 怎么验证是否划算？

对相同请求记录未缓存输入、缓存命中输入、输出 Token、延迟和账单；有的服务还收缓存写入费用。首次请求、缓存过期、模型切换或前缀变化可能导致未命中，不应套用固定“节省 90%”的结论。

## 🔐 用户数据怎么处理？

公共前缀只能包含可共享的信息；用户私有内容在应用层先做权限检查，再按照服务的数据处理政策决定是否发送。缓存不会替代租户隔离，也不能仅凭应用侧哈希相同就认定服务端必然命中。

> [!question]- 两次请求的前缀一样，为什么仍可能没有命中？
> 缓存可能已过期，也可能因模型、长度、路由或接口条件不满足而未命中。应检查接口返回的用量及相关规则。
