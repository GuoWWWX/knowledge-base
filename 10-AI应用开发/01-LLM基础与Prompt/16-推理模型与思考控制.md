# 🧠 推理模型与思考控制

> [!abstract] 一句话总结
> 推理模型可以在回答前投入额外计算来处理复杂任务。思考预算、可见性、计费和参数支持随模型及接口而变化，应以实际调用和评测为准。

## 🎯 为什么要控制推理投入？

代码审查可能需要追踪多个函数和异常分支；简单分类只需要判断一条消息属于哪个类别。两者适合的模型和计算预算可能不同。更多推理计算有时能改善复杂任务，但也可能增加等待和费用，不能保证结果正确。

## 🧩 要区分的概念

| 概念 | 含义 | 注意 |
| :--- | :--- | :--- |
| 推理时计算 | 生成答案时投入的计算 | 与训练阶段计算不同，效果需评测 |
| 思考预算 / effort | 部分接口允许控制推理投入 | 档位和可用值随型号、接口变化 |
| 推理 Token | 某些模型用于内部推理的输出 Token | 用量和计费口径以接口及账单为准 |
| 可见解释 | 返回给用户的步骤或摘要 | 不一定等同完整内部推理过程 |

## ⚙️ 一次请求如何评估？

```mermaid
flowchart LR
    Q["业务问题"] --> M["选择模型与可用的推理设置"] --> A["获得回答"]
    A --> V["核对事实或工具结果"] --> E["记录质量、延迟和费用"]
```

先在相同的问题集上比较不同模型和推理档位，再根据正确率、延迟、输出限制及成本选择。调用前查当前模型的参数文档，不假定所有模型都支持相同的 `effort` 或关闭思考。

## 💡 预留输出空间

部分服务将推理 Token 与最终回答纳入输出预算，预算太小可能导致回答截断甚至没有可见正文。应读取响应完成状态与用量，按实际任务设置上限；不同服务的计费和用量字段并不统一。

## 📝 提示词怎么写？

清楚描述任务、已知条件、限制和交付格式。例如“检查这段代码是否存在重复扣款，指出触发条件和证据”，比要求模型机械输出固定数量的推理步骤更容易检查。是否增加分步指令应通过任务评测决定，不应假设始终有效或始终有害。

> [!question]- 高推理档位一定比低档位更准确吗？
> 不一定。效果随模型、任务和样本变化；提高计算预算可能增加延迟和费用，应在相同测试集上比较。
