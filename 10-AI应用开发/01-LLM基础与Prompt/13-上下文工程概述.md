# 上下文工程概述

> [!abstract] 一句话总结
> 上下文工程是为 LLM 构造“正确工作记忆”的系统方法：选择、压缩、排序、隔离和验证模型本次需要的信息。

## 🎯 本节定位

- **本章第 13 课，上下文工程的开篇**。前置：[[03-上下文窗口]]；预算、压缩、缓存三件套见 [[14-上下文窗口预算管理]]、[[15-上下文压缩策略]]、[[17-Prompt-Caching提示缓存]]。

## 📌 这是什么

Prompt 工程关注“指令怎么写”，上下文工程关注“模型本次应该看到什么、以什么结构看到、占多少预算、哪些不能看到”。它是 RAG、Agent、长对话、代码助手的基础能力。

## 🤔 解决什么问题 / 为什么需要

LLM 应用效果往往受上下文质量决定。模型拿到错误资料会认真地错，拿到太多噪声会漏掉关键点，拿不到权限内证据会幻觉。

| 目标 | 做法 |
| ---- | ---- |
| 相关性 | 检索、重排、过滤 |
| 可控成本 | Token 预算、缓存、压缩 |
| 安全 | 权限裁剪、数据隔离 |
| 可验证 | 引用来源、结构化证据 |
| 稳定 | 固定上下文布局和评估集 |

## 🧩 核心概念

| 概念 | 含义 | 备注 |
| ---- | ---- | ---- |
| Context Assembly | 上下文组装 | 把系统提示、问题、证据、历史合并 |
| Retrieval | 检索 | 从知识库找候选材料 |
| Rerank | 重排 | 提升最相关证据优先级 |
| Compression | 压缩 | 在保真前提下降低 Token |
| Memory | 记忆 | 保存长期偏好和任务状态 |
| Context Evaluation | 上下文评估 | 测召回、噪声、答案质量 |

## ⚙️ 工作流程

```mermaid
flowchart LR
    A[用户任务] --> B[意图识别]
    B --> C[检索/读取候选上下文]
    C --> D[权限过滤]
    D --> E[重排与压缩]
    E --> F[按模板组装]
    F --> G[模型回答/工具调用]
    G --> H[校验与记录]
```

一个常见上下文布局：

```text
1. System: 稳定规则和安全边界
2. Developer: 应用流程和输出契约
3. User: 当前任务
4. Evidence: 检索资料，带来源 ID
5. History/Memory: 与当前任务相关的状态
```

## 💻 代码实践

```java
Context context = contextAssembler.assemble(ContextRequest.builder()
    .user(user)
    .question(question)
    .tokenBudget(24_000)
    .retrievalTopK(20)
    .rerankTopK(6)
    .includeConversationSummary(true)
    .build());

String answer = chatClient.prompt(context.toPrompt()).call().content();
```

## ⚠️ 踩坑与注意事项

- [ ] **只优化 Prompt，不优化证据**：没有正确上下文，Prompt 再漂亮也有限。
- [ ] **把所有记忆都塞进去**：长期记忆要按相关性和权限筛选。
- [ ] **忽略上下文顺序**：关键规则、问题、证据位置会影响模型注意。
- [ ] **没有引用 ID**：答案无法追溯来源。

## 🎯 面试问题

> [!question] 高频问题
> - Q: 上下文工程和 RAG 的关系？
>   - A: RAG 是上下文工程的一种资料获取方式；上下文工程还包括预算、压缩、排序、记忆和安全。
> - Q: 好上下文的标准是什么？
>   - A: 相关、完整、低噪声、权限正确、格式清晰、可追溯。
> - Q: 为什么长上下文不能替代上下文工程？
>   - A: 长窗口增加容量，但不会自动选择正确信息，还会带来成本、延迟和 context rot。
