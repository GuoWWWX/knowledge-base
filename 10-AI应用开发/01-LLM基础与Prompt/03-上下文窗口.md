# 上下文窗口

> [!abstract] 一句话总结
> 上下文窗口是模型一次调用能“看见”的 Token 范围，包括系统提示、用户问题、历史消息、检索资料、工具结果和即将生成的输出。

## 🎯 本节定位

本章第 3 课，承接 [[02-Token与Tokenizer]]。窗口内的预算分配见 [[14-上下文窗口预算管理]]，信息压缩见 [[15-上下文压缩策略]]，重复前缀的缓存见 [[17-Prompt-Caching提示缓存]]，系统的上下文方法论见 [[13-上下文工程概述]]。

## 📌 这是什么

上下文窗口可以理解为 LLM 的工作记忆。模型生成答案时只能引用当前请求里放进去的内容，以及训练中形成的参数记忆；没有放入窗口的对话历史、文档和实时事实，模型并不能自动访问。

## 🤔 解决什么问题 / 为什么需要

LLM 应用的很多问题不是“模型不聪明”，而是上下文放错了：关键信息没放进去、无关信息塞太多、历史消息遮蔽了新指令、工具结果太长导致溢出。

| 问题 | 上下文原因 |
| ---- | ---- |
| 答非所问 | 任务、约束、输出格式不明确 |
| 忘记前文 | 历史消息被截断或压缩过度 |
| 幻觉 | 没有提供可信证据或证据不完整 |
| 成本高 | 把重复系统提示和无关文档反复塞入 |

## 🧩 核心概念

| 概念 | 含义 | 备注 |
| ---- | ---- | ---- |
| Context Window | 一次调用可处理上下文的容量 | 输入和输出的具体限制以模型文档为准 |
| Input Tokens | 请求里已有的 Token | system/user/history/docs/tools |
| Output Tokens | 模型本次可生成的 Token | 需要预留 |
| Context Rot | 长上下文中的相关信息可能被遗漏 | 效果需要结合模型和任务评测 |
| Truncation | 截断超出窗口的内容 | 容易删掉关键证据 |
| Prompt Cache | 缓存重复前缀 | 可降低延迟和成本 |

## ⚙️ 工作原理 / 流程

```mermaid
flowchart TD
    A[系统提示] --> E[上下文窗口]
    B[用户问题] --> E
    C[历史消息] --> E
    D[RAG/工具结果] --> E
    E --> F[模型生成]
    F --> G[输出 Token]
```

典型构造顺序：
1. 放稳定规则：角色、边界、安全策略、输出格式。
2. 放当前任务：用户问题和本轮目标。
3. 放必要证据：RAG 文档、数据库结果、工具返回。
4. 放少量历史：只保留对当前任务有用的状态。
5. 预留输出：避免输入占满导致答案被截断。

## 💻 代码实践

下面是流程示意，`promptBuilder` 和相关组件由应用自行实现；具体预算需要按实际模型和请求统计。

```java
int maxWindow = 128_000;
int outputReserve = 4_000;
int inputBudget = maxWindow - outputReserve;

PromptParts parts = promptBuilder
    .system(systemRules)
    .history(memory.selectRelevant(userQuestion))
    .documents(retriever.topK(userQuestion, 5))
    .user(userQuestion)
    .fitToBudget(inputBudget);
```

## ⚠️ 踩坑与注意事项

- [ ] 窗口变长不代表效果更好，过多无关信息可能干扰模型。
- [ ] 预留输出空间，避免输入占满窗口后回答被截断。
- [ ] 按相关性筛选、摘要或结构化保存聊天历史。
- [ ] 清晰组织关键约束和证据，避免它们相互混淆。

## 🎯 面试问题

> [!question]- 上下文窗口和训练数据有什么区别？
> 训练数据是用于训练的样本，模型通过训练调整参数并形成能力与知识表征，不能等同于把原文完整存入参数；上下文窗口是本次调用可见的输入及生成空间。

> [!question]- 为什么长上下文仍需要 RAG？
> 长窗口解决容量，不解决资料选择、时效性、权限、证据排序和成本问题。

> [!question]- 如何处理上下文溢出？
> 先做预算，删无关内容，再摘要历史，最后压缩证据并预留输出 Token。
