# 上下文压缩策略

> [!abstract] 一句话总结
> 上下文压缩是在尽量保留任务相关信息和可验证证据的前提下，减少传给模型的 Token 数。

## 🎯 本节定位

- **本章第 15 课，承接 [[14-上下文窗口预算管理]]**。压缩是预算超限时的执行手段，总览见 [[13-上下文工程概述]]；压缩前后的 Token 计量见 [[02-Token与Tokenizer]]。

## 📌 这是什么

上下文压缩不是简单“把文本变短”，而是按任务目标保留关键事实、约束、实体、时间、证据来源和未解决问题。压缩对象包括聊天历史、RAG 文档、工具结果、日志、代码 diff 等。

## 🤔 解决什么问题 / 为什么需要

长上下文会带来成本、延迟、溢出和注意力下降。压缩让系统在有限窗口内放入更高密度的信息。

| 原始内容 | 压缩目标 |
| ---- | ---- |
| 长对话 | 当前任务状态、决策、待办 |
| 文档段落 | 与问题相关的证据句和来源 |
| 工具结果 | 结构化字段和异常摘要 |
| 日志 | 时间线、错误码、关键堆栈 |
| 代码 | 相关函数、接口契约、变更点 |

## 🧩 核心概念

| 概念 | 含义 | 备注 |
| ---- | ---- | ---- |
| Extractive Compression | 抽取式压缩 | 保留原文片段，证据更强 |
| Abstractive Summary | 生成式摘要 | 更短但可能引入误差 |
| Hierarchical Summary | 分层摘要 | 先局部后全局 |
| Query-focused Compression | 面向问题压缩 | 只保留与当前问题相关内容 |
| Lossy/Lossless | 有损/无损 | 大多数 LLM 摘要是有损 |
| Citation Preservation | 保留引用 | 防止压缩后不可追溯 |

## ⚙️ 工作流程

```mermaid
flowchart LR
    A[原始上下文] --> B[按任务筛选]
    B --> C[抽取关键片段]
    C --> D[生成摘要/结构化]
    D --> E[保留来源 ID]
    E --> F[校验是否覆盖问题]
```

压缩提示模板：

```text
目标：为回答用户问题压缩资料。
用户问题：{question}
要求：
1. 只保留与问题直接相关的信息。
2. 保留数字、时间、实体、限制条件。
3. 每条结论后保留来源 ID。
4. 不要引入原文没有的信息。
输出：
- facts: ...
- missing_info: ...
```

## 💻 代码实践

```java
List<Document> compressed = docs.stream()
    .map(doc -> compressor.compress(QueryFocusedRequest.builder()
        .question(question)
        .sourceId(doc.id())
        .content(doc.content())
        .maxTokens(600)
        .preserveCitations(true)
        .build()))
    .toList();
```

压缩后仍要做回答前检查：压缩内容是否覆盖问题、是否丢了关键限定词、是否仍能追溯来源。

## ⚠️ 踩坑与注意事项

- [ ] **摘要引入幻觉**：摘要模型可能补充原文没有的信息。
- [ ] **丢失否定词和限制条件**：“不支持”“仅限”“除外”最容易被压掉。
- [ ] **压缩后无来源**：答案无法引用和审计。
- [ ] **对所有内容同一种压缩**：日志、合同、代码、聊天历史需要不同策略。
- [ ] **压缩过度**：短到失去证据链，反而让最终模型幻觉。

## 🎯 面试问题

> [!question] 高频问题
> - Q: 抽取式压缩和生成式摘要怎么选？
>   - A: 高风险事实问答优先抽取式；低风险长对话记忆可用生成式摘要。
> - Q: 如何避免压缩丢关键信息？
>   - A: 面向问题压缩，保留数字/时间/实体/否定词/来源，并用覆盖性检查。
> - Q: 上下文压缩和 RAG 重排区别？
>   - A: 重排决定哪些片段优先；压缩决定入选片段以什么密度进入窗口。
