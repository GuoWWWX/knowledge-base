# 向量库选型对比

> [!abstract] 一句话总结
> 向量库选型不是看谁最强，而是看数据规模、团队运维能力、权限过滤、现有技术栈和成本。

## 📌 选型原则

先用最简单能满足需求的方案。知识库早期通常瓶颈在解析、切分和评估，不在向量库本身。

## 📊 常见选择

| 方案 | 优势 | 适合场景 |
| ---- | ---- | ---- |
| pgvector | 架构简单，复用 PostgreSQL | 小中规模、Java 业务系统 |
| Milvus | 专用向量库，扩展性强 | 大规模、高 QPS |
| Elasticsearch/OpenSearch | 关键词强，Hybrid 方便 | 已有搜索体系 |
| Redis Vector | 延迟低，缓存友好 | 小规模低延迟检索 |
| 云向量库 | 免运维 | 快速上线、云上业务 |

## 🎯 决策速查

```text
已有 PostgreSQL + 小中规模：pgvector
百万/千万级向量 + 高并发：Milvus
关键词检索很重要：Elasticsearch/OpenSearch + 向量
原型验证：任选框架内置或本地向量库
```

## 🧩 必问问题

- 数据量现在多少，半年后多少？
- 是否需要租户隔离和权限过滤？
- 是否需要混合检索？
- 团队能否运维新中间件？
- 延迟目标是多少？
- 是否需要云上托管？

## ⚠️ 踩坑与注意事项

- [ ] 不要为了“先进”提前引入重型集群。
- [ ] 不要忽略删除、更新、重建索引流程。
- [ ] 不要只测 demo 数据，要用真实 chunk 压测。
- [ ] 不要把权限控制完全交给应用层事后过滤。

## 🎯 面试问题

> [!question] 高频问题
> - **Q: 企业 RAG 怎么选向量库？**
>   - A: 小中规模优先 pgvector 简化架构；大规模高并发选 Milvus；关键词强诉求可用 Elasticsearch/OpenSearch 混合检索。
> - **Q: 向量库选型最容易忽略什么？**
>   - A: metadata 过滤、权限隔离、删除更新、备份恢复和压测。
