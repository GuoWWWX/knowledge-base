# 🗃️ 状态管理与会话持久化

> [!abstract] 一句话总结
> 会话状态让 Agent 找回一段对话及相关运行信息；持久化决定进程重启后能否恢复，用户和会话隔离仍需要应用正确提供身份。

## 🎯 一个会话怎么找回？

用户第一次说“我的订单是 A123”，下一次问“它到哪了”。如果两次请求携带同一用户和会话标识，且状态存储已正确配置，Agent 才有机会找回前文；换了会话或状态未保存时，不能假设模型自然记住。

## ⚙️ Agent 与状态存储

`ReActAgent` 可以配置 `AgentStateStore`；官方提供本地文件以及其他存储扩展。Harness 的默认行为与配置项可能随版本变化，应确认实际使用的实现、存储路径和保留策略。
下面是官方文档风格的配置片段，假设模型已准备，省略 imports 与依赖；没有运行验证。

```java
ReActAgent agent = ReActAgent.builder().name("assistant")
        .sysPrompt("你是订单助手。")
        .model(model)
        .stateStore(new JsonFileAgentStateStore(Paths.get("./agent-state")))
        .build();
```

调用时通过 `RuntimeContext` 提供服务端认证的用户与会话标识。文件存储适合本地练习；多实例服务需要根据部署方式选择共享或分布式存储，并测试恢复与并发更新。

## 🔄 一次保存和恢复的过程

例如已认证用户 `u1` 使用会话 `s1`：第一次请求开始时按 `(u1, s1)` 加载状态；找不到旧记录时开始新的对话。调用完成后，配置了 `stateStore` 的 Agent 保存状态；第二次仍使用 `(u1, s1)` 时加载该会话的内容。若切换为 `(u1, s2)`，就会使用另一个会话。
下面的片段假设 `userId` 由服务端认证得到，`sessionId` 已验证属于该用户；没有配置状态存储时不能指望自动持久化。

```java
RuntimeContext ctx = RuntimeContext.builder()
        .userId(userId).sessionId(sessionId).build();
agent.call(new UserMessage("我的订单到哪了？"), ctx);
```

返回值是异步调用结果，需要由上层订阅或在适当的非事件循环线程等待；不同版本的重载以官方文档为准。存储键的区分只能帮助定位状态，不代替业务鉴权，也不保证跨节点竞争、存储故障和过期删除都已经处理。

## 🔐 隔离和恢复应检查什么？

- 用户身份由服务端认证生成，会话 ID 需要检查归属，不能只相信客户端传入值。
- 测试同一会话并发请求、不同用户隔离、写入失败、进程重启和状态过期。
- 对敏感对话数据规定保留时间、访问权限和删除策略，日志避免保存密钥。
- 会话状态、长期记忆、知识库是不同的内容，压缩或召回时仍可能遗漏信息，见 [[06-高级特性-长短期记忆与RAG]]。

> [!question]- 把 sessionId 原样交给客户端生成，就完成会话隔离了吗？
> 没有。服务端还要验证这个会话属于当前用户，并确保存储键和权限设计不会让其他用户读取。
