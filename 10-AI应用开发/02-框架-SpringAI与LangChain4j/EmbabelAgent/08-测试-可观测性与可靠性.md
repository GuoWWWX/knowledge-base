# Embabel Agent 测试、可观测性与可靠性

> [!abstract] 一句话总结
> Embabel 的可测性来自 Action 是普通方法、LLM 调用可用 `FakeOperationContext` 截获、完整规划可用 `EmbabelMockitoIntegrationTest` 验证；生产可靠性还必须覆盖路径、Prompt、类型语义、工具副作用、预算和执行轨迹。

## 1. Agent 不能只测最终文本

一个 Agent 结果“看起来不错”，仍可能存在：

- 选错 Agent/Goal。
- 规划绕远路或跳过验证。
- Prompt 没带关键约束。
- 模型调用了越权工具。
- 结构正确但业务字段不合法。
- Action 重试造成重复副作用。
- 任务没有预算和终止上限。

测试金字塔：

```text
少量真实模型 E2E / 评测集
          ↑
完整 Agent 集成测试（模型 Mock）
          ↑
Action + Prompt 单元测试
          ↑
纯领域逻辑单元测试
```

不要让每个测试都调用真实模型。那会慢、贵、不稳定，也难以定位回归。

## 2. 测试依赖

```xml
<dependency>
    <groupId>com.embabel.agent</groupId>
    <artifactId>embabel-agent-test</artifactId>
    <version>${embabel-agent.version}</version>
    <scope>test</scope>
</dependency>

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-test</artifactId>
    <scope>test</scope>
</dependency>
```

## 3. 纯 Java 逻辑先直接测

```java
@Test
void reviewRejectsMissingDays() {
    var agent = new LearningPlanAgent();
    var request = new LearningRequest("Embabel", 3, "Java");
    var draft = new DraftPlan(request, List.of(
            new DailyTask(1, "setup", "run app"),
            new DailyTask(2, "actions", "add action")));

    var review = agent.review(draft);

    assertFalse(review.approved());
    assertTrue(review.issues().contains("每天应有一个任务"));
}
```

没有模型、Spring 和 Planner 的代码，不要强行用框架集成测试。先把领域规则测准。

## 4. 用 `FakeOperationContext` 测 LLM Action

```java
import com.embabel.agent.domain.io.UserInput;
import com.embabel.agent.test.unit.FakeOperationContext;
import org.junit.jupiter.api.Test;

import static org.junit.jupiter.api.Assertions.*;

class LearningPlanAgentTest {

    @Test
    void understandBuildsExpectedPromptAndType() {
        var context = FakeOperationContext.create();
        context.expectResponse(
                new LearningRequest("Embabel Agent", 7, "Java backend"));

        var result = new LearningPlanAgent().understand(
                new UserInput("我是 Java 后端，7 天学 Embabel"),
                context);

        assertEquals("Embabel Agent", result.topic());
        assertEquals(7, result.days());

        var invocation = context.getLlmInvocations().getFirst();
        assertTrue(invocation.getPrompt().contains("7 天"));
        assertEquals(
                "understand-learning-request",
                invocation.getInteraction().getId().getValue());
    }
}
```

它验证的是：

- Action 如何构造 Prompt。
- 是否请求正确输出类型。
- interaction ID、模型参数和 ToolGroup 是否正确。
- 模型返回预期对象时领域代码怎样处理。

它不验证 Planner 能否把多个 Action 串起来。

## 5. 完整流程集成测试

```java
@TestPropertySource(properties = {
        "embabel.models.default-llm=test-model",
        "embabel.agent.platform.models.openai.api-key=test-key",
        "spring.autoconfigure.exclude=" +
                "org.springframework.shell.boot.ShellRunnerAutoConfiguration"
})
class LearningPlanIntegrationTest
        extends EmbabelMockitoIntegrationTest {

    @Test
    void completesTheWholeTypedWorkflow() {
        var request = new LearningRequest("Embabel Agent", 2, "Java");
        var draft = new DraftPlan(request, List.of(
                new DailyTask(1, "Setup", "Start Shell"),
                new DailyTask(2, "Planning", "Inspect Blackboard")));

        whenCreateObject(
                prompt -> prompt.contains("Extract a learning request"),
                LearningRequest.class)
                .thenReturn(request);

        whenCreateObject(
                prompt -> prompt.contains("one practical task for each day"),
                DraftPlan.class)
                .thenReturn(draft);

        var invocation = AgentInvocation.create(
                agentPlatform,
                LearningPlan.class);

        LearningPlan result = invocation.invoke(
                new UserInput("Java 开发者两天学习 Embabel"));

        assertEquals("Embabel Agent", result.topic());
        assertEquals(2, result.tasks().size());

        verifyCreateObjectMatching(
                prompt -> prompt.contains("Extract a learning request"),
                LearningRequest.class,
                llm -> llm.getToolGroups().isEmpty());
        verifyCreateObjectMatching(
                prompt -> prompt.contains("one practical task for each day"),
                DraftPlan.class,
                llm -> llm.getToolGroups().isEmpty());
        verifyNoMoreInteractions();
    }
}
```

如果测试工程引入了具体模型 Provider Starter，Spring 创建 Provider 配置 Bean 时仍可能要求 API Key。这里的 `test-key` 只用于让配置 Bean 完成初始化；`EmbabelMockitoIntegrationTest` 已替换底层 `LlmOperations`，不会把请求发给真实模型。测试不验证命令行交互，因此显式排除 `ShellRunnerAutoConfiguration`，避免 Surefire 进程停在 JLine 输入上。

集成测试覆盖：

- Spring 是否扫描到 Agent。
- Goal 能否按输出类型被找到。
- Planner 能否从初始输入走到目标。
- Blackboard 类型是否正确流动。
- LLM 调用次数和顺序是否符合设计。
- 条件失败时 Process 是否正确停止或换路径。

## 6. 必测路径

| 类型 | 示例 |
| ---- | ---- |
| 正常路径 | 理解 → 草稿 → 审核 → 完成 |
| Goal 不可达 | 删除或禁用产生某个类型的 Action |
| 条件不满足 | 草稿任务数不足，审核拒绝 |
| 结构绑定失败 | 模型返回无法绑定的数据 |
| Action 异常 | 外部服务超时后重试，耗尽后 Process 失败 |
| 显式重规划 | 新状态写入 Blackboard 后选择备用 Action |
| 工具错误 | MCP 返回错误或超时 |
| 预算终止 | 超过最大 Action/Token/Cost |
| 取消 | 运行中终止，状态不应仍显示成功 |
| 副作用幂等 | 同一 Action 重试不重复提交/发信 |

## 7. 真实模型评测

Mock 测试证明“程序按预期接线”，不能证明真实模型质量。准备固定评测集：

```text
case_id
input
expected_goal
must_include_facts
forbidden_actions
max_actions
max_tokens
max_cost
semantic_assertions
```

至少记录：

- Goal/Agent 选择准确率。
- 端到端成功率。
- 结构化绑定失败率。
- 平均/95 分位 Action 数。
- Token、成本、耗时。
- 工具错误率和重试次数。
- 人工评分与不可接受错误。

升级 Embabel、Spring AI、模型或 Prompt 时都跑同一评测集，否则“感觉更聪明”无法作为工程结论。

## 8. 可观测性

依赖：

```xml
<dependency>
    <groupId>com.embabel.agent</groupId>
    <artifactId>embabel-agent-starter-observability</artifactId>
    <version>${embabel-agent.version}</version>
</dependency>

<dependency>
    <groupId>io.opentelemetry</groupId>
    <artifactId>opentelemetry-exporter-zipkin</artifactId>
</dependency>
```

配置：

```yaml
embabel:
  agent:
    platform:
      observability:
        enabled: true
        service-name: embabel-learning

management:
  tracing:
    export:
      enabled: true
    sampling:
      probability: 1.0
  zipkin:
    tracing:
      endpoint: http://localhost:9411/api/v2/spans
```

Embabel 可以跟踪：

- Process 生命周期。
- Planner 和 Action。
- LLM 调用。
- Tool 调用。
- Token、成本和耗时等指标。

注意 `1.5.0` 的配置前缀是 `embabel.agent.platform.observability.*`。旧的 `embabel.observability.*` 可能被静默忽略。

## 9. 日志与 Trace 的安全

默认不要记录：

- API Key、Authorization Header。
- 用户隐私和完整业务数据。
- 未过滤的文件内容。
- MCP `_meta` 中的临时凭据。
- 模型完整思维过程。

开发环境可以打开 Prompt/Response 辅助调试；生产环境应按字段脱敏、采样并设置留存期限。

## 10. 超时、预算和终止

至少设置三类上限：

```text
Process 层：最大 Action 数、Token、成本、总时长
Action 层：重试次数、退避、幂等性
Tool Loop 层：最大迭代数、单工具超时、批次超时
```

示例：

```yaml
embabel:
  agent:
    platform:
      toolloop:
        max-iterations: 20
        parallel:
          per-tool-timeout: 30s
          batch-timeout: 60s
```

程序化限制：

```java
var options = new ProcessOptions()
        .withAdditionalEarlyTerminationPolicy(
                EarlyTerminationPolicy.maxActions(12));
```

“模型最终应该会停”不是终止策略。

## 11. Action 重试与副作用

重试适合：

- 临时网络失败。
- 结构化绑定偶发失败。
- 可幂等查询。

重试不适合直接包住：

- 发邮件。
- 支付。
- Git push。
- 数据库无幂等写入。
- 部署和删除操作。

正确做法是先建立幂等键或把动作拆成：

```text
准备命令（readOnly）
  → 人工/策略审批
  → 带幂等键执行副作用
  → 查询外部结果确认
```

## 12. 上线检查表

- [ ] 所有 Goal 有正常、不可达和条件失败测试。
- [ ] LLM Action 用 Fake 验证 Prompt、类型、模型参数和工具。
- [ ] 完整流程用 Mock 模型验证规划路径。
- [ ] 真实模型评测集有基线。
- [ ] Process、Action、LLM、Tool 都有 trace/correlation ID。
- [ ] 最大 Action、Token、Cost、Tool Loop 和超时已限制。
- [ ] 写 Action 具备幂等、审批或补偿。
- [ ] Prompt/工具结果/凭据已按数据等级脱敏。
- [ ] 取消是真正终止后端 Process。
- [ ] 框架和模型升级有回归评测。

## 最小验证

1. 为 `understand` 写 `FakeOperationContext` 单元测试。
2. 为完整 `UserInput → LearningPlan` 写 Mock 集成测试。
3. 故意让审核失败，确认目标不会伪成功。
4. 设置最大 Action 数并构造循环，确认能终止。
5. 打开本地 Zipkin，确认一次 Process 下能看到 Action 和 LLM span。

## 自测题

> [!question]- Q1：Fake 单元测试与 Mock 集成测试各证明什么？
> Fake 单测证明单个 Action 的 Prompt、模型选项和领域处理；集成测试证明 Spring 扫描、Goal 发现、Planner 路径和 Blackboard 数据流可以完整工作。

> [!question]- Q2：为什么 Mock 测试通过后仍需真实模型评测？
> Mock 返回是人为设定的，不能衡量真实模型的意图理解、结构绑定、工具选择和内容质量；固定评测集才能量化这些非确定性能力。

> [!question]- Q3：Action 配了自动重试为什么还不够可靠？
> 外部副作用可能已成功但响应丢失，盲目重试会重复操作；必须结合幂等键、结果确认、审批或补偿，而不是只增加重试次数。
