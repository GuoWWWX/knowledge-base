# Embabel Agent 本章总结与复习

> [!abstract] 一句话总结
> Embabel 的主线只有一条：用领域类型表示世界状态，用 Action 声明状态变化，用 Goal 定义终点，用 Condition 补充布尔约束，再由 Planner 在 AgentProcess 中选择路径；模型和工具只是 Action 的实现手段。

## 1. 全章主线

```mermaid
flowchart LR
    A[用户/系统输入] --> B[初始 Blackboard]
    B --> C[选择 Agent 与 Goal]
    C --> D[Planner 读取当前世界状态]
    D --> E[选择可执行 Action]
    E --> F[普通 Java / LLM / Tool / MCP]
    F --> G[返回领域对象写入 Blackboard]
    G --> H{Goal 满足?}
    H -->|否| D
    H -->|是| I[返回类型化结果]
```

如果只记一句：

> **参数是前置事实，返回值是新事实，Goal 是终点，Planner 负责连路。**

## 2. 核心对象速查

| 对象/注解 | 责任 | 不负责 |
| --------- | ---- | ------ |
| `@Agent` | 定义可复用 Agent 边界并注册 Spring Bean | 不代表一次任务实例 |
| `@Action` | 声明一个状态变换 | 不自动保证副作用安全 |
| `@AchievesGoal` | 声明 Action 达成的终点 | 不替代结果业务校验 |
| `@Condition` | 表达类型之外的布尔事实 | 不应执行副作用 |
| Blackboard | 保存一次 Process 的类型化状态 | 不是 ChatMemory 或业务数据库 |
| Planner | 根据状态和 Goal 选 Action | 不凭空创造未声明能力 |
| `OperationContext` | Action 的当前运行上下文 | 不是全局单例会话 |
| `PromptRunner` | 模型、Prompt、结构化输出和工具调用 | 不负责高层 Action 路径 |
| `AgentInvocation<T>` | 发起类型化调用 | 不等于运行中的 Process |
| `AgentProcess` | 一次任务的状态、轨迹和结果 | 不等于 Agent 定义 |

## 3. 三层分工

```text
Spring AI / Provider 层
  模型、消息、结构化输出、Tool Calling、MCP 基础接入

Embabel Agent 层
  类型状态、Action、Goal、Condition、Planner、Process

产品 Runtime 层
  用户会话、权限审批、沙箱、文件/Git、取消恢复、桌面 UI
```

因此 Embabel 可以作为桌面编码 Agent 的高层编排层，但不会自动提供 Codex Desktop 的完整 Runtime。

## 4. Planner 与模式速查

### Planner

| Planner | 决策方式 | 首选场景 |
| ------- | -------- | -------- |
| GOAP | 找到通往 Goal 的低成本路径 | 默认业务流程 |
| Utility | 每轮选净价值最高 Action | 无固定终点的持续行为 |
| Hybrid | Utility 行为，Goal 达成即停止 | 探索 + 明确终点 |
| Supervisor | LLM 根据类型/状态选 Action | 语义驱动且接受非确定性 |

### 执行模式

| 模式 | 范围 |
| ---- | ---- |
| Focused | 调用方明确目标结果，范围最小 |
| Closed | 先选一个 Agent，只用其内部 Action |
| Open | 全平台选 Goal 并跨 Agent 组合 Action |

生产默认思路：**Focused + GOAP，逐步放宽，不从 Open + Supervisor 起步。**

## 5. 一次执行的因果链

以学习计划为例：

```text
1. UserInput 进入 Blackboard
2. understand(UserInput) 可执行，产生 LearningRequest
3. draft(LearningRequest) 可执行，产生 DraftPlan
4. review(DraftPlan) 可执行，产生 ReviewedPlan
5. planApproved(ReviewedPlan) 求值为 true
6. finish(DraftPlan, ReviewedPlan) 的输入与 pre 都满足
7. finish 产生 LearningPlan，并达成 Goal
8. AgentInvocation 从最终 Blackboard 取得 LearningPlan
```

中断其中任何一条边，都能解释 Goal 为什么不可达。排查时先看类型和条件，不要先怀疑模型。

## 6. Action 设计口诀

> **一个业务步骤，一个明确产物；能用类型表达，不用魔法字符串；有副作用先谈幂等。**

检查清单：

- 输入是否都是必要领域事实？
- 输出是否表示一个清楚的业务阶段？
- 是否把过多流程塞进一个 Action？
- 是否把无意义的小函数都变成 Action？
- `readOnly` 是否如实反映副作用？
- 重试或 `canRerun` 是否会重复写操作？
- Goal 描述是否能用于真实意图选择？

## 7. 模型与工具口诀

> **Action 决定做哪件事，PromptRunner 决定这件事里怎样用模型和工具。**

- 结构化阶段结果使用 `createObject`。
- 可选识别失败才用 `createObjectIfPossible`。
- 模型按默认/角色解耦，少硬编码模型名。
- Tool 只暴露给需要它的 PromptRunner。
- MCP 先过滤成 ToolGroup，再给 Action 使用。
- ToolCallContext 用于租户/关联/临时认证元数据。
- Planner 最大 Action 与 Tool Loop 最大迭代要分别限制。

## 9. 高频错误

| 现象 | 优先原因 |
| ---- | -------- |
| `agents` 为空 | Spring 扫描范围、`@Agent`、`scan=false` |
| 找不到结果类型 Agent | 缺 `@AchievesGoal` 或 Goal 输出不兼容 |
| Goal 不可达 | 缺少产生某输入类型/条件的 Action |
| Action 参数无法绑定 | 同类型冲突、参数名未保留、binding 不匹配 |
| 结构化输出总失败 | schema/Prompt 不清、模型能力不足 |
| Action 不断重复 | `canRerun`、循环状态、终止上限错误 |
| 写操作重复 | 重试但无幂等键 |
| 配置看似存在却不生效 | 使用旧版本属性前缀 |
| 示例无法编译 | 混用了 `0.3.x` README/Template 与 `1.5.0` API |

## 10. 30 秒面试表达

> Embabel Agent 是 JVM 上的强类型 Agent 规划框架。开发者用 Action 方法的输入输出类型描述前置事实和效果，用 AchievesGoal 声明终点，用 Condition 表达额外约束；运行时把领域对象放入 Blackboard，GOAP 等 Planner 根据当前状态动态选择路径。Action 内可以通过 OperationContext 调 Spring AI 模型和工具。它比直接写 Prompt 工作流更适合领域丰富、需要测试和动态重规划的 Java Agent，但不替代桌面 Agent 的沙箱、会话和工具 Runtime。

## 11. 自测题

> [!question]- Q1：为什么说 Embabel 是类型驱动规划？
> Action 的领域参数定义前置事实，返回类型定义效果；Blackboard 当前有哪些类型决定 Action 是否可执行，Goal 输出类型定义终点，Planner 据此构图和选路。

> [!question]- Q2：有 `ReviewedPlan` 为什么还要 `planApproved`？
> 类型存在只能证明审核执行过，不能证明审核通过；布尔条件或更强的 `ApprovedPlan` 类型才能表达结果语义。

> [!question]- Q3：GOAP 与 Supervisor 最大差异？
> GOAP 根据显式前置/效果和成本计算路径，确定性更强；Supervisor 让 LLM结合 Action 描述、schema 和 Blackboard 选择下一步，更灵活但更贵、更难复现。

> [!question]- Q4：`OperationContext` 与 Blackboard 参数有什么不同？
> Blackboard 参数是规划依赖的领域事实；OperationContext 是框架注入的基础设施上下文，不要求先由某个 Action 产生。

> [!question]- Q5：如何测试一次完整 Agent？
> 用 Mock LLM 预设结构化返回，通过 `AgentInvocation` 真正运行 AgentPlatform 和 Planner，断言最终 Goal、Action 调用、条件、Blackboard 数据流和不存在额外模型调用。

> [!question]- Q6：为什么 Embabel 不能直接变成 Codex Desktop？
> 它覆盖高层规划和运行过程，但文件/Shell/Git 工具、沙箱审批、会话恢复、上下文压缩、worktree、LSP、桌面 UI 等产品 Runtime 仍需实现。

## 12. 掌握等级

### 入门

- [ ] 能启动 `1.5.0` Shell。
- [ ] 能写单 Action Goal。
- [ ] 能解释 Blackboard。

### 会用

- [ ] 能用三个以上领域类型构建 GOAP 路径。
- [ ] 能使用 `OperationContext` 生成结构化对象。
- [ ] 能用 Condition 阻止不合格结果。
- [ ] 能用 `AgentInvocation<T>` 发起调用。

### 能做项目

- [ ] 有 Action 单测和全流程集成测试。
- [ ] 有真实任务评测集。
- [ ] 能设计超时、预算、重试、幂等和取消。
- [ ] 能接 ToolGroup/MCP 且限制权限。
- [ ] 能用 Process ID + SSE 支撑 Web/Desktop UI。

### 真正掌握

- [ ] 能解释并选择 GOAP/Utility/Hybrid/Supervisor。
- [ ] 能定位不可达 Goal 和 binding 冲突。
- [ ] 能设计循环、重规划和补偿，而不产生无限执行。
- [ ] 能量化框架升级或模型变化对成功率、成本和延迟的影响。
