# Embabel Agent 规划器与三种执行模式

> [!abstract] 一句话总结
> Planner 决定“已选定能力后下一步执行哪个 Action”，Focused/Closed/Open 决定“从多大范围选择 Agent、Goal 和 Action”；GOAP 默认且可预测，Utility 追求当前净价值，Hybrid 在 Utility 基础上以 Goal 终止，Supervisor 让 LLM 参与编排，四者不能与执行模式混为一谈。

## 1. 先区分两个维度

很多介绍把 Planner 和执行模式混在一起，导致概念混乱：

| 维度 | 问题 | 选项 |
| ---- | ---- | ---- |
| 执行模式 | 从哪些 Agent/Goal/Action 中选择？ | Focused、Closed、Open |
| Planner | 在可用范围内怎样选下一步？ | GOAP、Utility、Hybrid、Supervisor |

例如：你可以在 Focused 模式下明确调用一个使用 GOAP 的 Agent；也可以在 Closed 模式先选 Agent，再由该 Agent 的 GOAP 规划路径。

## 2. GOAP：默认规划器

GOAP 是 Goal Oriented Action Planning。它从当前世界状态出发，寻找一条满足 Goal 且总成本较低的路径。

学习计划例子：

```text
当前事实：UserInput
目标事实：LearningPlan

候选 Action：
understand: UserInput -> LearningRequest       cost 0.1
draft:      LearningRequest -> DraftPlan       cost 0.3
review:     DraftPlan -> ReviewedPlan          cost 0.2
finish:     ReviewedPlan -> LearningPlan       cost 0.1
shortcut:   UserInput -> LearningPlan          cost 0.9
```

两条可达路径：

```text
路径 A：understand → draft → review → finish，总成本 0.7
路径 B：shortcut，总成本 0.9
```

GOAP 会偏向路径 A。每个 Action 正常完成后，平台都会根据更新后的 Blackboard 重新规划；Action 也可以通过重规划控制信号提前触发重新规划。若 Action 抛出未捕获异常，框架会先执行 Action 重试策略，重试耗尽后将 Process 标记为失败；若需切换到备用路径，应将失败情况建模为领域状态写入 Blackboard。

### 适合 GOAP

- 终点明确。
- 领域输入/输出类型清楚。
- 动作依赖可建模。
- 需要可解释、可测试的路径。
- 希望尽量少依赖 LLM 来决定控制流。

### 不适合硬套 GOAP

- 没有明确终点，只想持续寻找高价值信息。
- Action 顺序高度依赖难以结构化的语义判断。
- 输入/输出全是无类型文本，规划图本身没有信息。

## 3. Utility AI：选择眼前最有价值的动作

Utility Planner 不先找完整 Goal 路径，而是每轮比较可执行 Action 的净价值：

```text
netValue ≈ value - cost
```

```java
@Agent(
        planner = PlannerType.UTILITY,
        description = "Continuously improve learning resources"
)
public class LearningResourceAgent {

    @Action(value = 0.8, cost = 0.2, canRerun = true)
    public ResourceList searchMissingTopics(CurrentKnowledge state) {
        // ...
    }

    @Action(value = 0.5, cost = 0.1, canRerun = true)
    public Summary summarize(ResourceList resources) {
        // ...
    }
}
```

Utility 的优势是机会主义：不要求每个动作都位于某条最短 Goal 路径上。但风险也明显：

- 贪心选择不保证全局最优。
- `canRerun=true` 时容易持续循环。
- 没有清晰终止策略就会不断消耗模型和工具调用。

## 4. Hybrid：Utility 选择加 Goal 终止

`PlannerType.HYBRID` 仍按 Utility 的净价值选择 Action，但在真实 Goal 已满足时立即终止。

它解决的典型问题是：

```text
纯 GOAP：只做通往 Goal 的最短路径，可能跳过有价值的探索动作
纯 Utility：愿意持续探索，但 Goal 已满足后仍可能继续
Hybrid：允许机会主义探索，同时在目标满足时停止
```

只有确实需要“探索 + 明确终点”时再选择 Hybrid。普通业务流程仍优先 GOAP。

## 5. Supervisor：让 LLM 选择 Action

```java
@Agent(
        planner = PlannerType.SUPERVISOR,
        description = "Create a market research report"
)
public class ResearchAgent {
    // 带 description 的类型化 Actions
}
```

Supervisor 会把可用 Action、类型 schema、Blackboard 当前 artifact 和 Goal 提供给 LLM，由 LLM 判断下一步调用哪个动作。

它仍不是完全无约束的 ReAct：

- Action 有声明的输入/输出类型。
- Blackboard 已满足的参数可被 curry 掉。
- 输出仍需要绑定为声明类型。
- LLM 只能选择开发者暴露的 Action。

### 适合 Supervisor

- Action 顺序取决于上下文语义，难以提前建图。
- 需要跨多个来源综合信息。
- 接受一定非确定性和额外模型成本。
- 领域类型仍然清楚，可以约束工具输入输出。

### 不适合 Supervisor

- 审批、支付、部署等要求严格可审计的流程。
- 顺序和依赖本来就可以用类型明确表达。
- 延迟、Token 成本敏感。
- Action 描述和 schema 质量很差。

## 6. Planner 对比

| 维度 | GOAP | Utility | Hybrid | Supervisor |
| ---- | ---- | ------- | ------ | ---------- |
| 默认 | 是 | 否 | 否 | 否 |
| 是否需要 Goal | 是 | 否 | 是 | 是 |
| 决策依据 | 前置/效果与路径成本 | 当前净价值 | 净价值 + Goal 终止 | LLM + 类型/状态 |
| 确定性 | 高 | 较高 | 较高 | 较低 |
| LLM 是否参与控制流 | 否 | 否 | 否 | 是 |
| 典型场景 | 业务流程、明确交付 | 持续优化、机会行为 | 探索后达成目标 | 语义驱动的动态组合 |

选择顺序：

```text
能用 GOAP 清楚表达？
  是 → GOAP
  否 → 是否是持续价值最大化且无固定终点？
         是 → Utility
         否 → 是否需要探索但有终点？
                是 → Hybrid
                否 → 是否接受 LLM 编排？
                       是 → Supervisor
```

## 7. Focused 模式

Focused 表示业务代码明确请求某个结果或 Agent 能力，不让平台先猜用户要哪个 Agent。

```java
var invocation = AgentInvocation.create(
        agentPlatform,
        LearningPlan.class);

LearningPlan plan = invocation.invoke(
        new UserInput("7 天学习 Embabel Agent"));
```

特点：

- 入口代码明确期待 `LearningPlan`。
- `AgentInvocation` 根据 Goal 输出类型定位 Agent。
- 范围小，最适合 REST API、事件处理和业务系统调用。
- 选择错误通常能在开发测试阶段暴露。

生产系统默认优先 Focused，因为它最可控。

## 8. Closed 模式

Closed 先根据用户意图从已注册 Agent 中选一个，选中后只运行该 Agent 内的 Action。

```text
用户输入
  → LLM/Ranker 选择 Agent
  → 在这个 Agent 的边界内选择 Goal 和规划
  → 其他 Agent 的 Action 不参与
```

Shell 默认的 `x "..."` 就体现这种用法。适合一个入口对接多个能力，但仍希望 Agent 之间保持边界。

风险：Agent 的 `description` 太相似时会选错，所以描述和真实评测集很重要。

## 9. Open 模式

Open 不先锁定 Agent，而是：

1. 从所有 Goal 中选择与用户意图匹配的 Goal。
2. 从平台全部可用 Action/Condition 中组装能实现它的临时 Agent。
3. 允许跨原始 Agent 边界组合路径。

Shell 示例：

```text
x "为我制定计划并查找配套资料" --open
```

Open 最灵活，也最难预测。它仍不会凭空发明 Java Action，但可能组合出开发者没直接设计过的路径。

生产使用前必须限制：

- 可选 Goal 范围。
- 可用 Action/Tool 范围。
- Goal 置信度阈值。
- 副作用审批。
- 最大动作数、预算和超时。

## 10. 三种执行模式对比

| 模式 | 谁选择 Agent/Goal | Action 范围 | 可控性 | 推荐用途 |
| ---- | ----------------- | ----------- | ------ | -------- |
| Focused | 业务代码明确结果 | 特定目标对应 Agent | 最高 | REST、事件、关键业务 |
| Closed | 平台先选 Agent | 单个 Agent 内 | 中高 | 多能力聊天入口 |
| Open | 平台选 Goal 并组装 | 平台全局 | 最低 | 探索、内部助手、受控实验 |

核心区别：

> **Focused 由调用方显式指定目标类型，Closed 在选定的单个 Agent 边界内规划，Open 跨 Agent 动态组合全局 Action。**

## 11. 状态变化后为什么能重规划

以两条数据获取路径为例：

```text
readLocalCache: Query -> Data, cost 0.1
callRemoteApi: Query -> Data, cost 0.7
```

Planner 初始会选择低成本的本地缓存路径。当本地 Action 返回“缓存未命中”等领域状态（或显式发送重规划信号并更新 Blackboard）时，下一轮规划即可根据新状态排除原路径并切换到远程 API。若直接抛出未捕获的运行异常，则会进入 Action 重试流程并在重试耗尽后终止 Process。

但重规划不是魔法：

- 必须事先存在备用 Action。
- 两条路径要产生兼容的领域类型。
- 失败必须被建模为可规划状态或显式重规划信号，不能只抛普通异常。
- 外部副作用必须可安全重试或补偿。
- Process 需要受最大动作数和预算约束。

## 12. 选择练习

为以下场景选执行模式和 Planner：

| 场景 | 推荐 |
| ---- | ---- |
| 订单审核后生成确定格式报告 | Focused + GOAP |
| 多个客服 Agent 共用一个聊天入口 | Closed + 各自 GOAP |
| 内部研究助手组合搜索、代码和文档能力 | 受限 Open + GOAP/Supervisor |
| 持续从信息流中选择最有价值的分析 | Focused/Closed + Utility |
| 编码 Agent 的提交、部署步骤 | Focused + 确定性流程，敏感动作审批 |

## 最小验证

1. 在 Agent 中加入两条都能生成 `LearningPlan` 的路径，并设置不同 `cost`。
2. 打开 Shell 的 planning/debug 输出，确认 GOAP 选择低成本路径。
3. 用 `AgentInvocation` 明确请求 `LearningPlan`，体验 Focused。
4. 再用 `x` 让平台选择 Agent，体验 Closed。
5. 暂时不要给有写操作的 Action 开 Open 模式。

## 自测题

> [!question]- Q1：Focused 和 GOAP 是同一维度的选项吗？
> 不是。Focused 决定调用范围和入口选择方式；GOAP 决定在已选范围内如何从当前状态规划到 Goal。

> [!question]- Q2：Supervisor 为什么比普通 ReAct 更受约束？
> LLM 看到的是声明过的类型化 Action，工具可用性受 Blackboard 输入约束，输出也要绑定为声明类型；它不能任意执行未暴露的能力。

> [!question]- Q3：为什么生产系统优先 Focused + GOAP？
> 入口结果明确、规划路径可解释、Agent 边界小，控制流不需要额外 LLM 决策，更容易测试、审计和限制副作用。
