# 🔀 多模型接入与切换

> [!abstract] 一句话总结
> 多模型不是为了炫技，而是为了在质量、成本、延迟、合规和可用性之间做工程取舍。

## 🎯 本节定位

- **本章第 5 课，多模型治理**。前置：[[01-Spring-AI项目搭建]]、[[02-ChatClient与ChatModel]]；本节在单模型之上做多 Provider / 多模型的路由与降级。
- **延伸**：框架选型对比见 [[11-SpringAI与LangChain4j对比]]。

## 📌 这是什么

Spring AI 通过不同模型 Starter 接入不同 Provider，再用 `ChatModel` / `ChatClient` 统一调用。常见组合：

| 需求 | 模型选择 |
| ---- | ---- |
| 高质量复杂推理 | 强模型 |
| 低成本分类/摘要 | 轻量模型 |
| 本地隐私数据 | Ollama / 本地模型 |
| 企业云合规 | Azure OpenAI / 私有云模型 |
| 降级兜底 | 备用 Provider |

## 🤔 解决什么问题

单模型系统容易遇到成本不可控、高峰期限流、某类任务效果差、跨境或合规限制、模型升级影响全业务等问题。多模型切换的目标是“按任务选对模型”，不是“每个请求随机换模型”。

## 🧩 常见架构

### 1. 配置级切换

适合学习项目或单环境部署：

```yaml
spring:
  ai:
    openai:
      chat:
        options:
          model: gpt-4.1-mini
```

改配置即可换模型，但粒度较粗。

### 2. Bean 级多模型

适合项目中同时使用多个 Provider 或多个 options：

```java
@Configuration
class AiModelConfig {

    @Bean
    ChatClient fastChatClient(ChatClient.Builder builder) {
        return builder
                .defaultSystem("你负责快速分类和摘要。")
                .build();
    }

    @Bean
    ChatClient reasoningChatClient(ChatClient.Builder builder) {
        return builder
                .defaultSystem("你负责复杂推理，回答前先检查约束。")
                .build();
    }
}
```

真实项目里通常会给不同 `ChatModel` Bean 配不同 Provider 或不同 options。

### 3. 路由服务

```java
@Service
class ModelRouter {

    private final ChatClient fastClient;
    private final ChatClient reasoningClient;

    String answer(TaskType type, String message) {
        ChatClient client = switch (type) {
            case CLASSIFY, SUMMARY -> fastClient;
            case REASONING, CODE -> reasoningClient;
        };

        return client.prompt()
                .user(message)
                .call()
                .content();
    }
}
```

## ⚙️ 路由策略

| 策略 | 适合场景 | 风险 |
| ---- | ---- | ---- |
| 按任务类型 | 分类、摘要、问答、代码分流 | 需要维护任务枚举 |
| 按用户等级 | 免费 / 付费 / 企业版 | 质量差异要可解释 |
| 按成本预算 | 大量低价值请求 | 可能影响体验 |
| 按失败降级 | 主模型失败转备用模型 | 输出风格可能不一致 |
| 按数据敏感度 | 敏感数据走本地或私有云 | 需要严格数据分级 |

> [!important] 简单原则
> 先做“任务类型路由 + 失败降级”，不要一开始就做复杂的动态调度平台。

## ⚠️ 常见坑

- [ ] **多模型输出不一致**：需要统一 System Prompt 和输出格式。
- [ ] **降级悄悄变差**：降级结果要打标，方便观测质量。
- [ ] **把路由写死在 Controller**：建议收敛到 Service，便于测试。
- [ ] **只看单次价格**：还要看上下文长度、重试率、延迟和失败率。

## 🎯 面试速记

> - **Q: 多模型切换解决什么问题？**
>   - A: 在质量、成本、延迟、合规和可用性之间做平衡。
> - **Q: 最实用的路由策略是什么？**
>   - A: 按任务类型选择模型，失败时降级到备用模型，同时记录降级标记。
