# Spring AI 2.x 工具调用循环与动态工具发现

## 1. 值得补什么？

原来的 [[06-Function-Calling工具调用]] 介绍了 `@Tool`，[[07-Advisor拦截器]] 介绍了 Advisor。Spring AI 2.0 中，两者有一个值得单独理解的连接点：`ChatClient` 的工具执行循环由 `ToolCallingAdvisor` 负责，可以和其他 Advisor 一起组织调用链。

```text
用户问题 → ChatClient → ToolCallingAdvisor → 模型请求工具
                                  ↑               ↓
                               模型继续 ← ToolCallingManager 执行工具
                                  ↓
                              返回最终回答
```

模型提出工具调用请求，实际方法由应用执行，结果再交还模型。循环直到模型不再请求工具，或遇到执行限制、错误等终止条件。直接调用底层 `ChatModel` 的行为需参考官方对应文档，不能把 `ChatClient` 的 Advisor 配置照搬过去。

## 🗣️ 一次工具循环如何结束？

以“订单 A123 在哪”为例：模型先请求订单查询，应用执行并返回“配送中”；模型读到结果后可以生成最终回答，也可能继续请求物流工具。每一轮都要把必要的工具请求和结果传回模型，不能把中间工具结果当作新的用户问题。
当前 Spring AI 文档中，`DefaultChatClient` 会自动注册默认的 `ToolCallingAdvisor`；需要调整配置时再显式构造。具体顺序、历史处理和接口应以项目所用版本为准。

## 2. 工具多了怎么办？

如果一个 Agent 连接多个 MCP 服务，可能注册大量工具。默认工具调用方式会把已注册的工具定义提供给模型；工具越多，上下文开销和工具选择负担可能越大。
`ToolSearchToolCallingAdvisor` 提供工具搜索入口，由模型按任务搜索，框架再把匹配的工具定义提供给模型。例如订单助手连接了订单、物流和库存工具，用户查询物流时可以先找到相关工具。工具较少时，多一次搜索未必划算，需要评估选择准确率、耗时和成本；搜索到工具也不代表获得授权，执行时仍要检查订单归属。

## 3. 学习时关注的边界

1. 对照官方文档检查 Advisor 顺序，明确记忆发生在工具循环外还是内部，不要把一次工具循环误认为多次独立用户对话。
2. 配置和测试工具调用次数限制、异常与超时，避免模型反复调用工具造成资源浪费。
3. `returnDirect` 会改变工具结果是否再送模型处理；使用前确认 API 的语义及多工具调用时的条件。
4. 工具搜索只影响模型看到哪些工具，不代替应用侧授权；敏感工具仍需校验调用者身份与权限。
