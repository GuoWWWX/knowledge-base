# AI 编程助手：Cursor / Claude Code / Codex 实战

> [!abstract] 一句话总结
> AI 编程助手可以协助理解代码、修改实现和运行检查；使用时需要给清目标、核对改动，并结合实际测试判断结果。

## 🎯 本节定位

本篇介绍如何用 AI 编程助手完成理解需求、修改代码、测试验证和总结交付，不要求掌握 Python 或 TypeScript 语法。产品设计可继续看 [[../09-标杆产品拆解/_index|标杆产品拆解]]。

## 🎯 为什么要学

AI IDE 和编程 Agent 已经从单行代码补全演进为支持仓库级检索、多文件编辑、命令执行与方案验证的工程协作工具。掌握规范的协作工作流比单纯熟悉工具界面更为重要。

## 🧩 三类能力

| 能力 | 代表工具 | 重点 |
| ---- | -------- | ---- |
| IDE 内联协作 | Cursor | 读上下文、局部改代码、规则文件 |
| 终端/仓库 Agent | Claude Code / Codex | 多文件修改、跑命令、检查 diff |
| 项目规范注入 | AGENTS.md / Rules / Skills | 让 Agent 遵守项目约定 |

## ⚙️ 实战工作流

1. 先让 Agent 读 `README`、`AGENTS.md`、关键目录。
2. 要求它复述理解和最小改动方案。
3. 让它实现一个小闭环，不要一次改太大。
4. 让它跑测试、构建、lint。
5. 要求输出改了什么、如何验证、残余风险。
6. 把反复出现的规则沉淀到 [[../05-Agent-MCP-Skills/16-AGENTS规范详解]] 或技能文档。

## 💬 好提示词模板

```text
请先阅读本模块现有实现，按现有风格做最小改动。
不要重构无关代码。
完成后运行相关测试，并汇报：
1. 改了哪些文件
2. 如何验证
3. 还有什么风险
```

## 🗣️ 一个具体任务怎么说？

例如“订单查询遇到不存在的订单时返回 404，保留现有错误响应结构；先查 Controller、Service 和相关测试，改完运行订单接口测试。”这样任务、范围和验证目标都明确，助手可以据此探索；如果本地没有数据库或测试失败，也应报告真实结果，而不是只说“已修复”。
审查时先看 diff 是否只改了目标路径，再看测试覆盖了正常订单、不存在订单和无权访问等实际业务条件；是否修改接口契约要以项目既有约定为准。

## ⚠️ 常见坑

- 直接让 Agent “优化整个项目”，容易引入无关改动。
- 不给测试命令，Agent 可能只靠静态判断。
- 不区分事实和猜测，容易接受错误解释。
- 不维护项目规则，导致每次都要重新教。

## 🎯 面试问题

> [!question]- 怎样使用 AI 编程助手完成一个可靠的修改？
> 先说明目标、上下文和修改边界，再检查产生的变更并运行适当的验证。项目约定可以写入宿主支持的规则文件，并持续维护。

## 🔗 与 AI 应用开发的关系

懂编程 Agent 能反过来帮助理解 Agent 产品：
- 工具调用：读文件、改文件、跑命令。
- 上下文工程：选择哪些文件进入上下文。
- 评估：测试是否通过、diff 是否合理。
- 安全：权限、危险命令、用户确认。
