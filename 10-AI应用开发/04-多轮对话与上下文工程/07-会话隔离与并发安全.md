# 🔒 会话隔离与并发安全

> [!abstract] 一句话总结
> 会话隔离保证用户只能访问授权的历史；并发控制保证同一会话中消息按预期顺序处理。两者都需要在服务端落实。

## 🎯 会出什么问题？

用户 A 猜到用户 B 的会话 ID，如果服务只按 ID 查历史而不检查归属，就可能看到 B 的消息。另一个问题是同一会话同时提交两条消息：两次请求可能读到同一版历史，导致回答顺序混乱或更新互相覆盖。

## 🧩 分别处理隔离和顺序

| 问题 | 处理方式 | 注意 |
| :--- | :--- | :--- |
| 用户越权 | 由服务端认证身份并校验会话归属 | 会话 ID 不是访问凭证 |
| 检索串数据 | 按租户和用户过滤记忆与文档 | 过滤规则由服务端生成 |
| 并发覆盖 | 对同一会话串行处理，或使用版本号 / 乐观锁检测冲突 | 锁超时、任务重试和多实例需要测试 |
| 消息乱序 | 保存会话内顺序号，按顺序读取 | 时间戳相同或时钟偏差时不可靠 |
| 流式中断 | 区分处理中、完成和中断 | 明确是否保存部分输出和如何重试 |

```mermaid
flowchart LR
    U["已认证用户"] --> A["验证会话归属"] --> C["读取有权访问的历史"]
    C --> S["同会话顺序处理"] --> M["模型调用"] --> P["记录状态与结果"]
```

## ⚙️ 会话锁能解决全部问题吗？

会话锁可以限制同时处理的请求，但锁过期后旧任务可能仍在执行，网络重试也可能重复提交。必要时结合请求幂等 ID、版本检查或其他能防止过期任务写入的机制；采用消息队列时也需定义顺序、失败和重复消费的处理。

## 🗣️ 两个请求同时到达会怎样？

假设会话当前版本为 5，请求 A 和 B 同时读取该版本，然后分别生成回答。如果 A 先写入版本 6，B 又用旧历史覆盖结果，A 的消息可能丢失。可以把同一会话的请求排队，或者在写入时要求版本仍为 5；B 发现版本已改变后，再按业务规则重读、重试或返回冲突。
仅在写入阶段发现冲突并不能撤销已经发生的工具副作用。涉及退款等动作时，需要独立鉴权、幂等标识和执行状态记录，不能只依赖会话乐观锁。

## 🧪 怎么验证？

使用两个用户验证读取、检索和删除权限；对同一会话并发提交两条请求，检查消息顺序与持久化结果；模拟客户端断连、模型超时和重复请求，检查状态是否可恢复。不要仅凭 Redis Key 中包含用户 ID 就认定授权已经正确。

> [!question]- 只要会话 ID 足够随机，是否可以不做权限校验？
> 不可以。随机 ID 可以降低猜测概率，但访问会话仍应由服务端验证当前用户是否有权操作。
