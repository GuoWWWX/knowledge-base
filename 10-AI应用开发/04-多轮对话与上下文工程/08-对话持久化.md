# 对话持久化

> [!abstract] 一句话总结
> 对话持久化把消息原文、模型输入快照、回复结果和记忆更新记录下来，让多轮对话可以恢复、审计、评测和排查。

## 🎯 本节定位

本篇在 [[07-会话隔离与并发安全]]、[[01-滑动窗口记忆]] 的基础上讨论会话记录的恢复与审计。对话控制见 [[09-意图识别]] 至 [[11-会话状态机]]，记忆删除与失效见 [[04-语义检索记忆]]。

## 📌 这是什么

持久化不只是保存聊天气泡。AI 应用至少要保存四类数据：用户和助手消息、会话元数据、模型调用 trace、记忆变更记录。Redis 适合短期在线读取，数据库负责长期事实和审计。
- 输入：用户消息、assistant 回复、工具调用结果、模型配置、上下文快照。
- 输出：可恢复的会话记录和可复盘的调用链。
- 目标：用户刷新页面不丢记录，线上回答异常能追到 Prompt 和记忆来源。

## 🤔 解决什么问题 / 为什么需要

- 页面关闭或刷新后，可以恢复之前的会话。
- 记录实际传入的消息和检索片段，便于排查回答问题。
- 用经过适当处理的历史构造回归样例，比较新 Prompt 或新模型的表现。
- 在允许的范围内记录关键操作、删除请求和模型输出，满足审计需要。

## 🧩 核心表设计

| 表 | 关键字段 | 用途 |
| ---- | ---- | ---- |
| `chat_conversation` | `id, tenant_id, user_id, title, status, created_at` | 会话列表和权限校验。 |
| `chat_message` | `id, conversation_id, role, content, token_count, sequence_no, status` | 原始消息和窗口来源。 |
| `chat_request_trace` | `request_id, conversation_id, model, prompt_tokens, context_snapshot` | 单次模型调用复盘（`context_snapshot` 与 07 课 `request_context_snapshot` 同义）。 |
| `memory_change_log` | `id, user_id, memory_id, action, source_message_id` | 记忆新增、更新、删除审计。 |

Redis key：
- `chat:{cid}:messages`：最近窗口。
- `chat:{cid}:summary`：当前摘要。
- `chat:{cid}:stream:{requestId}`：流式输出临时缓冲。

## ⚙️ 工作原理 / 流程

```mermaid
flowchart LR
    A[收到用户消息] --> B[DB 写 user 消息]
    B --> C[Redis 写窗口]
    C --> D[组装上下文快照]
    D --> E[调用模型]
    E --> F[DB 写 assistant 消息]
    F --> G[更新 Redis/摘要/向量记忆]
```

1. 用户消息先落库，拿到 `messageId`，再开始模型调用。
2. 构造 Prompt 时生成 `context_snapshot`，记录 message ids、summaryId、memory ids。
3. assistant 回复完成后落库，并写入 Redis 窗口。
4. 如果流式输出失败，把消息状态标记为 `failed` 或 `partial`。
5. 以关系型数据库作为事实源的一种设计是使用事务性发件箱，再由消费者幂等更新 Redis 窗口与向量库。异步链路仍需要重试、失败告警与对账；仅使用队列本身不能保证最终一致。

## 💻 Spring AI / Redis 落地点

下面是流程示意片段；相关类型和方法由应用自行实现，省略配置与错误处理。

```java
messageRepository.save(userMessage); // 应用自定义持久化接口
String answer = chatClient.prompt().user(userText).call().content();
messageRepository.save(assistantMessage(answer));
```

生产中要把模型名、temperature、tool calls、token 用量、错误码一起写入 trace。

## 🔍 VectorStore 关系

对话原文不一定全部进 VectorStore。推荐策略：
- DB 保存全量原文，用于展示和审计。
- Redis 保存最近窗口，用于在线调用。
- VectorStore 只保存抽取后的稳定记忆或高价值片段。
- `sourceMessageIds` 指回 DB 原文，便于解释和删除。

> **工程建议**：写入消息时复用请求的 `request_id`，针对业务定义幂等键和唯一约束；`(conversation_id, sequence_no)` 的唯一约束只能防止相同顺序号重复，不能单独保证同一请求重试不重复写入；当用户触发会话或记忆删除时，需联动清理数据库原文、会话摘要、Redis 缓存及 VectorStore 中的关联向量切片。

## ⚠️ 踩坑与注意事项

- 只存 assistant 最终答案，不存 Prompt 快照，线上问题很难复盘。
- Redis 不能替代数据库，TTL 过期后会话恢复会丢数据。
- 流式输出逐字落库会造成大量写放大，建议缓冲后分段或完成后落库。
- 用户删除会话时，要同步处理摘要、Redis 窗口、VectorStore 记忆和审计策略。
- 保存工具结果时要区分展示文本和原始 payload，避免敏感信息泄漏。

## 🎯 面试问题

> [!question]- 对话系统为什么既用 Redis 又用数据库？
> Redis 负责低延迟读取最近窗口和临时流式状态；数据库负责长期保存、恢复、审计和离线评测。

> [!question]- trace 里应该记录什么？
> requestId、模型参数、上下文片段 ID、token 用量、工具调用、错误信息和输出状态。

> [!question]- 如何处理用户删除会话？
> 删除或脱敏 DB 消息，清 Redis key，让相关 VectorStore 文档失效，并记录合规允许的删除审计。

## ✅ 精通检查清单

- 能设计 conversation、message、trace、memory log 四张表。
- 能说明 Redis 和 DB 的职责边界。
- 能处理流式输出成功、失败、取消三种状态。
- 能把 VectorStore 片段和源消息关联起来。
- 能基于历史记录构建离线回归样例。
