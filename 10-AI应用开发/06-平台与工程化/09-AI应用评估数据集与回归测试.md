# AI 应用评估数据集与回归测试

> [!abstract] 一句话总结
> AI 应用上线后最怕“改 prompt / 换模型 / 改召回后悄悄变差”，所以必须把真实 badcase 沉淀成评估数据集并接入回归测试。

## 🎯 本节定位

本篇承接 [[08-LLM评估指标体系]] 和 [[07-Ragas评估实践]]，介绍样例来源、数据字段和回归流程。评估数据的采集与展示可参考 [[06-Langfuse接入]]。

## 🎯 为什么需要回归测试

模型版本、提示词、知识库、工具描述或重排参数变化后，同一个问题的回答可能改变。固定一组有代表性的样例，可以在发布前发现效果退化。

## 📚 评估数据集从哪里来

| 来源 | 价值 | 处理方式 |
| ---- | ---- | -------- |
| 线上 badcase | 最真实 | 脱敏后加入回归集 |
| 高频问题 | 覆盖核心业务 | 根据业务风险和预算确定样本数量 |
| 边界问题 | 测安全和鲁棒性 | 越权、注入、无答案、歧义 |
| 人工构造 | 补覆盖 | 用模板生成但要人工审核 |
| 历史工单 | 贴近客服/办公场景 | 抽取问法、标准答案和证据 |

## 🧩 数据集字段设计

```yaml
id: rag_refund_001
task_type: rag_qa
user_query: "会员退款规则是什么？"
expected_answer: "..."
expected_sources:
  - "refund_policy_v3.pdf#page=2"
must_contain:
  - "7天内"
must_not_contain:
  - "无条件退款"
metadata:
  tenant: demo
  risk_level: low
  tags: [客服, 退款, RAG]
```

## 🔄 回归测试流水线

```mermaid
flowchart LR
    A[修改 Prompt/模型/知识库] --> B[跑离线评估集]
    B --> C[自动打分]
    C --> D[人工抽查坏例]
    D --> E{是否达标}
    E -->|是| F[灰度发布]
    E -->|否| G[回滚修改]
    F --> H[线上反馈进入数据集]
```

## 📊 指标体系

| 类型 | 指标 | 说明 |
| ---- | ---- | ---- |
| RAG | faithfulness、context precision、召回命中 | 答案是否基于证据 |
| Agent | 工具选择准确率、步骤成功率 | 是否会选对工具并完成任务 |
| 安全 | 越权率、敏感信息泄露率 | 是否触发安全风险 |
| 体验 | 首 token 延迟、总耗时、用户点赞率 | 是否能被真实用户接受 |
| 成本 | tokens/次、模型成本/租户 | 是否可规模化 |

> [!important] 保持评测结果可信
> - 将调优样本与最终验收集分开，避免测试答案泄露到提示词中。
> - 固定数据集、知识库快照和裁判模型配置，便于比较。
> - 对越权、敏感信息泄露和高危工具误调设置单独的安全门槛。
> - 对临界结果多次复测，观察波动；重复测试不能消除随机性。

## 🧰 工具组合

- **Langfuse**：trace、dataset、prompt 版本、人工标注。
- **promptfoo**：本地/CI 回归测试，适合 prompt 和模型对比。
- **Ragas**：RAG 指标评估和测试集生成。
- **自研表**：业务标准答案、权限、证据、风险等级。

## ☕ Java 项目落地

1. 线上每次调用生成 `trace_id`。
2. 用户差评、人工标注、异常 trace 进入 badcase 池。
3. 每周把 badcase 脱敏后加入 eval dataset。
4. CI 中跑核心数据集，低于阈值禁止发布。
5. 灰度后继续按 trace 抽样复核。

## ❓ 面试问题

> [!question]- 如何持续检查模型或提示词变更是否带来退化？
> 使用固定版本的数据集，对模型、提示词和检索参数的变更进行回归；线上问题脱敏后可以补充进样例集，并注意调优集与验收集隔离。
