# Git 分支模型与团队协作

## 1. 分支解决什么问题

分支只是一个指向 commit 的可移动引用。它不复制整个项目，创建分支主要是创建一个新的指针：

```text
A---B---C  main
     \\
      D---E  feature/login
```

分支的价值是隔离不同发布节奏和不同工作意图，而不是让每个人随意创建长期分叉。

## 2. 先确认团队模型

| 模型 | 核心做法 | 适合场景 |
| --- | --- | --- |
| Trunk-Based | 短分支、频繁合入 `main`、用 feature flag 隔离未完成代码 | 高频发布、CI/CD 成熟 |
| GitHub Flow | `main` + 短期功能分支 + PR | 流程轻、持续部署 |
| Git Flow | `main`、`develop`、release/hotfix 等职责分支 | 有明确版本发布窗口 |

不要把 Git Flow 当作 Git 的强制规则。仓库保护规则、CI 和发布系统才是团队的最终约定。

## 3. Git Flow 分支职责

| 分支 | 创建来源 | 合入目标 | 规则 |
| --- | --- | --- | --- |
| `main` | 长期存在 | - | 生产基线，禁止直接提交 |
| `develop` | 长期存在 | - | 下一版本的集成分支 |
| `feature/*` | `develop` | `develop` | 新功能，完成后删除 |
| `fix/*` | `develop` | `develop` | 测试环境缺陷修复 |
| `release/*` | **`develop`** | `main`、`develop` | 只修发布阻断问题 |
| `hotfix/*` | `main` | `main`、`develop` | 线上紧急修复 |

### Release 为什么从 develop 创建

待发布功能已经集成在 `develop`。从 `main` 创建会缺少这些功能，只适合 hotfix，不适合新版本 release。

```bash
git switch develop
git pull --ff-only origin develop
git switch -c release/v1.2.0
```

## 4. 一个功能的协作闭环

```bash
git switch develop
git pull --ff-only origin develop
git switch -c feature/user-login

# 开发、测试、精确暂存、提交
git add src/login.ts tests/login.test.ts
git commit -m "feat: add user login validation"
git push -u origin feature/user-login
```

然后创建 MR/PR，等待 CI 和评审。合入后删除本地和远程功能分支：

```bash
git branch -d feature/user-login
git push origin --delete feature/user-login
```

## 5. 协作边界

- `main`、`develop` 和发布分支应启用保护，禁止直接 push 和 force push。
- 分支名表达业务意图，例如 `feature/payment`、`fix/login-timeout`。
- 一个分支尽量对应一个 MR/PR，不把无关重构混入功能分支。
- 分支已经由多人使用，就把它视为公共历史，不再 rebase 改写。
- hotfix 合入 `main` 后必须同步到 `develop`，避免下一版本重新引入旧问题。
