# Git 冲突处理与历史整理

## 1. 冲突是什么

冲突表示 Git 无法替你判断两组修改的最终语义。它可能发生在两个分支修改同一段、修改与删除同一文件，或 rebase 重放提交时基线发生变化。

先看状态，不要直接猜：

```bash
git status
git diff
```

## 2. Merge 冲突处理

```bash
git merge origin/develop
git status
```

处理冲突文件中的标记：

```text
<<<<<<< HEAD
当前分支内容
=======
被合并分支内容
>>>>>>> origin/develop
```

保留正确业务结果并删除标记，然后：

```bash
git add <resolved-files>
git diff --cached
git commit
```

放弃本次 merge：

```bash
git merge --abort
```

## 3. Rebase 冲突处理

```bash
git status
# 编辑冲突文件并完成验证
git add <resolved-files>
git rebase --continue
```

若基线选错或冲突处理方向不对：

```bash
git rebase --abort
```

`git rebase --skip` 只有在确认当前提交的变更已经由其他提交包含时才能使用，不能把它当成跳过冲突的快捷键。

## 4. 解决冲突的判断顺序

1. 确认当前操作是 merge、rebase 还是 revert。
2. 阅读两边代码及提交说明，理解各自要解决的问题。
3. 以业务不变量、接口契约和测试为判断依据。
4. 解决后查看完整 diff，不只看冲突文件。
5. 运行单测、集成测试和构建，再继续操作。

## 5. 保持提交可审查

- 功能代码与无关格式化分开。
- 不留下 `tmp`、`test2`、`fix again` 等无法理解的提交说明。
- 提交前用 `git diff --cached` 确认暂存区内容。
- 已经共享的提交不要靠 reset/rebase 重新排列，使用新的修复提交。

## 6. 交互式 Rebase 的安全用法

```bash
git branch backup/before-rebase
git rebase -i HEAD~5
git log --oneline --graph --decorate -10
git diff origin/develop...HEAD
git push --force-with-lease
```

先建立临时保护分支，再执行 `squash`、`reword` 或 `drop`。推送改写后的历史前确认分支由自己独占。
